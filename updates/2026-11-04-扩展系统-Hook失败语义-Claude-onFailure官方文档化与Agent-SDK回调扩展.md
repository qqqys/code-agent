# 扩展系统 · 生命周期 Hooks：Claude `onFailure` 官方文档化并扩到 Agent SDK 回调，五家失败语义重新核对

日期：2026-11-04
能力字段：`extension-hooks`（扩展系统 · 生命周期 Hooks）

## 本次改动

本次以 Claude Code 一个已发布的新条目为起点，把「Hook 失败时放行还是阻断」在五家全部重新核对，结果作废了三条旧结论（Claude 的 `onFailure` 未文档化、Codex 官方页不列模型请求事件、Kimi 的启动失败归类未确认），并补齐了 Claude 的平台条件 fail-closed 默认与 Agent SDK 回调侧的完整语义。

**Claude Code 的 `onFailure` 已从更新日志走进官方文档**（官方 Hooks 参考页 2026-11-04 以 `.md` 形式复核，286,102 字节，比 2026-10-28 记录的 282,379 字节增加）：

- **取值集合与默认值有了官方口径。** `#### Command hook fields` 表新增行逐字为 “`onFailure` | no | Whether the action that triggered the hook goes ahead when the hook fails: `"continue"` or `"block"`. See [Block the action when a hook fails](#block-the-action-when-a-hook-fails) for `"block"` and for leaving the field unset. Requires Claude Code v2.1.295 or later”，`#### HTTP hook fields` 表逐字为 “`onFailure` | no | What happens to the action when the hook fails: `"continue"`, the default, or `"block"`. See [Block the action when a hook fails](#block-the-action-when-a-hook-fails). Requires Claude Code v2.1.295 or later”，即取值只有 `"continue"` 与 `"block"`、默认 `"continue"`。**作用域问题也一并回答**：该键不在 `#### Common fields` 公共字段表里（公共字段仍只有 `type`、`if`、`timeout`、`statusMessage`、`once`），`prompt`、`agent` 与 `mcp_tool` 三张字段表也都没有它，因此是按 Handler 类型生效而不是按事件或按作用域覆盖。
- 参考页新增整节 “Block the action when a hook fails”，开头逐字为 “On most events, when a hook fails or times out, Claude Code still carries out the action. A policy hook with a wrong path or a crashing script then lets everything through. To block the action instead, set `"onFailure": "block"` on a `command` or `http` hook. Requires Claude Code v2.1.295 or later. For Agent SDK callback hooks, see [Block the action when a callback fails](https://code.claude.com/docs/en/agent-sdk/hooks.md#block-the-action-when-a-callback-fails).”
- **「失败」被拆成五类逐字定义**：Can't start（“a command hook fails to start, for example because the script or executable doesn't exist”）、Exit code other than 0 or 2（“counts for a command hook even if it printed JSON that allows the action, such as `permissionDecision: "allow"`. To return a JSON decision, exit 0”）、HTTP error（“an HTTP hook's connection fails, or the response status isn't 2xx”）、Timeout（“the hook reaches its `timeout`”）、Invalid output（“the JSON output can't be parsed or fails schema validation. For an HTTP hook, a 2xx body that is neither empty nor a JSON object also counts. Plain-text stdout from a command hook isn't a failure”）。
- **`PermissionRequest` 是效果上的例外**：逐字为 “With `"block"` set, a failure does what [exit code 2 does on that event](#exit-code-2-behavior-per-event), except on `PermissionRequest`, where it denies the request.”，而同页 “Exit code 2 behavior per event” 表的 `PermissionRequest` 行写 “Exit code 2 isn't honored for this event and the permission flow proceeds unchanged. Deny through the `decision` object instead”，两处对照说明 `"block"` 在该事件上比退出码 2 更强。
- **无效范围逐字列出**：“The field has no effect on these hooks: **`Stop`, `SubagentStop`, `TaskCompleted`, and `TeammateIdle` hooks**: exit code 2 on these events sends Claude back to keep working, and Claude can't repair a hook that won't run” 与 “**Background command hooks**: command hooks that set `async` or `asyncRewake`”。
- 用户可见文案与自测办法：`PreToolUse:Bash hook error: [node ${CLAUDE_PROJECT_DIR}/.claude/hooks/check-command.js]: failed; blocking because onFailure is "block"` 加解释器自己的错误输出，“After a timeout, the message says `timed out` instead of `failed`.”、“Without `onFailure` set, the same missing script is a non-blocking error and `ls` runs.”
- `#### Timeouts` 与 `#### Other exit codes` 两节的 non-blocking 说明都改成带前置条件——“On `PreToolUse`, a timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call, except for hooks whose failure blocks the action.”、“To block the call when a `command` or `http` hook times out, set `onFailure: "block"`.”、“To block the action when the hook can't start, set `onFailure: "block"`.”，WARNING 也改成 “Exit code 1 without valid JSON output is a non-blocking error unless the hook is one whose failure blocks the action, even though 1 is the conventional Unix failure code.”
- **Hooks 指南页同样收录**（66,413 字节，此前记录 66,090 字节）：`#### Hook output` 小节逐字为 “With an exit code besides 0 and 2 and no valid JSON output, the action proceeds on most events, unless the hook is one whose failure blocks the action. A hook with `onFailure` set to `"block"` is one example.”，`## HTTP hooks` 小节逐字为 “**Any other status, or the request fails**: Claude Code reports a non-blocking error and lets the action continue. To make a failed endpoint block the action, set `onFailure: "block"` on the hook.”
- **据此作废旧结论「官方 Hooks 参考的公共字段表与 Hooks 指南在核对日期都没有出现 `onFailure`，因此取值集合、默认值与能否按事件或按作用域覆盖记为未确认」**——三项全部有了官方口径。

**Claude 另有一条平台条件的 fail-closed 默认，此前只以 v2.1.310 的一条修复记过、本次按官方文档展开**（“Failed hooks on Windows without Git Bash” 一节）：Windows 上没有 Git Bash 时，shell 形式（未设 `shell`）的 `PreToolUse` 或 `PermissionRequest` command Hook 只要退出码不是 0 或 2 就算失败并阻断该次调用，逐字为 “Without Git Bash, any exit code other than 0 or 2 from that hook counts as a failure, even when it prints JSON that doesn't deny the call.”，节首 NOTE 为 “On Windows without Git Bash, a shell-form `PreToolUse` or `PermissionRequest` command hook that fails with `onFailure` unset can instead block the tool call.”，错误文案 `blocking because Git Bash wasn't found, so only exit code 0 or 2 counts as this hook's verdict.`（“Before v2.1.309, the message read …” 给出旧措辞）。官方给的五条修法里，恢复放行的一条正是 “**The call should go ahead when the hook fails**: add `"onFailure": "continue"` to the hook”；而 “**A PowerShell guard hook that must block on failure**: with `onFailure` unset, it stops doing so once Git for Windows is installed and Claude Code finds Git Bash. Add `"onFailure": "block"` so a failure or a timeout blocks the call with or without Git Bash. Also set `"shell": "powershell"` …” 说明这条默认会随环境安装而消失，跑单个 `.exe` 的 Hook 则改用 exec form 加 `"onFailure": "block"`。

**v2.1.317 把同一开关扩到 Agent SDK 的回调 Hook**（Release 2026-11-03T01:25:46Z，更新日志固定到提交 `964d69565952a176ac1975ed218362991db71433`，2026-11-03T01:25:28Z，`CHANGELOG.md` 1,142,787 字节、最新段为 `## 2.1.317`），逐字为 “Added `onFailure: "block"` for Agent SDK hook callbacks, so a callback that fails blocks the action instead of letting it run”。官方 Agent SDK Hooks 页（`.md` 形式 49,119 字节）新增整节 “Block the action when a callback fails”：

- **字段写在 matcher 上而不是单个回调上**，Matchers 表新增行逐字为 “`onFailure` | `"continue" \| "block"` | `undefined` | What a failed callback does. Set `"block"` to block the action when a callback fails. In Python, use `on_failure`”，版本条件为 “Requires TypeScript Agent SDK v0.3.317 or later, or Python Agent SDK v0.2.177 or later.”，官方示例是 Python 的 `HookMatcher(matcher="Bash", hooks=[check_policy], on_failure="block")` 与 TypeScript 的 `PreToolUse: [{ matcher: "Bash", hooks: [checkPolicy], onFailure: "block" }]`。
- **默认行为有了明确的可观测信号**：“On most events, if a callback throws or returns output that fails validation, the action goes ahead and your app receives an `SDKInformationalMessage` warning whose `tag` is `hook_callback_failed`. A `PreToolUse` guard that crashes then lets the tool call reach the normal permission flow. A callback that returns nothing, such as a path with no `return`, also counts as failing. In Python, read `tag` from `SystemMessage.data`.”，阻断后 “The tool result includes `failed; blocking because onFailure is "block"`, and Claude doesn't see your error text.”，并提醒 “Return `{}` when the callback has no opinion. With `"block"` set, a path with no `return` blocks the action. A callback that catches its own error and returns `{}` isn't failing, so let the error propagate from a guard.”
- **事件例外三条**：`Stop`/`SubagentStop`/`TaskCompleted`/`TeammateIdle` “ignore the option, so the action goes ahead”；`PermissionRequest` “the block counts only if it arrives before your `canUseTool` callback answers”；`PostToolUse` “the tool has already run, so Claude receives the failure as feedback”。超时一句为 “A callback that exceeds its timeout follows Hook timeout. With `"block"` set, a timeout also blocks `PreCompact`, `Elicitation`, and `WorktreeCreate`.”，而不设 `"block"` 时的逐事件默认（`PreToolUse` 阻断该次工具调用、`UserPromptSubmit`/`UserPromptExpansion` 阻断提示词、`PreModelSwitch` 阻断切换、`PostToolUse`/`PostToolUseFailure` 保留工具结果继续、`Stop`/`SubagentStop` 算没有决定、`SessionStart` 算没有输出、其余只记录继续）与既有记录一致。
- **新增启动期失败形态**：“With `"block"` set, the query fails at startup and sends no prompt when it can't honor the option”，两条分别是 “**Claude Code doesn't support the option**: the error includes `does not honor`.” 与 “**The session was already running and didn't register your hooks**: the error includes `did not register your hooks`.”
- 核对日期最新 Release 为 v2.1.318（2026-11-04T00:01:03Z），其更新日志没有 Hook 失败语义条目；v2.1.313–v2.1.316 之间涉及 Hook 的三条是 v2.1.314 的 “Fixed a PreCompact hook with very large output making compaction fail or repeat; each hook's output is now cut at 10,000 characters”、“Fixed hooks matching Bash not running on shell commands started by the Monitor tool; such hooks can block or ask, but not approve or rewrite those commands”、“Changed hook `if` conditions such as `Monitor(tail *)` to match the Monitor tool's shell commands as `Bash(tail *)` matches Bash's” 与 v2.1.316 的 “Fixed PowerShell hooks not blocking on exit code 2 when the command begins with a type cast, `param`, `using` or an attribute”，都不改 `onFailure` 的取值、默认值或并发口径。

**作废旧结论「Codex 官方 Hooks 页仍只列 12 个事件、`PreModelRequest`/`PostModelRequest` 记为已发布但官方文档未列」**：官方 Hooks 页（`.md` 形式 2026-11-04 复核，48,643 字节，比 2026-10-28 记录的 47,133 字节增加）已收录这两个事件、全页共 14 个——触发时机表新增一行逐字为 “For each model request attempt | `PreModelRequest`, `PostModelRequest`”，`matcher` 支持表新增一行逐字为 “`PreModelRequest`, `PostModelRequest` | not supported | Both events run for each model request attempt”，说明段逐字为 “Use these hooks to log model requests, including retries within the same turn. `PreModelRequest` runs before each attempt. `PostModelRequest` reports the outcome. Both receive the model and `turn_id`, plus `agent_id` and `agent_type` when available. Hook output is diagnostic only. It can't change the model's context or block a request.”，并以 “`PostModelRequest` includes three additional fields:” 引出 `status`、`error` 与 `token_usage`；全页没有任何说明事件总数的句子，原有 12 个事件的四个分组未变。失败语义侧逐字未变：全页仍没有 `onFailure`、`on_failure`、`failClosed` 或任何同类键，失败、超时与畸形响应默认放行的四句（`PreToolUse` 回调错误/超时/畸形响应不阻断工具、`mcp_tool` 的错误与缺失 Server 不阻断、`SessionEnd` 超时或错误只报为 hook failure、退出 0 无输出算成功）与唯一 fail-closed（`PermissionRequest` 的 `updatedInput`/`updatedPermissions`/`interrupt` 保留字段）都在，并发口径与 Handler 口径 “`command` and `mcp_tool` handlers are supported. `prompt` and `agent` handlers are parsed but skipped.” 也未变。发布坐标：核对日期最新 Release 是 alpha 通道的 rust-v0.168.0-alpha.1（2026-11-04T02:54:53Z）与 rust-v0.167.0-alpha.4（2026-11-03T02:24:00Z），两者发布说明都只有 “Release <版本号>” 一行、没有任何条目，最新非 alpha 仍是 rust-v0.165.0（2026-10-27T20:09:38Z），仓库 `CHANGELOG.md` 在 main 只有一条与 Hook 无关的 `## Unreleased`（“Fix missing command lifecycle events when unified exec cannot create a process…”，#44557）。

**作废旧结论「Kimi 文档没有单独描述命令无法启动的情形，启动失败属于哪种取值记为未确认」**：中文 Hooks 文档坐标前移到提交 `5f3ab5fac81e050fc2fa10787dd560655f377d16`（2026-10-29T12:43:07Z，随 PR #4062 “feat: remote environments for SSH and Docker execution targets (phase 1: creation-time binding)”，9,523 字节，此前坐标 `494df61ce9858c70a9f37a996614534bc9b1cd12` 下同一文件为 8,319 字节），新增一整段失败处置口径，逐字为「当 hook 执行失败时（无法启动、超时或以错误退出码结束），CLI 会记录日志，并在会话中显示一次警告；之后的失败只记录日志。阻断决策保持 fail-open：失败的 hook 永远不会阻断操作。」——该段在历史坐标下不存在，据此确认「命令无法启动」被官方明确归入失败形态之一且仍按 fail-open 处理。新记的两点是失败只在会话里警告一次、之后静默进日志（这条一次警告按 Hook、按事件还是按会话计数官方没有说明，记为未确认），以及配置面逐字为「`[[hooks]]` 只允许这四个字段，多写会导致配置文件加载失败。」，四字段即 `event`、`matcher`、`command`、`timeout`，**因此在这一家连把 `onFailure` 一类键写进配置都会让配置文件加载失败**。其余逐字未变：退出码四行表（`0` 放行、`2` 阻断、其他非零「默认放行（fail-open）」、超时或崩溃「默认放行（fail-open）」）、`timeout` 「超时秒数，范围 1–600；默认 30 秒」、「非 Windows 平台上，hook 进程运行在独立进程组中；超时后 CLI 先发送信号让脚本有机会善后，再强制终止。」、可阻断事件只有 `PreToolUse`/`Stop`/`UserPromptSubmit` 而其余为观察型即发即忘、同一事件命中的多条规则并行且 `command` 完全相同只运行一次；全页仍无 `onFailure`、`sequential` 与任何并发数字上限。发布坐标：核对日期最新稳定 Release 为 `@moonshot-ai/kimi-code@2.4.1`（2026-10-30T09:50:16Z），最新 canary `2.5.0-canary.20261104024245-8fc5e22`（2026-11-04T02:57:42Z）同批提交只涉及 wire reader 最低版本、本地 FetchURL 允许私网地址、编辑时保留 UTF-8 BOM 与 MCP OAuth 取消隔离，不涉及 Hook 失败语义。

**Qwen Code 与 Qoder CLI 的「无 `onFailure`」结论经坐标前移后复核成立**：

- Qwen `docs/users/features/hooks.md` 前移到提交 `35aa4b76ae10a458632d23c9b0052af5a31b3885`（PR #16196 “fix(core): require explicit trust for settings-file project hooks”，2026-11-03T15:54:00Z，98,620 字节，此前坐标 `d13ff87407d673c547726b43928dedba0465ffa1`），全页仍无 `onFailure`、`on_failure`、`failClosed` 或任何同类键；退出码三档、HTTP “never follow redirects. - Qoder Hooks 页规范地址已改为 `https://docs.qoder.com/cli/hooks`（`en/cli/hooks` 会跳过去），全页仍没有 `onFailure`、`on_failure`、`failClosed` 或任何把失败改成阻断的配置键，阻断只能靠退出码 2；退出码三档逐字为 “Hooks control behavior through exit codes and stdout.”、“`2`: blocking; stderr content is fed back to the Agent (only effective for events that support blocking).” 与 “Other values: non-blocking error; stdout is ignored, stderr is written to diagnostic logs, the main flow continues.”，JSON 侧 “`deny` is equivalent to exit 2.”，四类 Handler 的 `timeout` 默认值仍是 command 600、http 600、prompt 30、agent 60，事件表仍 23 个；页面仍没有描述 Hook 命令启动不了或超过 `timeout` 之后的具体后果，这两点继续记为未确认。本次补录按事件的硬编码例外逐字文本：`WorktreeCreate` “The hook must return the absolute path of the worktree; any non-zero exit code is treated as failure.”、`ConfigChange` “Exception: when source is policy_settings, hooks still fire for audit purposes but the change is enforced and cannot be blocked.”、`StopFailure` 与 `InstructionsLoaded` 各写 “Notification only — output and exit code are ignored.”、`WorktreeRemove` “Notification only — failures are surfaced via stderr.”，以及 `asyncRewake` “When `true`, runs in the background; if it exits with code 2, the CLI builds a system reminder from stderr/stdout/error and wakes the model — useful for long-running checks”，即后台 Hook 的退出码 2 不阻断任何动作、改成唤醒模型。Release Notes（HTML 1,419,034 字节）最新条目为 **CLI 1.1.82（November 3, 2026，“Session status reporting via OSC 7501 and reconnection fixes”）**，其前是 1.1.81（October 29, 2026，“Introducing CodeMode and More Reliable Session Continuity”），这两版都没有任何提到 Hook、退出码、超时、信任或阻断的条目；仍是最新 Hook 条目的三版为 1.1.80、1.1.79 与 1.1.78，CLI 1.0.29 的 “Aligned SessionEnd hook timeout and PreToolUse fail-closed behavior with strict semantics” 仍未在 Hooks 页展开、其 fail-closed 覆盖哪些失败形态继续记为未确认。
