# 后台与并行：Claude Code v2.1.302 把 Fork 默认开启扩到 `claude -p`、Agent SDK、桌面端与 VS Code，Kimi Code 的 `Agent` 默认其实是前台，五家并发上限与查看停止入口补齐

Claude Code 于 2026-10-16 发布 v2.1.302（[Release](https://github.com/anthropics/claude-code/releases/tag/v2.1.302)，2026-10-16T20:53:06Z），其更新日志（固定到提交 `c017428c8c27e604840435048d5bce6a9a22c040`）有两条此前完全没有进入本仓库的一手确认变更，且都正落在 `agent-background` 这一个字段上。第一条逐字为 “Changed fork subagents (`subagent_type: "fork"`) to be on by default in `claude -p`, the Agent SDK, the desktop app and VS Code, as they already are in the terminal; `CLAUDE_CODE_FORK_SUBAGENT=0` turns them off, and `claude mcp serve` never offers them”，即 Fork 模式默认开启的范围由交互会话扩到四个非终端 Surface，并第一次给出关闭它的环境变量取值与 `claude mcp serve` 的例外。第二条逐字为 “Changed the desktop app and VS Code to always run the main conversation's subagents in the background, as the terminal does, rather than let Claude choose; a subagent's own Agent calls in `claude -p`, the Agent SDK, the desktop app and VS Code now run in the foreground by default”，把桌面端与 VS Code 的前后台决定权从模型收回给产品，同时给「Subagent 自己再派生的 Agent」定了与主会话相反的默认值。旧记录的 Claude 列只写「支持后台与并行；Fork 模式开启时统一后台（v2.1.232 起交互会话默认开启）」，两个 Surface 维度的默认值都不在里面。

顺着这两条复核官方 Subagents 页的 “Run subagents in foreground or background” 一节与并发上限段后发现，Claude 列还有一整块机制从未记录：前后台是一条四级判定链（进程内 Agent Team 队友派生一律前台，且定义写 `background: true` 时官方逐字为 “Claude Code refuses with an error to spawn a teammate's subagent whose definition sets `background: true`.” → `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 一律前台 → Fork 模式开启时一律后台 → Fork 模式关闭时默认后台、Claude 需要结果时改前台）；并发上限逐字为 “By default, when 20 subagents are running in a session, spawning another with the Agent tool fails with `Concurrent subagent limit reached`, and the error tells Claude not to retry.”，`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 可改为任意正整数（需 v2.1.217 及以上）、ultracode 会话豁免，而 `/subtask` 启动的会话内 Fork 占槽位却永不被上限拦住、恢复已结束的 Subagent 不检查上限地占新槽位因而可以把运行数推到上限之上、workflow agent 与 Agent Team 队友走各自的上限；工具边界逐字为 “Background subagents run with a smaller built-in tool set than foreground subagents, except for conversation forks and resumed foreground subagents.”；快捷键逐字为 “Press **Ctrl+B** to background a running task”。发布状态与文档缺口需要标条件：官方 Subagents 页在核对日期仍逐字写 “Fork mode is off in non-interactive mode with `-p` and in the Agent SDK unless you turn it on.”，与 v2.1.302 更新日志直接冲突，且该页前后台一节根本没有出现桌面端、VS Code、`claude -p` 或 Agent SDK，因此四个 Surface 的默认值只有一手更新日志支撑。本次按更新日志记录并保留这处冲突。

复核另外四家时发现 Kimi Code 列的结论方向是错的。旧记只写「支持后台与并行」，而官方工具文档（main 提交 `4a82a07f08d0b135c4349c20aae53a2d51e5c3fa`，22,181 字节）的 `Agent` 参数表把 `run_in_background` 的默认值写成 `false`，正文逐字为 “前台模式下父 Agent 等待 subagent 完成再继续；后台模式立即返回任务 ID，完成时通过合成 User 消息自动回到 main agent。多个前台 `Agent` 调用在同一步运行时，TUI 会合并展示，并为每个 subagent 显示运行、等待、完成或失败状态以及已耗时长。”，即 Kimi 的默认落点是前台而不是后台。同一页还给出 `AgentSwarm` 的两个此前没有记录的数字与开关：“本工具最多支持 128 个 subagent，会等待全部 subagent 完成，并返回聚合报告。”、“默认情况下，本工具会逐步提升并发且不设上限（立即启动 5 个 subagent，之后每 700 毫秒再启动 1 个）；将 `KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY` 设为正整数可限制该阶段同时运行的 subagent 数量，不设置则表示不限制。若设置为非正整数的值，本次 AgentSwarm 调用会立即失败。”，以及 “在 TUI 中，前台 swarm 会在输入框上方显示实时 `Agent swarm` 进度面板。” 与「一次模型响应调用 `AgentSwarm` 时该调用必须是唯一工具调用」。配置文档的 `[background]` 一节逐字写明它“控制后台任务（通过 `Bash` 工具或 `Agent` 工具的 `run_in_background=true` 参数启动）的并发数”，`max_running_tasks` 因此是覆盖后台 subagent 的并发键，`KIMI_CODE_BACKGROUND_MAX_RUNNING_TASKS` 覆盖它且不设置表示无上限；同一节的 `print_background_mode` 默认 `"steer"`，官方逐字写 print 模式下 “只要还有未决的后台任务，Kimi Code 在 main agent 的 turn 结束后不会退出”。发布状态可以确认为已发布而不是 main 分支：Release `@moonshot-ai/kimi-code@2.2.0`（2026-10-14T15:31:16Z，标签指向提交 `472192c34c1efad89a369870eff0da0b708ce9bb`）下的同一工具文档（22,038 字节）已含 `run_in_background`（默认 false）、128 个上限与 `KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY`。`Ctrl+B` 只有变更记录支撑——0.19.0（2026-06-22）逐字为 “允许使用 `Ctrl+B` 将长时间运行的前台命令和子 Agent 移动到后台任务，并通过 `/tasks` 面板查看它们。”，而现行交互指南只写 “后台运行：命令执行期间按 `Ctrl+B` 可将其转为后台任务。”、Slash 命令表没有任何快捷键，这处文档缺口按原样记录。另发现 Kimi 两份官方文档的节名互相矛盾：环境变量文档把 `bash_task_timeout_s` 与 `print_background_mode` 归到 `[task]`，配置文档把它们定义在 `[background]` 下。

Qwen Code、Codex 与 Qoder CLI 三列本次由一句话补成完整机制。Qwen 的 Subagents 文档在 main 提交 `97925919acb92b089d817991bfefe4545601c8f6` 与 stable 标签 v0.25.2（指向提交 `8a415cb628db88844e0196bdfdcce83b4f88d812`）下字节数相同均为 41,363 字节、四句关键结论逐字一致，因此下述行为已随 stable v0.25.2 发布：顶层命名 Subagent 默认后台并经完成通知回传、`run_in_background: false` 改为 inline、Fork “Always detached; parent continues immediately” 且 “headless forks always use the background path”、委派外部执行器的内置 `claude-code` 与 `codex` Agent 反而默认前台、调用方自有 `working_dir` 的匿名派生固定前台并拒绝显式后台请求、交互 TUI 与 ACP 共享一条至多 20 条的完成通知队列并带明确的驱逐与永不驱逐规则而 headless CLI 的本地队列不受该上限约束。`background` 不在 frontmatter 字段表里、只出现在 YAML 示例与散文中，这一点也一并记录。Codex 官方根本没有前台与后台两种模式的划分，只写 “ChatGPT Work and Codex can run subagent workflows by spawning specialized agents in parallel and then collecting their results in one response.” 与 “When many agents are running, Codex waits until all requested results are available, then returns a consolidated response.”，`agents.max_concurrent_threads_per_session` 的默认值栏为空且全页写 “When unset, Codex chooses the default.”；查看与停止入口按 Surface 分成五种（CLI `/subagents` 与直接要求 Codex steer/停止、审批时按 `o` 先打开非活动线程、IDE 扩展的 background-agent 面板、桌面 App 的活动入口、ChatGPT Work 网页侧栏只读的 **Active** 与 **Done** 两个列表且 “it doesn't provide controls to stop or steer an individual subagent.”）。Qoder CLI 的 `background` 字段逐字为 “Whether the Subagent should launch in the background by default. Requires background Subagent sessions to be enabled.”，但启用后台 Subagent 会话的开关在 Subagent 页、Parallel Tasks 页与设置参考里都找不到（设置参考全页没有任何含 background 的键，`agents` 组只有 `agents.overrides`），记为未确认；并发上限只见于 CLI Release Notes 的 1.1.31（2026-08-26）“Added a concurrency limit for subagents, configurable via the `QODER_CLI_MAX_CONCURRENT_SUBAGENTS` environment variable”，该条没有给出默认并发数。

本次只处理 `agent-background` 一个字段，能力字段总数维持 115。五行的核对日期都更新为 2026-10-18，五列的结论与证据都发生实质变化，其中 Kimi 列属结论方向改正。
