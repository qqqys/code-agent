# 扩展系统 · MCP 异步任务：新增能力字段，Claude Code 的 MCP tasks 公测与四家「只有同步超时」的边界

日期：2026-11-08
能力字段：`extension-mcp-tasks`（扩展系统 · MCP 异步任务，本次新增，能力字段总数由 115 增至 116）

## 本次改动

本次从 Claude Code v2.1.319（2026-11-06T17:04:01Z 发布）更新日志里的三条 MCP tasks 条目出发，发现「MCP Server 把一次 `tools/call` 变成服务端长任务、客户端在后台轮询取回结果」这一类能力在本矩阵里从未记录过：全仓库对 `MCP task`、`mcp_task`、`MCP 任务` 与 `denyInsteadOfPrompting` 的命中数都是 0，`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` 与 `CLAUDE_AUTO_BACKGROUND_TASKS` 也一次都没出现。它与既有的「MCP 客户端」（传输、作用域、认证）和「工具延迟声明与按需发现」（工具声明的加载时机）都不同义，因此按 `docs/00-阅读说明.md` 的「同名能力拆到足够细」原则新开一个字段，并把五家一次核完。

**Claude Code 是目前唯一有一手资料记录 MCP tasks 的一家**（官方 MCP 页 2026-11-08 以 `.md` 形式复核，157,241 字节；环境变量页 188,724 字节；更新日志固定到 main `0ed94698aa0aeee471465fc9c867c2e8434c4d68`，1,176,779 字节）：

- 官方把它定位成 Server 自己跑的长作业，逐字为 “An MCP task is a long job, such as a report export or a build, that an MCP server runs itself using the MCP tasks extension. Claude's tool call returns once the server accepts the job, so Claude keeps working unless you make Claude wait. When the job ends, the transcript says so and Claude gets the result. Ask Claude for it.”，并标为公测：“MCP tasks are in public beta in the Claude Code CLI and require Claude Code v2.1.304 or later.”
- 协议面：Server 用 `resultType: "task"` 加 `taskId` 回答 `tools/call`；Claude Code 随即发一次 `tasks/get`，之后按 `pollIntervalMs` 重复，该值 “clamped to between 250 and 30000”、缺失或为 `null` 时用 2000 且每次响应都重读。`status` 只有 `working`／`input_required`／`completed`／`failed`／`cancelled` 五个取值：`completed` 把顶层 `result` 当普通 `tools/call` 结果交出（其中 `isError: true` 报失败）、`failed` 用顶层 `error.message`（缺则 `statusMessage`、再缺则 `Task failed`）、`cancelled` 用 `statusMessage`（缺则 `Task was cancelled by the server`）、其他值请求取消并报失败。`tasks/result`、`tasks/list` 与 `notifications/tasks` 官方明确 “Not used, so put the outcome in your `tasks/get` responses”。
- 结果投递方向容易被误读：**结果只给 Claude、不进 transcript**，transcript 只出现 `MCP task <server task id> (<server>/<tool>) completed.` 一行，官方直接写 “The result goes to Claude, not into the transcript, so ask Claude for it. If Claude is idle when the result arrives, Claude starts on it unprompted.”
- 用户面：底部状态栏显示 `1 MCP task` 一类计数，任务列在 `/tasks`，选中按 `x`（或让 Claude 停）会停止跟踪并发 `tasks/cancel`，但 “the server may still finish it”；Server 断开时必须先从 `/mcp` 重连，否则 “no cancel request goes out and Claude Code forgets the task and can't follow it again”；`Esc` 不停止后台任务；退出时不发 `tasks/cancel`。
- 任务索取输入走 `input_required` 的 `inputRequests`，经 `tasks/update` 的 `{ taskId, inputResponses }` 每个 key 只回答一次、单任务超过 16 个 key 被忽略；`elicitation/create` “is served only in interactive terminal sessions, and `roots/list` everywhere”，无法受理时请求 Server 取消；非交互会话直接请求取消且 “without running your `Elicitation` hooks or calling the Agent SDK's `onElicitation` callback”；`/tasks` 打开期间 elicitation 对话框是隐藏的，要先关掉 `/tasks` 才能回答。
- 跨退出与恢复是这套机制里最容易踩的部分：远程 Server 上的任务在退出后继续运行，但 “No exit option cancels a remote server's task, even when the exit dialog lists it under `The following will stop when you exit:`”；stdio Server 的进程随 Claude Code 退出而停止，尽管 `/tasks` 仍显示 `runs on the server; survives exiting this session`。`/clear`、`/branch` 或 `/resume` 到别的会话时，只要进程还开着结果仍到达当前对话；退出后必须 `claude --resume` 当初启动任务的那个会话、且 “Keep the server's name and connection settings unchanged”；用一次性 `claude -p "<prompt>"` 加 `--resume`／`--continue` 恢复该会话不跟踪，新会话与 `--fork-session` 也不跟踪。
- 时限：后台任务默认 “has no Claude Code time limit”，墙钟上限（per-server `timeout` 或 `MCP_TOOL_TIMEOUT`，未设时约 28 小时、progress 通知不延长）与空闲超时（`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`，网络类默认 300000 毫秒、stdio 默认 1800000 毫秒）只在 Server 用 task 应答该调用之前适用；让 Claude 等待时它们覆盖整个任务，成功应答的状态检查算作空闲超时的活动。
- **与之相邻但不是同一件事的自动后台机制此前也完全没记录**：主会话任何 MCP 工具调用运行满两分钟就移成后台任务（v2.1.212 起，逐字为 “MCP tool calls running longer than 2 minutes now move to the background automatically so the session stays usable; configure the threshold or disable with `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`”），阈值键 `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` 默认 120000 毫秒、设 `0` 关闭自动后台并让 Claude 等待 MCP tasks。三类调用永不后台：Subagent 发起的（“Claude Code backgrounds only main-conversation calls”）、IDE Server 的、非交互模式的（除非 `CLAUDE_AUTO_BACKGROUND_TASKS=1`）；正在等 elicitation 对话框的调用推迟到对话框关闭。移成后台的普通调用 “doesn't survive exiting the session”，这一点与服务端 MCP task 正好相反。
- 等待开关的语义要分清：`CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND=1` 让 Claude 在工具调用内等任务结果，但自动后台还开着时两分钟后仍会把调用移走，而 “The moved call is a plain background call rather than an MCP task”；`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 与 bare mode “alone doesn't make Claude wait for MCP tasks”，且该变量下 “MCP tasks and the Monitor tool still run in the background”。
- 成为 MCP task 的前置条件里有两条落在别的字段上：Server 必须是 HTTP／stdio／claude.ai connector 且连在协议修订 2026-07-28 上（`MCP_SDK_GENERATION=v1` 或 `MCP_PROTOCOL_NEGOTIATION=legacy` 排除），而 2026-07-28 的默认协商是按连接类型分批打开的——直连 HTTP 在 v2.1.274、本地 stdio 在 v2.1.292（含 Bedrock/Vertex/Foundry）、claude.ai connector 在 v2.1.295、云会话与 Remote Control connector 在 v2.1.299；调用还必须来自主会话而非 Subagent。
- **两处一手资料冲突，均按未确认记录**：其一，官方 MCP 页与环境变量页都写 MCP tasks 与 `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND` 需 v2.1.304 及以上，但更新日志全文检索 `MCP task`／`MCP_TASK`／`MCP_AUTO_BACKGROUND`／`tasks/get` 只有四条命中——v2.1.319 三条与 v2.1.212 一条，`## 2.1.304` 一节没有任何相关条目。其二，v2.1.319 逐字写 “Changed MCP tasks to work in the terminal without feature-flag fetching (Bedrock, Vertex, Foundry, LLM gateways, `DISABLE_TELEMETRY`); set `CLAUDE_CODE_DISABLE_MCP_TASKS=1` to turn them off”，而官方 MCP 页的条件清单在核对日期仍写会话必须获取 feature flags。此外 `CLAUDE_CODE_DISABLE_MCP_TASKS`、`MCP_TIMEOUT`、`MCP_SDK_GENERATION`、`MCP_PROTOCOL_NEGOTIATION` 与同版新增的 `CLAUDE_CODE_DISABLE_FEATURE_FLAGS` 在环境变量页都没有独立条目，`MCP_TOOL_TIMEOUT` 只作为字符串出现在空闲超时行的说明里。
- Server 作者侧的失败行为也一并记下：请求没带 `params._meta["io.modelcontextprotocol/clientCapabilities"]` 下 `extensions` 里的 `"io.modelcontextprotocol/tasks": {}` 时用 task 应答会失败并给工具错误 `Unsupported result type 'task' for tools/call`（缺 `taskId` 或 `status` 无效同样报错）；`taskId` 超过 128 个不含空格的可打印 ASCII 字符报 `MCP server "<name>" returned a malformed task handle for tool "<tool>"`；`ttlMs` 过期不会让客户端丢弃任务；v2.1.317 之前省略 `createdAt`／`lastUpdatedAt`／`ttlMs` 或把 `pollIntervalMs` 设为 `null` 会失败；HTTP 与 claude.ai connector 上任务应答必须在 per-request 计时器内开始；JSON-RPC `-32602` 读作未知任务 ID，后台任务最多再问五分钟后报 `outcome unknown.`，此时第二次调用可能重复已完成的工作。

**Codex、Qwen Code、Kimi Code 与 Qoder CLI 的官方 MCP 资料在核对日期都没有 tasks 扩展**，四家都只用同步超时界定长调用，但键名、单位与默认值互不相同：

- Codex（官方 MCP 页 `learn.chatgpt.com/docs/extend/mcp`，560,111 字节）：`resultType`、`taskId`、`tasks/get`、`pollInterval`、`input_required` 与 `elicitation` 六个字符串命中数都是 0，`task`／`tasks` 只出现在 ChatGPT Work task、Scheduled tasks、Teams and Team Tasks 与 Tasks and memory 等导航或提示词语境。长调用只有两个 per-server 秒级键，逐字为 “startup_timeout_sec (optional): Timeout (seconds) for the server to start. Default: 10.” 与 “tool_timeout_sec (optional): Timeout (seconds) for the server to run a tool. Default: 60.”。顶层 `mcp_optional_startup_grace_ms`（默认 1000 毫秒、设 `0` 改为等各 Server 的 `startup_timeout_sec`、`required = true` 的 Server 仍用自身启动超时）只影响构建启动期工具目录，同段另写 “Tool calls still need a live connection.”。侧栏的 “Async tool calling”（`/api/docs/guides/async-tool-calling`）与 “Background mode”（`/api/docs/guides/background`）都属站点 API 段，按 Surface 规则不计入 Codex CLI，本次没有把它们的能力算到 CLI 上。
- Qwen Code（v0.27.0 标签提交 `03b0c2435be1890a21b117860eaf389076787275` 下的 `docs/users/features/mcp.md`，28,576 字节）：`resultType`、`taskId`、`tasks/get`、`pollInterval`、`async` 与 `poll` 命中数都是 0，`tasks` 只在 “- Automate workflows (repeatable tasks exposed as tools/prompts)” 出现一次。长调用只有 per-server `timeout`（“Request timeout in milliseconds (default: 600,000ms = 10 minutes)”）与 CLI `--timeout`，官方并写 “The existing `timeout` field is **tool-call** timeout (used for each `tools/call` request, default 10 minutes) and is unaffected by `discoveryTimeoutMs` — a long-running tool invocation is not a startup pathology.”
- Kimi Code（main `eb2035f3cad57cc12d4d5082ec626f7f0ea5f651` 下的 `docs/zh/customization/mcp.md`，12,941 字节）：`task`、`tasks`、`异步`、`后台`、`轮询`、`poll`、`resultType`、`taskId` 与 `progress` 命中数都是 0。只有 `startupTimeoutMs`（默认 `30000`）与 `toolTimeoutMs`（“单次工具调用超时”，**未给独立默认值**，因此未显式配置时的实际上限记为未确认），全局默认走 `[mcp] startup_timeout_ms`／`[mcp] tool_timeout_ms` 或 `KIMI_MCP_STARTUP_TIMEOUT_MS`／`KIMI_MCP_TOOL_TIMEOUT_MS`，优先级为 “server 字段 > 环境变量 > `config.toml` > 内置默认”。断线的指数退避重连（`reconnect_initial_delay_ms` 默认 5000、`reconnect_max_delay_ms` 默认 300000）是连接恢复，不是把进行中的调用移到后台。
- Qoder CLI（MCP Servers 页 836,033 字节、MCP reference 页 846,779 字节、更新日志 `changelog.qoder.com/cli` HTML 782,358 字节／去标签正文 67,996 字符，最新条目 CLI 1.1.84／November 6, 2026）：三处 `resultType`、`taskId`、`tasks/get` 与 `MCP task` 命中数都是 0，两个文档页的 `poll`、`async`、`background`、`progress` 与 `elicit` 也都是 0，`task`／`tasks` 只出现在站点导航。MCP Servers 页没有任何超时键；MCP reference 的 “Common Optional Fields” 表里与时长有关的只有 `timeout`（`number`，“Connection/request timeout (in milliseconds).”），**没给默认值也没拆出单独的工具调用超时键**。更新日志里唯一相关的一条在 CLI 1.1.3（July 22, 2026）段内、逐字为 “Added timeout control for MCP tools”，既没给键名与单位也没给默认值，因此它与 MCP reference 的 `timeout` 是否同一个键无法从一手资料确认，Qoder 这一格整体记为未确认。同页 “Lazy Loading Mode”（`mcp.lazyLoad`／`QODER_MCP_LAZY=1` 与 `mcp_list`／`mcp_get`／`mcp_call`）是按需加载工具声明、不是异步任务，已归在「工具延迟声明与按需发现」字段，本次不重复计。

**顺带补录两条容易被误当成异步任务的机制**，两者都写进了详情页的「跨产品事实」以免后续混淆：

- Qwen Code 的 Progressive availability 是「后台发现 Server」而不是「后台执行调用」：官方写 “Qwen Code discovers MCP servers in the background after the UI is already interactive.”，交互模式右下角状态胶囊显示 `N/M MCP servers ready`，非交互模式（`--prompt`、stream-json、ACP）仍等发现结束再发第一条提示词；`discoveryTimeoutMs` 只覆盖 `connect` + `tools/list` + `prompts/list` + `resources/list` 握手（stdio 默认 30 秒、远程 HTTP/SSE 默认 5 秒）；`QWEN_CODE_LEGACY_MCP_BLOCKING=1` 可回退旧同步行为，官方注明 “is kept as an escape hatch for at least one release”。
- Qwen Code 的 “Connection-loss replay” 是四家里唯一有明文条件的长调用补救：只有 server 写了 `trust: true`、工作区受信且工具显式声明 `idempotentHint: true` 或一致的只读注解时才重连并重放当前调用；注解缺失、注解冲突（只读注解与 `destructiveHint: true` 或 `idempotentHint: false` 冲突）、server 不受信或工作区不受信时不重放，并报告结果可能未知（Server 可能在响应丢失前已完成操作）、要求先核实再重试；官方注明这与早期版本对未注解工具透明重试的行为不同，且注解 “not permissions or an authorization boundary”。重放次数与间隔上限官方未给。

本次未处理但已看到的同期条目，留给后续单元：Claude v2.1.319 的 `permissions.denyInsteadOfPrompting`（会等权限提示的调用改为拒绝并让回合继续，覆盖终端会话、Subagent 与 teammates）、`/tasks` 新增 “Earlier in this session” 行列出已结束的 Subagent、自定节奏 `/loop` 改为回合结束未重排即终止（`CLAUDE_CODE_LOOP_KEEPALIVE=1` 保留旧行为）、`CLAUDE_CODE_DISABLE_FEATURE_FLAGS`，以及 auto mode 在关掉 telemetry／feature flags 或经 LLM gateway 时不再回退内置 classifier；Qwen Code v0.27.0 的 `experimental.unifiedAgentLoop`、GitHub channel 的 Repository Filter 与「一条提示词叠加超过五个 Skill 时告警」。
