# 项目目录信任：Claude Code v2.1.309 的 `claude ultrareview` 工作区信任门禁、Kimi Code 2.3.1 的信任读写脱离运行时初始化，并更正 Kimi 的「v2 实验引擎」旧记法与 Codex 的 `approval_policy = "untrusted"`

本次只处理 `security-trust`（项目目录信任）一个能力字段，能力字段总数维持 115。这一轮同时带来一处「矩阵尚未记录的新功能」（Claude v2.1.309 的 ultrareview 信任门禁与 `--trust-workspace`）、两处更正（Kimi 的引擎门禁记法已过期、Codex 的 `untrusted` 审批策略已退役）、一处结论升级（Kimi 由条件项改为官方确认）、一处新记录键（Qoder 的 `security.folderTrust.enabled` 默认 `true`）与一批把浅描述换成一手细节的深化（Qwen 的 Trusted Folders 专页与 `TrustGateError`、Claude 的信任键规则与「信任前会跑什么」表）。

主线是五家其实都有目录信任，但门禁的东西完全不同，而此前矩阵只写了「有」没写「门禁什么」。核对下来：Claude 门禁的是项目 `permissions.allow` 与 `additionalDirectories`（`deny`/`ask` 不受影响），Codex 门禁的是整个项目作用域 `.codex/` 层（项目本地配置、Hooks 与 Rules），Qwen 门禁的是项目 `.qwen/settings.json`、项目 `.env`、扩展管理、工具自动接受、自动记忆加载与项目级 Hooks，Kimi 门禁的是项目层配置与项目级 MCP（披露结构里还包括附加目录与 AGENTS.md/Skill/Agent profile 等指令来源），Qoder 门禁的是非默认权限模式（未信任直接回退 `default`）。总开关的默认值还正好相反：Qoder 的 `security.folderTrust.enabled` 默认 `true`，Qwen 的同名键默认 `false`，Claude、Codex 与 Kimi 根本没有这个开关。

最大的新增在 Claude Code。官方仓库 `CHANGELOG.md`（固定到提交 `65823ec0034ed0aa0266bc43903fefd3ff94a327`，2026-10-22T22:18:33Z，提交说明 “chore: Update CHANGELOG.md and feed.xml”）在 `## 2.1.309` 段下逐字写明 “Changed `claude ultrareview` to require workspace trust: it asks on a terminal, else refuses; scripts pass `--trust-workspace`, which takes no value (put a PR number or base branch before it), or set `CLAUDE_CODE_DISABLE_ULTRAREVIEW_TRUST_CHECK=1`”，对应 Release [v2.1.309](https://github.com/anthropics/claude-code/releases/tag/v2.1.309) 发布于 2026-10-22T22:18:57Z。与前一轮 `sandbox.allowNestedUserNamespaces` 的情况不同，这次官方三页在核对日期都已跟进：ultrareview 页新增了 “Trust the folder before the review runs” 一节与 `--trust-workspace` 旗标行（并写明 “Requires Claude Code v2.1.309 or later”、“Unlike `y`, the flag saves nothing.”），环境变量页新增了 `CLAUDE_CODE_DISABLE_ULTRAREVIEW_TRUST_CHECK` 行（写明要设在启动 Claude Code 的环境而不是 settings 的 `env` 块、“Runs that can ask still ask.”），错误参考新增了 `Workspace not trusted when running claude ultrareview` 一节，把四种失败形态与退出码都列了出来。只有一处没同步：CLI 参考页全文只有 `--bg`/`--background` 一行提到 trust，`claude ultrareview [target]` 行只列 `--json`、`--timeout`、`--post` 与 `--no-post`，没有 `--trust-workspace`。顺着这一层复核时把此前只有一句话的 Claude 列补齐了：官方 Permissions 页的 “Project allow rules and workspace trust” 与 “What runs before you trust a folder” 两节给出了信任键的三种算法（仓库内按 git 仓库根、worktree 用主检出的根、仓库外按启动目录并覆盖子目录、home 目录只按会话保留且“There is no setting to persist it.”）、`.claude/settings.local.json` 被 git 跟踪或 `.claude` 是符号链接时改按仓库提供处理、以及一张逐行说明「信任前什么照跑、什么不跑」的表。

第二处是更正，也是本轮最实质的一条。本仓库此前把 Kimi 列写成「条件：v2 引擎启动信任提示；项目 MCP 门禁」，详情里写「目录信任仅在 v2 引擎（`KIMI_CODE_EXPERIMENTAL_FLAG`）中生效；v1 引擎始终视为受信任」，来源固定在提交 `32d693f644de`（PR #2453，`feat(tui): ask for workspace trust on startup with the v2 engine`）。这条记法在 2026-08-05 之后就过期了：官方中文变更记录 0.33.0（2026-08-05）逐字为 “CLI 各界面（交互式 TUI、`kimi -p`、`kimi acp` 等）默认运行在 agent-core-v2 引擎上；设置 `KIMI_CODE_LEGACY_FLAG=1` 可回退旧引擎。”，而“启动时询问是否信任当前文件夹。”正是同一个 0.33.0 的条目；2.3.1 标签提交 `684bae9ea6a437f3bae98bba1dcb797a917d500b` 下的 `docs/zh/configuration/config-files.md` 也写 “本节由 `agent-core-v2` 引擎读取，Kimi Code 的所有界面都运行在该引擎上。”。也就是说信任提示与引入它的那个引擎在同一个版本转正，回退开关是 `KIMI_CODE_LEGACY_FLAG` 而不是 `KIMI_CODE_EXPERIMENTAL_FLAG`。同时更正来源：`docs/zh/guides/interaction.md` 在该标签下已没有任何信任内容，现行一手文档改为 `docs/zh/customization/mcp.md`（信任提示与无头行为）、`docs/zh/configuration/env-vars.md`（`KIMI_CODE_TRUST_WORKSPACE`）、`docs/zh/reference/server-api.md`（三个信任端点）与 `docs/zh/release-notes/changelog.md`（时间线）。Kimi 列因此由条件项改为官方确认。

第三处是 Kimi 2.3.1 的新修复，它顺带暴露了信任实现的真实形状。[PR #4348](https://github.com/MoonshotAI/kimi-code/pull/4348) `fix: decouple workspace trust from runtime initialization`（合并提交 `c569bab55d4d510b09f01205d760001d16117aff`，2026-10-23T04:52:22Z 合入 `release/2026-10-23`，随 [@moonshot-ai/kimi-code@2.3.1](https://github.com/MoonshotAI/kimi-code/releases/tag/%40moonshot-ai%2Fkimi-code%402.3.1)（2026-10-23T07:31:22Z）发布，变更日志条目为 “Fix workspace trust failures when Git Bash is unavailable on Windows.”）把 `GET /trust`、`POST /trust`、`POST /untrust` 三个接口从 `WorkspaceInstanceManager.getOrCreate`（会创建完整工作区运行时并等待 `HostEnvironment.ready`，其中包含 Git Bash 探测）改为 `WorkspaceService.get` → `WorkspaceTrustStore.forRoot` → `AtomicDocumentStore`。修复本身之外，PR 描述与源码给出三条此前没有的记录：存储异常不再被转换成 `trusted: false` 而是保留原始 message 与 request ID（PR 影响范围表同时写明“失败仍按未信任处理，不放开权限”）；初始化失败不再永久缓存已拒绝的 ready Promise、后续读写会重试，恢复时重新完成文件与插件 MCP 的完整初始化并发布配置差异，即使信任值没有变化也发一次状态恢复事件；信任记录以 `workspace-trust` 作用域存储、键为 `encodeWorkDirKey(canonicalWorkspaceRoot(root))`、值为 `{ root, trustedAt }`，读到记录即信任、没有独立的「未信任」记录、撤销即删除，旧键与旧 Windows 路径变体会被迁移。官方数据位置页的 `$KIMI_CODE_HOME` 目录树没有列出这个文件，因此确切磁盘路径记为未确认。

第四处是 Codex 的更正。本仓库此前在权限档里写「`approval_policy` 支持 `untrusted`、`on-request`、`never` 和 granular 分类策略」。官方 Agent approvals and security 页现在有专门一节 “Migrate from the retired `untrusted` approval policy”，逐字为 “Codex and ChatGPT Work no longer support `approval_policy = "untrusted"`. The retired setting can prevent either client from starting. Remove it from user or project configuration, profile files, startup scripts, and managed defaults.”；配置参考的 `approval_policy` 行类型只列 `on-request`、`never` 与 `{ granular = { … } }`，描述含 “`untrusted` is unsupported, and `on-failure` is deprecated”。严格的命令审批现在由目录信任派生：在用户级 `~/.codex/config.toml` 写 `[projects."/path/to/project"]` 加 `trust_level = "untrusted"`，此后 “Commands then require approval unless an execution-policy rule allows them. This also disables project-local configuration. Explicitly setting `on-request` overrides the project-derived policy; managed `allowed_approval_policies` must include `untrusted` to permit it.”。这条更正只写进 `security-trust` 一行的记录，权限档共享的 Codex 档仍留着旧写法，需要另起一轮按 `security-approval` 单独复核后再改，本轮没有动它。

第五处是 Qwen 与 Qoder 的补录。Qwen 一侧此前只引 approval-mode、sandbox、settings 与 headless 四页，官方其实有 `docs/users/configuration/trusted-folders.md` 专页；v0.26.0 标签提交 `ac97ce7a70d9b2ea5d62b357e3d9b0851423afc9` 下该页 5,587 字节，给出对话框三选项（**Trust folder**、**Trust parent folder**、**Don't trust**）、集中文件 `~/.qwen/trustedFolders.json`、失败关闭语义（含文件缺失时此前信任过的目录也重新按未信任开始）、一整套文件错误码（`500 trusted_folders_invalid`、`500 internal_error`、`409 trust_grant_ineffective`、v2 报 `200` 且 `configured.state: "error"`）、未信任 safe mode 的五条影响与 IDE 信号优先的判定顺序。源码侧补齐了三件官方文档没写的事：规则解析是「最深包含规则胜出、同深度未信任胜出、与写入顺序无关」，`TRUST_PARENT` 先解析成父目录再匹配；`QWEN_CODE_TRUSTED_FOLDERS_PATH` 可改文件路径；高权限模式门禁是硬门禁——`Config.setApprovalMode` 在未信任目录对既不是 `DEFAULT` 也不是 `PLAN` 的模式抛 `TrustGateError`（“Cannot enable privileged approval modes in an untrusted folder.”），daemon 的 `POST /session/:id/approval-mode` 把它翻成结构化 `errorKind: 'auth_env_error'`，这为此前那句「未信任目录会阻止 Auto-Edit、Auto、YOLO 等高权限路径」补上了源码级依据。Qoder 一侧补录了此前完全没记的 `security.folderTrust.enabled`（boolean、默认 `true`、Restart 为 Yes、描述 “Enable Folder Trust.”），以及 `permissions.trustDirectories`（string[]、默认 `[]`、“stored in user-level configuration and not overridden by project-level configuration”）与 `permissions.additionalDirectories` 的字段级取值；官方没有写 `security.folderTrust.enabled` 设为 `false` 时的行为，也没有描述 Release Notes 里 CLI 1.0.17 提到的 workspace dialog，两处都记为未确认。

## 修正

- `security-trust`（项目目录信任）矩阵五列结论改写：Claude 列由「Workspace Trust」扩为「Workspace Trust；未信任时项目 `allow` 与 `additionalDirectories` 不生效」；Codex 列由「Project Trust；未信任时跳过项目 `.codex/`」改为「`projects.<path>.trust_level`；未信任时跳过项目 `.codex/` 层」；Qwen 列由「`/trust`；功能默认关闭」改为「条件：`security.folderTrust.enabled` 默认关闭，开启后才有 `/trust`」；Kimi 列由「条件：v2 引擎启动信任提示；项目 MCP 门禁」改为「启动 `Trust this folder?` 弹窗；未信任时跳过项目层」；Qoder 列维持「Trust Directories；未信任时回退 `default`」。五列证据状态：Claude、Codex 与 Qoder 仍为官方确认，Qwen 仍为条件项，**Kimi 由条件项改为官方确认**（v2 引擎自 0.33.0 起已是默认引擎）。行 `description` 由「首次进入项目时确认是否信任仓库配置与指令。」改为「首次进入目录时确认是否信任仓库配置与指令，并据此门禁项目层加载与高权限模式。」
- 跨产品事实由 2 条增至 5 条：第 1 条改写为五家的门禁对象逐项对照；第 2 条新增总开关默认值相反（Qoder `true`、Qwen `false`、其余三家无开关）；第 3 条新增五家信任记录的保存位置；第 4 条新增高权限模式门禁的三家写明与两家不写明；第 5 条新增非交互入口的四种处理方式。
