日期：2026-11-28
能力字段：`execution-files`（执行与 Git · 文件读写）

## 本次改动

每日研究在核对五个产品 2026-11-26 之后的官方更新日志、Release 与仓库提交时，发现两条直接改变 `execution-files` 字段既有结论的一手材料，且都落在同一个子话题「写前读与过期写入保护」上：

- Qwen Code PR #17255（合并提交 `b5fdabf55e71fd3c861697cfbd6360cbbd7008f6`，2026-11-16T12:23:28Z，随 v0.28.0 发布）为 `edit` 增加「授权过期恢复」，并新增官方设计文档 `docs/design/2026-11-15-edit-stale-recovery.md`。此前记录的 “`edit` 以 `checkPriorRead` 强制读后再改并在写入前复核过期” 只说了一半：读后磁盘指纹漂移时 `edit` 不再一律拒绝，而是自动按当前文件内容恢复；`write_file` 仍一律拒绝。

### 恢复的语义与边界（官方设计文档 `docs/design/2026-11-15-edit-stale-recovery.md`）

标题 “Edit output and automatic stale recovery”，Goal 段逐字为 “Keep automatic recovery enabled by default without adding human confirmation. Normal Edit success results omit model-supplied text.”

授权与匹配：

> Recovery replaces the one exact literal occurrence of `old_string` in the **current file**, preserving content outside that replacement. It does not prove that this occurrence is the semantic location seen in an earlier Read. If an external rewrite moves the only matching text into another function, that current occurrence is the target.

> This is a deliberate tradeoff for default automatic recovery, including AUTO_EDIT/YOLO and noninteractive execution. A confirmation warning or a returned snippet communicates the event; neither is an authorization boundary or a proof of the old semantic location.

> An existing file still needs prior session text-read evidence. Recovery applies only to single, nonempty, non-no-op text replacements, with automatic read permission from the production default-read rules and permission manager.

> Recovery never uses fuzzy whitespace, quotation or Unicode matching. Missing and multiple matches, no-ops and unsupported cases return `FILE_CHANGED_SINCE_READ` without exposing unread contents through distinct content-derived errors.

即：**写前读强制本身没有被取消**，被放宽的只是「读后文件在磁盘上变了」这一种情况；且恢复不等于授权，也不保证改的是当初 Read 看到的那一处语义位置。

指纹、基线与快照：

> `readBaselineNeedsRefresh` means recovery preserved external bytes that have not been refreshed by a successful text Read.

> WriteFile rejects until a successful text Read refreshes the baseline.

> Partial or truncated text reads qualify under the existing prior-read contract; requiring a full Read would reintroduce the large-file deadlock from #3945 / #4002.

> Grep and RipGrep retain ordinary prior-read credit, but search snippets do not clear a pending recovery baseline; only an actual text Read does.

> The shell tool's simulated `sed -i` edit also waits for a successful text Read.

> A recovery decision captures a dev/inode/mtime/size snapshot. Post-read, confirmation and pre-write checks must match that snapshot. Passing `expectedStaleSnapshot` grants a matching recovery continuation even without `allowStaleRecovery`; callers must pass only an authorized captured snapshot.

> A concurrent Read making the cache fresh does not replace the frozen snapshot. A later file change or deletion is still rejected.

> The stat-to-write race and identical-mtime/size collisions remain limitations of fingerprint-based checks; this change introduces neither locks nor content hashes.

结果与诊断：

> User-modified and recovered results include an edited snippet when the existing line bound and an 8,000-character bound allow it; otherwise they ask for Read. Recovered results explain that WriteFile needs Read and subsequent Edit still uses recovery checks.

> One debug event is emitted after a successful recovered write, never merely during preparation.

文档末尾逐字为 “The regression tests specify current behavior; no model latency, token savings or production recovery-rate claim follows from deterministic replay results.”，即官方明确不为该改动主张任何延迟、token 节省或线上恢复率结论，本仓库同样不记。

### 源码侧判据（`packages/core/src/tools/edit.ts`、`priorReadEnforcement.ts`）

恢复门禁逐字为：

```ts
const canAttemptStaleRecovery =
  !replaceAll &&
  params.old_string !== '' &&
  params.old_string !== params.new_string &&
  !(this.confirmationCompleted && !this.confirmedStaleSnapshot) &&
  (await this.canAutoReadFileForStaleRecovery(params.file_path));
```

整块包在 `if (!this.config.getFileReadCacheDisabled()) { … }` 之内，随后以 `allowStaleRecovery: canAttemptStaleRecovery` 调用 `checkPriorRead(cache, path, 'editing', …)`。四条不恢复的情况对应 `replace_all`、空 `old_string`（即新建文件）、no-op（`old_string === new_string`）与缺少自动读权限。

`canAutoReadFileForStaleRecovery` 在四种情况下返回 `false`：`getFileSystemService().textFileIo` 存在（托管 Runtime 自带文件 IO）、`getFileService().shouldQwenIgnoreFile(filePath)` 命中忽略规则、`getFileReadDefaultPermission(config, filePath)` 不等于 `'allow'`、以及权限规则求值后 `finalPermission !== 'allow'` 或 `pmForcedAsk` 为真；取不到 PermissionManager 时返回 `true`。忽略文件名由同标签 `packages/core/src/utils/qwenIgnoreParser.ts` 给出：`const QWEN_IGNORE_FILE_NAME = '.qwenignore';`，另有 `DEFAULT_QWEN_CUSTOM_IGNORE_FILE_NAMES = ['.agentignore', '.aiignore']`，且 `.qwenignore` 恒被包含、不能作为自定义项重复登记（源码逐字 “'.qwenignore is always included'”）。

`checkPriorRead` 的 doc comment 给出了此前没有记录过的放行判据：

> Approval requires more than `cache.check === 'fresh'`: the recorded read must also have been (a) stamped with `lastReadAt` and (b) `lastReadCacheable` (i.e. plain text, not binary / image / audio / video / PDF / notebook — those return a structured payload the Edit / WriteFile tools cannot mutate as text).

> `lastReadCacheable` is purely about content type, not completeness. A truncated or partial text read still records `lastReadCacheable: true` because the bytes the model saw were text.

> Whether the model has seen *every* byte is recorded on `lastReadWasFull` for the Read fast-path; we do NOT consult it for enforcement, because the truncate-tool-output limit makes "fully read" an impossible precondition on files larger than the limit (issue #3945).

> Aligning with Claude Code's `readFileState`: any prior read clears enforcement for both Edit and WriteFile; the mtime/size drift check distinguishes current from older evidence. WriteFile rejects drift; Edit can request the explicit stale recovery exception and must enforce its additional authorization, matching and frozen-snapshot checks.

> Issue #2499 (model hallucinates unread bytes on overwrite) is the residual risk this stance accepts, mitigated by the drift check. There is no built-in stricter mode — `fileReadCacheDisabled: true` is an OPT-OUT (it bypasses enforcement entirely so application-level locking can take over), not an opt-in to anything stricter.

stat 策略逐字为 “`ENOENT` means the path disappeared between the caller's `fileExists` check and now — a disappearance race that is harmless for our purposes”、“Any other stat error (`EACCES`, `EBUSY`, NFS hiccup, …) is fail-closed”。新建文件段逐字为 “when a tool *creates* a file via Edit (`old_string === ''`) or WriteFile (new path), the FileReadCache `recordWrite` call seeds `lastReadAt` / `lastReadCacheable` on the brand-new entry, so a subsequent edit on that same file passes here without an intervening explicit Read.”，而 “A stale-recovered Edit is different: recordWrite must retain readBaselineNeedsRefresh, so further Edits use recovery guards and WriteFile requires an actual text Read even when the fingerprint is fresh.”

结果侧同版瘦身：普通成功编辑只回简洁确认、不复述模型自己给的文本；用户改过的替换与恢复出来的编辑在既有行数上限与 8,000 字符上限都放得下时附带 “Showing lines <start>-<end> of <total> from the edited file:” 片段（源码为 `snippetResult.content.length <= 8_000`），放不下时要求改用 Read。

### Managed 会话整体不适用

`packages/core/src/config/config.ts` 构造函数逐字为：

```ts
// A Managed session reads in its Runtime worker, so this process could
// neither elide a repeated read nor prove the read an edit requires.
this.fileReadCacheDisabled =
  params.sessionExecutionEngine === 'managed' ||
  (params.fileReadCacheDisabled ?? false);
```

即 `sessionExecutionEngine` 为 `managed` 时读缓存被强制关闭，写前读强制与过期恢复一起失效。`fileReadCacheDisabled` 自身默认 `false`，且它只是 `ConfigParameters` 的可选字段、不是设置项——同标签下 `packages/cli/src/config/settingsSchema.ts`（253,968 字节）对 `fileReadCache` 与 `readCache` 的命中数均为 0，因此终端用户没有可写的开关，只有嵌入式调用方能传。这是一条 Surface 边界：托管执行下 `edit`/`write_file` 的写前读保护不存在。

## 4. Claude Code：写前读坐标前移，结论未变

工具参考 `https://code.claude.com/docs/en/tools-reference.md`（2026-11-28 以 `.md` 形式核对 99,807 字节，比 2026-11-01 复核时的 87,860 字节增加 11,947 字节）“Edit tool behavior” 一节四段引文逐字未变：

- 前置拒绝：“These checks must pass for an edit to apply. Before any of them, a path matched by a `Read` deny rule is refused, including creating a new file there.”
- **Read-before-edit**：“Claude reads the file in the current conversation before editing it, and a read cut short with a `PARTIAL view` notice doesn't count. Claude Opus 4.6, Claude Haiku 4.5, and older models always require the read. Newer models can edit an unread file when reading it wouldn't need a permission prompt and the Read tool is available.”
- 磁盘漂移例外：“A file that changed on disk after Claude last read it can still be edited when `old_string` matches the current content exactly and unambiguously and Claude Code can read the file without prompting. … In any other case, such as a stale `old_string` or one that matches more than once without `replace_all`, Claude reads the file again before editing.”
- Bash 抵充：“Claude can also edit a file without a separate Read after viewing it with a Bash command such as `cat` or `grep`. Those commands are `cat`, `nl`, `bat`, `batcat`, `head`, `tail`, `sed -n 'X,Yp'`, `grep`, `egrep`, `fgrep`, and `rg`, each run on one file with no pipes or redirects.”

`Write` 一节另逐字为 “Newer models can overwrite a file they never read this session under the same conditions as read-before-edit: reading it wouldn't need a permission prompt and the Read tool is available.”。新增的 11,947 字节来自权限 Hook 上限、Perforce 只读保护（`CLAUDE_CODE_PERFORCE_MODE=1`）与非 UTF-8 文件等其他小节。

main 更新日志（1,423,161 字节）到 v2.1.332（2026-11-25T01:32:14Z 发布）为止没有改动读后再改要求、25,000 token 默认或 256 KB 整文件拒绝的条目。`## 2.1.332` 段里与文件读取相关的三条都是缺陷修复而不是规则变更：命名管道无写入方时 Read／`@` 提及／压缩挂起改为 20 秒后失败；`@` 提及的带扩展名文本文件即使前 2,000 行也超读取上限时不再被静默丢弃、改为告知大小与读法；Linux 上 Claude 通过符号链接读过文件后 Bash 编辑 diff 把未改动的符号链接显示为已编辑。

Claude 与 Qwen 的差别因此可以写清楚：两家的漂移例外都要求「精确唯一匹配 + 读取免权限提示」，但 Claude 的例外由官方文档描述、按模型分档，Qwen 的例外有独立设计文档与显式源码门禁、且不按模型分档而按权限与运行环境分档。
