# 交互审批：Claude Code 沙箱自动放行默认关闭（`sandbox.autoAllowBashIfSandboxed`），并把「沙箱是否让命令免审批」补成五家对照

日期：2026-11-16
能力字段：`security-approval`（权限与沙箱 · 交互审批）

## 本次改动

官方来源快照里 Claude Code 的最新 Release 是 v2.1.325（2026-11-13T20:40:01Z），更新日志该段有两条与审批直接相关的 Changed：“Changed sandboxed Bash commands to follow the normal permission flow by default; set `sandbox.autoAllowBashIfSandboxed: true` to keep running them without prompts” 与 “Changed managed settings that turn the sandbox on: to keep commands running without prompts, set `sandbox.autoAllowBashIfSandboxed: true` in your highest-ranking managed source”。核对官方 Sandboxing 页与 Settings reference 后确认这是一次默认行为翻转：沙箱有 auto-allow 与 regular permissions 两种审批模式，由 `sandbox.autoAllowBashIfSandboxed` 一个布尔键切换，默认值已由 `true` 改为 `false`。

本仓库此前完全没有记录这一层：全文（`site/`、`docs/`、`updates/`）对 `autoAllowBashIfSandboxed` 的命中数为 0，`security-approval` 的 Claude 记录只写到 “`/sandbox` 单独配置 Bash 沙箱”，`security-filesystem` 只记了 `sandbox.failIfUnavailable`、`sandbox.allowUnsandboxedCommands`、`enableWeakerNestedSandbox` 与 `allowNestedUserNamespaces`。因此本次把「沙箱内命令是否免审批」正式并入 `security-approval`：该页 `includes` 增加一条「沙箱是否让命令免审批（不含沙箱边界强度）」，与既有的 `excludes`「OS 沙箱强度」保持分工——沙箱边界强度仍留在 `security-filesystem`，本页只记它对应否询问的影响。

同一字段的另外四家按官方来源重新核对，顺带改正两处过期记法：

1. **Codex**：`security-approval` 等七页共用的 Codex「规则能力」原文写 “`approval_policy` 支持 `untrusted`、`on-request`、`never` 和 granular 分类策略”，与官方现行文档冲突。Configuration reference 的 `approval_policy` 类型只列 `on-request`、`never` 与 `{ granular = { sandbox_approval, rules, mcp_elicitations, request_permissions, skill_approval } }`，描述逐字为 “`untrusted` is unsupported, and `on-failure` is deprecated; use `on-request` for interactive runs or `never` for non-interactive runs.”。该退役事实此前只落在 `security-trust`（2026-10-23 记录、2026-10-29 复核），共用 profile 的六个页面与 `security-filesystem` 的 Codex override 都还是旧写法，本次统一改正。
2. **Kimi Code**：`security-approval` 的 Kimi「条件与边界」原文写 “`dangerous_command_guard` 关掉全部三条 guard 的语义只在 main 分支（提交 `6e7cc909da90`，PR #4250，2026-10-16），最新 Release `@moonshot-ai/kimi-code@2.2.0`（2026-10-14）里该键只关危险命令一项”。该坐标已过期一个月：用 compare API 夹逼，2.3.0（2026-10-21）与最新的 2.6.2（2026-11-13）都包含该提交，2.6.2 的中文配置文档里该段逐字未变，本次改正为「自 2.3.0 起随 Release 发布」。

**一手证据**（Claude Code 文档为 code.claude.com 的 `.md` 孪生体、更新日志固定到 `CHANGELOG.md` 提交 `715ff104ba2f38c7158fbb7dd831f5cc3f21e5c9`；Codex 文档为 learn.chatgpt.com 的 `.md` 孪生体；Qwen Code 固定到 v0.27.4 标签提交 `f35dde84157f992bc324c0a3f59b1119344a683d`；Kimi Code 更新日志固定到 `f082f04a093a3e71a2263c5461d52507dc31f83a` 与 `8d939f7dc76adde3d68a1d489eea3e8ea57e2b9a`、配置文档固定到 2.6.2 标签提交 `6a8493df3e1d796a63f7c7ca0de76c1e690cd943`；Qoder CLI 为 docs.qoder.com 的 `.md` 孪生体）：

- **Claude Code 的两种沙箱审批模式有官方专节**。Sandboxing 页（`.md` 110,894 字节，全页 `auto-allow` 命中 12 处）页首逐字为 “Sandboxed commands still go through the regular permission flow unless you choose auto-allow mode, which can run them without asking you.”，“### Sandbox modes” 一节逐字为 “Claude Code offers two sandbox modes. In both, the sandbox enforces the same filesystem and network restrictions; the difference is only in whether sandboxed commands are auto-approved or require explicit permission.”，即两种模式的文件系统与网络边界完全相同、差别只在是否自动批准；auto-allow 的定义是 “Claude Code approves a command automatically, with no prompt, when the command runs inside the sandbox. A command goes through the regular permission flow when it runs outside the sandbox because it matches `excludedCommands` or because Claude retries it unsandboxed.”，regular permissions mode 是 “All Bash commands go through the regular permission flow, even when sandboxed. This provides more control but requires more approvals.”。
- **auto-allow 不是无条件放行，官方列了五类例外与三类命令形状**。五类逐字为：命中 `Bash` deny 规则的形状 “is still blocked”；被识别为指向 critical path 的 `rm`/`rmdir` “still go through the regular permission flow”；`Bash(git push *)` 这类 content-scoped ask 规则 “still force a prompt even for sandboxed commands”；裸 `Bash` 或 `Bash(*)` ask 规则 “is skipped for commands that run sandboxed; it still applies to commands that run outside the sandbox. In plan mode, the rule isn't skipped: it prompts for sandboxed commands too, including read-only ones”；Monitor 工具命令 “aren't approved automatically, though they still run in the sandbox”，要免询问得写 `Bash(npm run *)` 一类 allow 规则。三类命令形状是 “commands such as `FOO=bar npm test`, where a variable set in front of a command can change which program runs, and with `make CC=clang` or `eval "ls"`”，它们仍走常规权限流程但仍在沙箱内运行，官方给的免询问规则是 `Bash(make *)`、`Bash(FOO=bar npm *)`（“When the command starts with a variable assignment, include the assignment in the rule”）与 `Bash(eval "ls")`（“A wildcard rule such as `Bash(eval *)` doesn't stop this prompt, so write a rule that matches the whole command”）。另有 “An allow rule that matches a command also approves an unsandboxed retry of it, so the command can run outside the sandbox with no prompt.”。
- **auto-allow 与权限模式相互独立，但有三条例外，且与 auto mode 不是一回事**。Note 逐字为 “Auto-allow mode works independently of your permission mode setting, with three exceptions: plan mode, an auto mode command that carries per-command allowed domains, and server-side classifier review of sandboxed commands in auto mode. Even if you're not in "accept edits" mode, sandboxed Bash commands run automatically when auto-allow is enabled. This means Bash commands that modify files within the sandbox boundaries execute without prompting, even in Manual mode, where the file edit tools would prompt.”，并补 “In plan mode, auto-allow doesn't widen approvals”。“How sandboxing relates to permissions and permission modes” 一节的三行表把 `/sandbox`、Auto mode、`--dangerously-skip-permissions` 的 “What it controls”／“What replaces the prompt” 分别写为 “What a Bash command can access once it runs”／“The sandbox boundary itself, in auto-allow mode”、“Whether each tool call runs”／“A classifier that reviews actions”、“Whether each tool call runs”／“Nothing.”，正文强调 “The sandbox's auto-allow mode is separate from auto mode: auto-allow approves Bash commands because the sandbox boundary contains them, while auto mode uses a classifier to review actions. The two work independently and can be combined”。同节还写权限规则 “are evaluated before any tool runs”、沙箱 “applies to Bash, PowerShell, and Monitor tool commands and their child processes”、“The operating system enforces the sandbox boundary on the running process, so it holds regardless of what the model chose to run”。
- **键的取值、作用域与默认值全部有官方条目**。Settings reference（`.md` 457,744 字节）的 `sandbox.autoAllowBashIfSandboxed` 段：Scope 为 `Any file`、类型 Boolean，描述逐字为 “Let Claude Code run sandboxed Bash commands without a permission prompt. Commands that can't run in the sandbox still go through the regular permission flow. `deny` rules and content-scoped `ask` rules such as `Bash(git push *)` still apply, but a bare `Bash` ask rule is skipped for sandboxed commands. To set it to `true` in managed settings, add it to the `sandbox` block of your highest-ranked managed source.”；`true` 侧写 “except in the cases that Auto-allow mode describes; `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` turns auto-allow off”，`false` 侧写 “sandboxed commands go through the regular permission flow, so your allow rules and permission mode decide. The `/sandbox` **Mode** tab calls this regular permissions mode”；默认值逐字为 “**Default**: `false`. Before v2.1.324, the default was `true`”。同页 `sandbox` 对象索引表把该键与 `enabled`、`failIfUnavailable`、`excludedCommands`、`allowUnsandboxedCommands` 等并列，索引描述为 “Run sandboxed commands without a permission prompt”。
- **默认值翻转的版本坐标有三处不一致，需要并读**。设置参考写 “Before v2.1.324”，更新日志把两条 Changed 列在 `## 2.1.325` 段，而 `CHANGELOG.md` 没有 `## 2.1.324` 段（版本段由 `## 2.1.325` 直接跳到 `## 2.1.323`）；GitHub 的 tag 与 Release 列表也没有 v2.1.324（tag 依次为 v2.1.325、v2.1.323、v2.1.322、v2.1.321、v2.1.319）。npm 官方包 `@anthropic-ai/claude-code` 的 `time` 表补上了缺口：`2.1.323` 发布于 2026-11-12T20:29:28.626Z、`2.1.324` 发布于 2026-11-13T18:42:36.300Z、`2.1.325` 发布于 2026-11-13T20:07:25.823Z，`dist-tags` 的 `latest` 与 `next` 都是 `2.1.325`。因此 2.1.324 是一个只发到 npm、没有 GitHub tag／Release、也没有更新日志段落的版本。固定用的 `CHANGELOG.md` 提交 `715ff104ba2f38c7158fbb7dd831f5cc3f21e5c9`（2026-11-13T20:39:41Z，“chore: Update CHANGELOG.md and feed.xml”）与 main 上同一文件的 SHA-256 一致（`162c169ef6210093e02b77453a2e44cae2561c40c5350c02688100a08c08cd83`，1,255,016 字节）。
- **`/sandbox` 面板是这层的交互入口，保存位置与被覆盖时的报错都有逐字文案**。面板 “opens the sandbox panel with three tabs, plus a Dependencies tab on Linux when the optional seccomp filter is missing”，三个页签为 **Mode**（“choose how sandboxed commands are approved”）、**Overrides**（对应 `allowUnsandboxedCommands`）与 **Config**（“view the resolved sandbox settings”）；选模式一步为 “On the Mode tab, select auto-allow or regular permissions.”；保存位置为 “Claude Code saves it to your project's local settings at `.claude/settings.local.json` … Claude Code adds that file to your global gitignore when it saves a setting there.”；只改一次会话用 `--settings`（官方示例 `claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'`）。更高优先级设置（managed settings 或 `--settings`）设了 `sandbox.enabled`、`sandbox.autoAllowBashIfSandboxed` 或 `sandbox.allowUnsandboxedCommands` 任一项时，`/sandbox` 不开面板而报 “Error: Sandbox settings are overridden by a higher-priority configuration and cannot be changed locally.”，并让用户用 `/status` 的 `Setting sources` 行区分 `Command line arguments` 与 `Enterprise managed settings`；写不进文件时报 “✗ Sandbox settings not changed: /home/you/project/.claude/settings.local.json couldn't be updated (EACCES). …”。改用户设置里的 `sandbox.enabled` 时 “The change takes effect in your running session at the next shell command Claude runs, and the **Mode** tab of `/sandbox` then marks the mode in effect.”，且官方明确只开 `enabled` “turns on regular permissions mode. For auto-allow mode, also set `sandbox.autoAllowBashIfSandboxed` to `true`.”。
- **企业侧的两个边界**：沙箱被 managed settings 变成 admin-required（`allowUnsandboxedCommands: false` 或 `allowManagedDomainsOnly: true`）后，仓库 `.claude/settings.json` 与 `.claude/settings.local.json` 里大多数放宽项被忽略，但 “In a repository's files: deny entries and the `autoAllowBashIfSandboxed` value.
