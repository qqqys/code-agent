# 跨会话消息：Qoder CLI 官方 Cross-Session Messaging（`QODER_FEATURE_CROSS_SESSION`、`/peers`、入站策略与批准框）

Qoder CLI 官方文档站在 CLI → Using Qoder CLI → Parallel Collaboration 分组下有一个独立的 Cross-Session Messaging 页（`https://docs.qoder.com/cli/cross-session-messaging`），记录同机同用户账号下两个 Qoder CLI 会话互相发现并交换消息的能力：开关是 `QODER_FEATURE_CROSS_SESSION=1`（beta，默认不开启，可写进用户级 `.env`），发现与投递用 `ListAgents` 与 `SendMessage`，保留消息用 `/peers` 加 `approve`/`deny <id>` 裁决，入站策略是 `security.crossSessionInbound` 的 `accept`/`hold`/`refuse` 加一条权限模式回退，批准框期限是 `general.dialogExpiry`（默认 `5m`）。CLI Release Notes 给出时间线：CLI 1.1.19（2026-08-11）“Added cross-session messaging, so sessions can discover each other and send messages”、CLI 1.1.21（2026-08-13）“Cross-session messages now show the sender and the message body inline”、CLI 1.1.25（2026-08-18）“Added @-mention of other live sessions in the composer”。矩阵 `session-messaging`（跨会话消息）字段 Qoder 列此前只记了 Agent Teams 的队内 `SendMessage`（单会话内、需 `QODER_AGENT_TEAMS=1`），完全没有记这条同机会话之间的能力，属于矩阵漏记而非产品新增；本次按官方页面补录，并把两个共用 `SendMessage` 工具名但作用范围不同的机制分开写清楚。其余四家本次复核无同类变化：Claude Code v2.1.292–v2.1.294 更新日志只有 `SendMessage` 相关的修复条目（提示词不再建议用已被 host、权限规则或 `--tools` 移除的 `SendMessage`、长会话收件方重名不再并成一个），没有新增跨会话消息能力；Codex 官方仓库 `CHANGELOG.md` 在核对日期只有 Unreleased 段；Kimi Code 中文 Slash 命令表仍未列出任何会话间消息命令；Qwen Code 的 `agents.crossSessionMessaging` 入站门禁保持 v0.22.2 时点的记录。

## 修正

- `session-messaging`（跨会话消息）矩阵 Qoder CLI 列由“条件：`QODER_AGENT_TEAMS=1` Agent Teams `SendMessage`（beta，单会话内）”改为“条件：`QODER_FEATURE_CROSS_SESSION=1` 同机会话互发消息（beta，仅 macOS 与 Linux，CLI 1.1.19 起）· `ListAgents`/`SendMessage` · `/peers` 与 `/peers approve|deny <id>` · `@` 对等会话提及（CLI 1.1.25 起）· `security.crossSessionInbound` · `general.dialogExpiry`；条件：`QODER_AGENT_TEAMS=1` Agent Teams `SendMessage`（beta，单会话内）”。证据状态仍为“条件项”（beta 开关加平台限制）。其余四家矩阵结论不变。
- Qoder CLI 详情（入口与切换）补录：`QODER_FEATURE_CROSS_SESSION=1 qoder` 启动或写进用户级 `.env`（默认 `$HOME/.qoder/.env`，改后需重启）；`ListAgents` 输出分 `Agents in this session (address by name)` 与 `Peer sessions (other Qoder sessions on this machine)` 两组，对等会话行形如 `api-service — interactive, idle, started 12m ago, cwd /home/dev/api, handle -3f`；`@` 加至少一个字符补全对等会话，行以 `@` 开头、类型标 `session` 并附状态与运行时长（示例 `@reviewer    session · idle · started 3m ago`），接受补全插入寻址标签且含空格的标签像文件路径一样转义；`/peers` 列出生效入站策略及其来源、可达对等会话（含本会话自己被寻址的 handle）与待审查消息，`/peers approve ab12cd34` 与 `/peers deny ab12cd34` 为官方示例。
- Qoder CLI 详情（保存位置）补录：每个会话监听一个私有 socket 并登记进每用户注册表，其他会话读注册表发现对等会话后直连投递，socket 与其所在目录只对本人用户账号可读；官方页面没有给出注册表与 socket 的具体路径，路径记为未确认。附件按绝对路径随消息发送、到达时复制给接收方、消息被拒绝时再删除。被保留的消息不进入模型上下文，只能在 `/peers` 看到 id、发送方、被保留原因与预览。
- Qoder CLI 详情（具体行为）补录：消息投递进接收会话的下一回合，CLI 1.1.21 起内联显示发送方与正文；发送如实回报，对等会话在列出与发送之间退出时结果说明情况并建议重新列出而不是静默成功；`accept`/`hold`/`refuse` 的逐字含义；未设置时按本会话处理权限的方式回退（绕过权限检查的会话保留、仍会逐次确认的会话接受、拿到显式 socket 路径的非交互运行把本该保留的改为拒绝并立即告知发送方，显式配置的值即使在那里也总被尊重）；项目级设置只能更严（仓库可把 `accept` 收紧为 `hold`，绝不能把 `hold` 放宽为 `accept`），因此 `/peers` 总是写明生效取值与来源文件；批准框内容（发送方名称与 handle、“name and address are supplied by the sender and are not verified”、绕过权限检查的说明、被截短的摘录、按数量列出的附件、`Deliver it to this session` 与 `Decline — drop it and tell the sender` 两个选项）；该提示永远最后上屏、不打断权限确认或进行中的对话框、一次只问一条且只在屏幕空闲时问，提示或对话框打开期间到达的消息仍保留并改由 `/peers` 审查，被抢占屏幕的提示回到队列而不是在替代物后面耗到过期；`general.dialogExpiry` 到期后丢弃并回报 expired 而不是 refused，`never` 去掉其他对话框期限但不去掉这一个；用户自己配置的 `hold` 不弹框而仓库设置的 `hold` 会弹框；对等消息不算用户对待处理权限提示的批准、开头的 `/` 是纯文本而非 Slash 命令、权限边界按会话各自计算因而被拒动作改问另一会话时接收方 Agent 被指示拒绝并上报。
- Qoder CLI 详情（状态范围）补录：官方页面逐字写明 “two Qoder CLI sessions running on the same machine, under the same user account”；同机上其他用户的会话看不到也够不到；隔离只依赖文件权限，发送方自述名称没有密码学验证，任何已以你的身份运行的进程都能冒充任意对等会话，官方建议在以更高权限运行的会话上优先用 `hold`；官方页面没有描述跨机器传输。
- Qoder CLI 详情（自动行为）补录：Agent 可自行调用 `ListAgents`；会话名即当前标题，`/rename` 与 Agent 自行改标题都会改变它；状态列取 `busy`/`waiting`/`shell`/`idle`；无标题会话按工作目录名加 handle 命名（同在 `/home/dev/api` 显示为 `api-7c` 与 `api-3f`），handle 由监听的 socket 派生、在所有会话的列表里相同、不随改名变化、可单独寻址，有标题的会话行内另标一个；名称歧义时 Agent 拿到各自唯一寻址的标签并询问而不猜测；提及本身不发送，只提及不提要求的消息不投递，单独 `@` 不列出对等会话，匹配不到任何对象的提及原样留在文本里。
- Qoder CLI 详情（保存与保留）补录：官方页面没有记录独立的磁盘消息队列或保留时长；`general.dialogExpiry` 取 `60s`/`5m`/`10m`/`never`、默认 `5m`、只从用户自己的设置读取而永不从仓库读取；`security.crossSessionInbound` 默认未设置且仓库内设置只能收紧；`QODER_FEATURE_CROSS_SESSION=1` 可写进用户级 `.env` 跨会话保留、改后需重启；附件到达即复制、被拒即删。
- Qoder CLI 详情（适用界面）补录：CLI，页面位于文档站 Parallel Collaboration 分组下（与 Process Tasks in Parallel、Agent Teams、Dynamic workflows 并列）；非交互运行只有在拿到显式 socket 路径时才涉及该功能且其回退把本该保留的消息改为拒绝；官方 Slash 命令参考、设置参考与 Tools 参考在核对日期都没有列出 `/peers`、`SendMessage`、`ListAgents`、`security.crossSessionInbound`、`general.dialogExpiry` 或 `QODER_FEATURE_CROSS_SESSION`，`SendMessage` 只出现在 Agent Teams 页；不从 IDE、JetBrains Plugin、Cloud Agents、Mobile & Web、QoderWake 或 Agent SDK Surface 推断同一能力。
- Qoder CLI 详情（条件与边界）补录：beta、默认不开启、需 `QODER_FEATURE_CROSS_SESSION=1`；官方页面写明需要 UNIX domain socket 且仅 macOS 与 Linux 可用，Windows 不在范围内；官方页面没有给出生效的最低 CLI 版本、只标 Beta；CLI Release Notes 时间线为 1.1.19（2026-08-11）、1.1.21（2026-08-13）、1.1.25（2026-08-18），公开 Release Notes 最新条目为 CLI 1.1.64（2026-09-25）且其中没有 `/peers`、`security.crossSessionInbound`、`general.dialogExpiry` 或 `QODER_FEATURE_CROSS_SESSION` 的条目；本页不把 Agent Teams 的队内 `SendMessage` 算作跨会话消息。

## 证据版本

- Qoder CLI 官方文档 [Cross-Session Messaging](https://docs.qoder.com/cli/cross-session-messaging)（2026-10-08 抓取）逐字要点：Beta 段 “Cross-session messaging is a beta feature and is not enabled by default. Set the feature flag before starting Qoder CLI: `QODER_FEATURE_CROSS_SESSION=1 qoder`. The flag can also be stored as `QODER_FEATURE_CROSS_SESSION=1` in the user-level configuration `.env` file so later sessions enable it automatically. Default user-level configuration path: `$HOME/.qoder/.env`. Restart Qoder CLI after changing `.env`. The feature requires Unix domain sockets and is available on macOS and Linux only.”；How it works 段 “When the feature is on, each session listens on a private socket and records it in a per-user registry. Other sessions read that registry to discover peers, and connect directly to deliver a message.” 与 “Both the socket and its directory are readable only by your own user account. Sessions belonging to other users on the same machine cannot see or reach yours.”；Discovering peers 段 “A session's name is its current title, so it changes when you run `/rename` and when the Agent retitles the conversation.”、“`busy` while its Agent is working, `waiting` while it is asking for a confirmation, `shell` while its user is at a shell prompt, and `idle` otherwise”、“A session that has no title is named after its working directory, plus its **handle**”、“A handle is derived from the socket the session listens on, so it is the same in every session's listing, and it does not change when the session is retitled”、“Run `/peers` to see the same list along with the handle this session is reachable at.”；Mentioning a peer in the prompt 段 “Type `@` followed by at least one character to complete on peer sessions along with files and agents.”、“Mentioning a session tells the Agent which one you mean; it does not send anything.”、“A message that only mentions a session does not message it.”、“Typing `@` on its own does not list peer sessions, and a mention that matches nothing is left in the text as written.”；Sending a message 段 “The Agent uses the same `SendMessage` tool it uses for teammates, with a peer name as the recipient. Files can be attached by absolute path and are copied to the recipient so it can read them.”、“If the peer exited between the listing and the send, the result says so and suggests listing again rather than silently succeeding.”；Controlling what arrives 段 `accept`/`hold`/`refuse` 三条定义、“In a session with nobody to review anything — a non-interactive run that was given an explicit socket path — a message this fallback would have held is refused instead”、“Project-level settings may only make this stricter. A value in a repository's checked-in settings can tighten `accept` to `hold`, but never loosen `hold` to `accept`.”、“`/peers` always names the setting in effect and the file it came from.”；Approving a held message 段批准框原文（含 “From worker -7c (name and address are supplied by the sender and are not verified)”、“Deliver it to this session”、“Decline — drop it and tell the sender”）、“The prompt is the last thing this session will put on screen”、“Only one approval is asked at a time, and only while the screen is otherwise free.”、“How long the prompt waits is set by `general.dialogExpiry`, which defaults to five minutes. When it lapses the message is dropped and the sender is told it expired rather than that you refused it”、“`never` removes the deadline for other dialogs but not for this one”、“A message held because you configured `hold` yourself is parked without a prompt… A `hold` that came from a settings file in the repository does prompt.”；Reviewing held messages 段 “The first line always states the inbound policy in effect and where it came from”、“`/peers approve ab12cd34`”、“`/peers deny ab12cd34`”；What a peer message can and cannot do 段三条；Security notes 段 “Isolation rests on file permissions… the sender's self-reported name is not cryptographically verified, so any process already running as you could present itself as any peer… prefer `hold` on sessions that run with elevated permissions.”；Settings reference 段 “`security.crossSessionInbound` — `accept`, `hold`, or `refuse`.”、“`general.dialogExpiry` — `60s`, `5m`, `10m`, or `never`. … Defaults to `5m`. Read from your own settings only, never from a repository.”。
