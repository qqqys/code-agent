# 服务端与 Daemon：Qwen Code v0.26.0 发布 `qwen daemon start|status|logs|stop|restart`，Claude Code 的后台会话 supervisor 与 `claude daemon` 四行命令补录，「只有 Codex 有 CLI 自管本地后台服务」的旧结论作废

Qwen Code 在 2026-10-21T23:20:53Z 发布 [v0.26.0](https://github.com/QwenLM/qwen-code/releases/tag/v0.26.0)（标签提交 `ac97ce7a70d9b2ea5d62b357e3d9b0851423afc9`），Release 的 Features 清单里有五个 `feat(serve)` 条目共同补齐了本地 daemon 的启动、发现与控制闭环：#14739 “add local daemon discovery and control commands”（合入提交 `35e0b4960def3af880862f18eab636908830dd26`，2026-10-20T00:50:38Z）、#14869 “add qwen daemon start”（`f4f3749f3661712d28d72a05e1a9436594e457b9`，2026-10-20T11:05:34Z）、#14902 “add daemon status detail”（`171f8a6d4d11961e3c61e65e9a5e0d21339737d4`，2026-10-20T13:32:46Z）、#14914 “add daemon start --wait”（`69b3149654315d15eb60639a4069beec9d1b75c8`，2026-10-20T15:23:31Z）与 #14929 “add daemon restart”（`a8616497861fd779a0a90d3d2986b5327211f03d`，2026-10-21T05:00:39Z）。该标签下的 `docs/users/qwen-serve.md`（218,629 字节）新增 “Inspect and control a local daemon” 一节，逐字给出七行示例：`qwen daemon start --port 4170      # detached; waits for the discovery record`、`qwen daemon status                 # ports, PIDs, workspaces, and health`、`qwen daemon status --json          # one JSON object per daemon`、`qwen daemon status --detail        # version, uptime, sessions, and issues`、`qwen daemon logs --port 4170 -f    # follow the recorded log file`、`qwen daemon stop --port 4170       # SIGTERM the recorded process` 与 `qwen daemon restart --port 4170    # stop, then start with the recorded settings`；官方文档站的同名页标题就是 “Daemon mode (`qwen serve`)”，内容与仓库文档一致，同站另有 “Daemon Mode (Developer Deep Dive)” 21 页开发者专章。命令源码 `packages/cli/src/commands/daemon.ts`（54,330 字节）的根命令是 `command: 'daemon'`、`describe: 'Inspect and control local qwen serve daemons'`，五个子命令的 describe 逐字为 start “Start a local qwen serve daemon in the background”、status “List local qwen serve daemons and their health”、logs “Show or follow a local daemon log file”、stop “Stop a local qwen serve daemon” 与 restart “Restart a local qwen serve daemon on its recorded port and workspaces”。

发现记录的位置与权限由文档逐字固定：“Records live under the runtime directory ($QWEN_RUNTIME_DIR, $QWEN_HOME, or ~/.qwen) in daemon/daemon-<port>.json. They are 0600 on POSIX and never contain the bearer token.”；源码里目录 mode 是 `0o700`、启动日志 fd 是 `0o600`，用临时文件加改名原子发布，记录内容含绑定 URL、PID、已注册的规范工作区、日志路径、认证类型、`startedAt` 与写入方的 `pidNamespace`。健康状态只有 `running`、`stale` 与 `unreachable` 三种：`probeHealth()` 把 `/health` 的任何 HTTP 响应（含 `--require-auth` 下的 401）都当作存活证据，`/health` 有响应但 PID 可寻址且进程已不在时是 `stale`，`/health` 抛错而 PID 不可寻址或仍存活时是 `unreachable`；崩溃遗留的记录由 `status --prune` 或 `stop` 清理。`start` 以 detached 子进程（`detached: true`、`windowsHide: true`，子进程 stdio 指向一个日志 fd）启动 `qwen serve`，等它发布发现记录后打印绑定 URL、PID、日志路径与停止命令，再 `unref()` 回到 shell；匹配记录用 `record.pid === child.pid` 而不是按端口，因此支持 `--port 0`；子进程一律带 `--no-token-qr` 启动以免 token 进入启动日志，显式 token 走环境变量而不是子进程参数，启动会话的标识与私有能力绑定会从子进程环境里移除。启动日志名为 `start-<pid>-<时间戳>.log`，成功后删除、失败或超时保留并打印末 40 行，超过 24 小时（`START_LOG_MAX_AGE_MS = 24 * 60 * 60_000`）清扫；logger 没有文件 sink 时记录里省略日志路径、读侧回落到运行时目录的 `debug/daemon/daemon.log`。`--wait` 要等到运行时无 `daemon_runtime_starting` issue 且不为 `error` 才返回，超时保留启动日志并以非零退出。`stop` 只在监听器应答 `/health` 或记录的 PID 仍存活时才发 SIGTERM，`--force` 在优雅超时（`STOP_TIMEOUT_MS = 10_000`、`STOP_POLL_MS = 100`）后加 SIGKILL，多 daemon 时必须传 `--port`，`--all` 停全部。`restart` 先经 `daemon stop` 再经 `daemon start --wait`，沿用记录的端口、hostname、启动工作区、Web Shell 模式与 `--require-auth`，`--web`/`--no-web` 与 `--require-auth`/`--no-require-auth` 可覆盖记录，`--force` 只在显式传时转发给 `stop`。防 PID 复用做得比较细：POSIX 用 `ps -o lstart=` 读进程启动时间并要求落在记录两侧窗口内（`PROCESS_START_TOLERANCE_MS = 5_000`、`PROCESS_START_LEAD_MS = 10 * 60_000`）且命令行是 `serve` 进程，Windows 用 PowerShell 读 `Get-Process.StartTime`；删记录校验 `expectedPid`，重启中的 daemon 不会删掉并发实例的记录；记录携带的 `pidNamespace` 让跨容器的 PID 被当作不可寻址，既不发信号也不当存活证据，`status --detail` 也因此绝不会把 `QWEN_SERVER_TOKEN` 发给自己寻址不到的进程。Windows 下 `stop` 是硬杀：未带 `--force` 直接拒绝并报 “qwen daemon: Windows stop is a hard kill; pass --force to confirm (shutdown handlers do not run).”，带 `--force` 时由 `terminateTree()` 调 `%SystemRoot%\System32\taskkill.exe` 以 `/pid <pid> /T /F` 结束进程树、成功文案是 `hard-killed` 而不是 `stopped`。同一工作区重复 `start` 且未传 `--port` 时报 “qwen daemon: a daemon is already running for ${primary} on port ${existing.record.port}; pass --port to start another.”。设计文档 `docs/design/2026-10-20-daemon-start.md`（4,453 字节）的 Status 一节逐字为 “Implemented in this change. `qwen daemon start` is local process management; it does not change the serve protocol, authentication, or workspace isolation.”，PR #14869 的说明则写 “Starting a local daemon previously required systemd, tmux, or `nohup`.” 与 “There is no supervision or crash restart.”、“No service installation or restart command is included.”，并把 Windows 与 Linux 未在本地跑过、`logs --follow` 只做了代码审查、自签名 TLS 证书的 daemon 可能显示为 `unreachable` 三项列为已知范围。

顺着「谁有 CLI 自己管理的本地常驻服务」这一层核对其余四家，发现本仓库此前的一条跨产品结论已经站不住。旧记录写「只有 Codex 记录到由 CLI 自己发现、附加并管理版本的本地后台服务器……其余四家的常驻服务都由用户显式启动」，而 Claude Code 官方 [CLI 参考](https://code.claude.com/docs/en/cli-reference)（48,250 字节）的 `claude` 子命令表里其实有四行 daemon 命令，逐字为 “`claude daemon logs` | Follow the background-session supervisor's log file, `~/.claude/daemon.log`, printing new lines as they arrive until you press `Ctrl+C`”、“`claude daemon run` | Run the background-session supervisor in the foreground of this terminal, printing its log”、“`claude daemon status` | Print the background-session supervisor's state, version, socket directory, and worker count for diagnostics. Exits 1 if the supervisor isn't running” 与 “`claude daemon stop --any` | Stop the background-session supervisor and the sessions it hosts. Pass `--keep-workers` to leave background sessions running for the next supervisor to reconnect to. `--any` confirms stopping an on-demand supervisor, which is the default. Use this to recover from an unresponsive supervisor”。[Agent view 页](https://code.claude.com/docs/en/agent-view)（143,172 字节）的 “The supervisor process” 一节把启动方式写死为按需自动：“The supervisor is a background service that runs your background sessions so they keep working after you close agent view or your terminal. Claude Code starts it the first time you background a session or open agent view, and you don't need to manage it yourself.”；“Where state is stored” 表给出四个路径——`~/.claude/daemon.log`（Supervisor log）、`~/.claude/daemon/roster.json`（“List of running background sessions, used to reconnect after a restart”）、`~/.claude/jobs/<id>/state.json`（官方要求走 `claude agents --json` 而不是直接解析该文件）与 `~/.claude/jobs/<id>/tmp/`（每会话临时目录，Claude 在此的 `Write` 与 `Edit` 不提示权限，删会话时一并移除）；排障段两次要求删 `~/.claude/daemon.lock`，并写 “Claude Code started with `daemon` is a supervisor, so run `kill -9 <pid>`.”。版本联动也有官方文案：supervisor 自动更新后 “restarts itself onto the new version and moves idle sessions over in the background”，`claude daemon status` “also warns when the running supervisor is on a different version than the `claude` you invoked”，告警给出两个版本并让你跑 `claude daemon stop --any` 换新版本，`claude respawn --all` 则把所有会话迁到更新后的二进制。另外三条边界同样取自该页：supervisor 与其会话用同一批已存凭据、后台会话的凭据来自 supervisor 因而 `Could not resolve authentication method` 要回到启动 supervisor 的那个 shell 处理；supervisor 自身被外部结束时 “on macOS and Linux, your sessions stop unless a new supervisor connects within about a minute. To start one, run `claude agents` in your shell.”；设 `CLAUDE_CONFIG_DIR` 时 supervisor 改用该目录并成为带自己会话的独立实例。引入版本无法确定：官方两页都没有标注最低版本，官方仓库 `CHANGELOG.md`（固定到提交 `5ed799e5cc56bea9efff57398ca43e31d82784ff`）全文含 daemon 字样的只有 `## 2.1.300` 段下两条、且都是修复（“Fixed `claude daemon stop --any` printing \"stopped\" while a stuck background service kept running: it now waits, force-kills the service, and says so with exit 1 if it is still there” 与 “Fixed `claude daemon stop` exiting with no output, and leaving sessions listed as running, when telemetry is turned off”），没有任何 “Added `claude daemon`” 一类引入条目，因此本仓库把引入版本记为未确认。同一页还顺手否掉了一个旧假设：`claude mcp` 下只有 `login <name>` 与 `logout <name>`，官方 CLI 参考里没有 `claude mcp serve`。

Codex、Kimi 与 Qoder 三家的既有结论复核后不变，但各补了一条边界。Codex 一侧 `codex-rs/app-server-daemon/README.md` 与 `src/settings.rs`（都固定到 main 提交 `40db507eeca2ff778c040c325449eb72e90c0590`，2026-10-22T19:54:04Z）的八个子命令、`CODEX_HOME/app-server-daemon/` 四个状态文件、Windows 108 字节 AF_UNIX 限制与内嵌服务器回退都与既有记录一致；不过发现一处官方材料自相矛盾——`settings.rs` 的常量是 `DEFAULT_UPDATE_INTERVAL_MINUTES: u32 = 60`、`DEFAULT_SHUTDOWN_GRACE_SECONDS: u32 = 60` 与 `MAX_SHUTDOWN_GRACE_SECONDS: u32 = 5 * 60`，README 正文也写 “Eligible managed daemons check for updates after five minutes, then hourly by default.”，但同一份 README 的示例 JSON 把 `updateIntervalMinutes` 写成 `120`；本仓库按源码记默认 60，并把这处冲突写进来源标签以免后续被示例误导。Releases 页最新十项全部是 pre-release（最新 rust-v0.164.0-alpha.12，2026-10-22T11:11:51Z），页内没有 stable 标签。Kimi 一侧按 main 提交 `759958afdfeb0f8c7d09cb03cbc2cf85b6255e9e` 复核 `docs/zh/reference/kimi-command.md`（20,041 字节）：顶层子命令只有 `login`、`acp`、`web`、`doctor`、`export`、`migrate`、`upgrade`（别名 `update`）、`provider`、`app`、`install-desktop`（隐藏别名 `install-app`）与 `vis`，`kimi web` 下只有 `rotate-token`，没有任何 daemon 生命周期子命令；`kimi web` 仍逐字为 “在当前终端前台运行本地 Kimi 服务……命令会一直挂在终端，直到收到 `SIGINT` / `SIGTERM`（如 `Ctrl-C`）时干净退出。”，`kimi server` 命令树整体废弃、除 `kill` 外一律打印弃用提示并以退出码 1 结束。Qoder 一侧官方命令行参考的子命令表共 14 行，与常驻服务有关的只有 “`remote-control` | Start the remote-control daemon.”，`status` 是 “Display session status.” 而不是 daemon 状态，表里没有 daemon 的 stop、restart、logs 或 update；CLI Release Notes 最新条目已推进到 1.1.77（October 22, 2026），1.1.72 至 1.1.77 六版都没有 daemon、remote-control 或后台服务条目。本次只处理 `surface-service` 一个能力字段，能力字段总数维持 115。
