# 只读或计划模式：Kimi Code 2.4.0 把 Plan 模式收归用户开启并让每份计划都等审阅（删除 `EnterPlanMode`、"Never Ask" 不再自动批准计划退出、`kimi -p` 跳过 `default_plan_mode`），并据此补齐五家「谁能开启 Plan、计划是否总要人工评审」的口径

本次只处理 `security-plan`（只读或计划模式）一个能力字段，能力字段总数维持 115。这一轮带来一处旧结论作废（Kimi 列此前写「Agent 先产出计划并等待确认；退出 Plan 通常仍需确认」，而权限档共享的 Kimi 记录写「Auto 会自动处理全部审批」，2.4.0 之后 Plan 是 "Never Ask" 的唯一例外）、一处官方文档已同步的确认（PR #4247 同一提交改了 12 个中英文文档文件，因此本轮不存在文档滞后）、四处此前只有一句话的浅描述被换成源码级口径（Claude 的 `EnterPlanMode`/`ExitPlanMode` 与规划期 shell 命令三种情况、Codex 的 Plan 协作模式模板与 “Implement this plan?” 确认框、Qwen 的 `enter_plan_mode`/`exit_plan_mode` 与每轮注入提醒、Qoder 的 `general.plan.enabled` 与 Plan 确认不属于权限裁决），以及一条矩阵此前完全没有记录的比较轴——**模型自己能不能开启 Plan 模式**：Claude、Qwen、Qoder 三家都有进入工具，Codex 没有，Kimi 自 2.4.0 起也没有。

主线是「Plan 由谁开启、计划由谁批准」这两件事。五家此前都只记到模式名与一两句行为，没有记到入口归属与审批强度；而这一天正好有 Kimi 2.4.0 发布，把其中一家从「模型可进入 + Auto 自动批准退出」改成「只有用户能进入 + 任何模式都要人工审阅」，其余四家的一手材料也能把同一条轴补齐。

## Claude Code：模型可以自己进 Plan，退出要确认，但 bypass 可用的交互式会话不强制阻断

官方[工具参考页](https://code.claude.com/docs/en/tools-reference)（2026-10-28 以 `.md` 形式抓取，87,846 字节）的两行逐字为 “| `EnterPlanMode` | Switches to plan mode to design an approach before coding | No |” 与 “| `ExitPlanMode` | Presents a plan for approval and exits plan mode | Yes |”，第三列表头是 “Permission required”、页首 Note 说明它表示 “whether the tool prompts in Manual mode for paths inside the working directory”，因此 Claude 自己切入 Plan 模式不弹确认、提交计划要经确认；规则格式一节另写 “Tools not listed here, such as `ExitPlanMode` or `ShareOnboardingGuide`, accept only the bare tool name with no specifier.”。

[Permission Modes 页](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)（117,065 字节）的 “Analyze before you edit with plan mode” 一节给出规划期 shell 命令的三种情况，并写明 “the first of these cases that matches applies”：bypass permissions 可用的交互式终端会话 “neither the classifier nor a prompt applies to planning commands”；auto 可用且 `useAutoModeDuringPlan` 开启（“which it is by default”）时由 classifier 审查除 critical-path 删除以外的命令；两者都不成立时内置只读集之外的命令逐个询问（沙箱 auto-allow 开着也一样）。进入方式为 `Shift+Tab`、“prefixing a single prompt with `/plan`” 或 `claude --permission-mode plan`，再按 `Shift+Tab` 可在不批准计划的情况下离开；审批选项为 **Yes, and use auto mode**（auto 不可用时读作 **Yes, auto-accept edits**、以 bypass 启动时读作 **Yes, and switch to BYPASS PERMISSIONS (no further prompts) for this session**）、**Yes, manually approve edits** 与 **No, keep planning**，批准即退出 Plan 并切到该选项描述的模式；`Ctrl+G` 在默认文本编辑器里打开拟议计划，`showClearContextOnPlanAccept` 开启时列表首项变为批准并清理规划上下文，接受计划还会按计划给会话生成标题。默认值写法是项目 `.claude/settings.json` 的 `defaultMode: "plan"`，VS Code 扩展发起的对话不读项目设置的起始权限模式、改在 VS Code 用户设置写 `claudeCode.initialPermissionMode`。

边界两句最关键：bypass 一节写 “In interactive terminal sessions with bypass permissions available, Claude Code also doesn't enforce plan mode's blocks. Claude is still instructed to plan without editing, but a file edit or shell command it attempts during planning runs without prompting.”，而 “Plan mode keeps its blocks wherever Claude Code runs without an interactive terminal, including non-interactive runs with `-p`, Agent SDK sessions, and conversations in the VS Code extension's chat panel.”；受保护路径 “are never auto-approved, except in `bypassPermissions` mode and in interactive terminal sessions in plan mode with bypass permissions available”，critical-path 删除则 “run with no prompt only in `bypassPermissions` mode itself, not in plan mode”。计划文件的保存路径官方未公开，记为未确认。核对日期最新 Release 仍是 v2.1.312（2026-10-27T20:24:20Z），main 的 `CHANGELOG.md` 为 1,104,632 字节、最新段落仍是 `## 2.1.312` 且没有 Plan 模式条目。

## Codex：Plan 是协作模式，模型没有进入或退出它的工具，批准后由 TUI 问 “Implement this plan?”

Plan 在 Codex 里是与 `Default` 并列的协作模式而不是沙箱或审批策略：[`config_types.rs`](https://github.com/openai/codex/blob/rust-v0.165.0/codex-rs/protocol/src/config_types.rs)（tag `rust-v0.165.0`，31,651 字节）的 `ModeKind` 只有 `Plan` 与带 `#[default]`（并接受 `code`、`pair_programming`、`execute`、`custom` 四个别名）的 `Default`，`TUI_VISIBLE_COLLABORATION_MODES` 只含这两个；[`collaboration_modes.rs`](https://github.com/openai/codex/blob/rust-v0.165.0/codex-rs/tui/src/collaboration_modes.rs)（3,598 字节，首行注释 “//! Missing discovery adds no presets.”）从服务端发现结果里过滤出可见预设，`next_mask()` 按列表顺序循环、`default_mask()` 优先取 `Default`。用户入口是 [`/plan`](https://learn.chatgpt.com/docs/cli/slash-commands#switch-to-plan-mode-with-plan)（官方命令表 “Switch to plan mode and optionally send a prompt.”，可带内联提示词、可粘贴内容或附图，“While Codex is already working, `/plan` is temporarily unavailable.”）。模型侧没有对应工具：该 tag 下 `codex-rs/core/src/tools/handlers` 共 57 个条目，名字含 plan 的只有实现 `update_plan` 的 [`plan.rs`](https://github.com/openai/codex/blob/rust-v0.165.0/codex-rs/core/src/tools/handlers/plan.rs)（3,334 字节）与 `plan_spec.rs`（1,740 字节），而 `plan.rs` 在 `turn.mode() == ModeKind::Plan` 时直接返回错误 “update_plan is a TODO/checklist tool and is not allowed in Plan mode”。

When unset, Plan mode uses its built-in preset default.”），没有默认进 Plan 或开关 Plan 的键；技术只读边界仍由 `read-only` 沙箱提供，官方审批页写 “If you want to chat or plan without making changes, switch to `read-only` mode with the `/permissions` command.”。`codex exec` 一类非交互运行下的 Plan 行为官方未公开，记为未确认。核对日期最新稳定 Release 是 rust-v0.165.0（2026-10-27T20:09:38Z），发布说明没有 Plan 模式条目，只有 “Prevented queued agent messages from restarting work after an interrupt or a switch to Plan mode. ## Qwen Code：进入是降权动作不弹确认，退出强制询问，YOLO 下模型自行进入被拒

官方[审批模式文档](https://github.com/QwenLM/qwen-code/blob/eeee1443a7e36ab22b2f1dcded8dec64b621a7ee/docs/users/features/approval-mode.md)（v0.26.3 标签提交 `eeee1443a7e36ab22b2f1dcded8dec64b621a7ee`，15,241 字节）把 Plan 记为文件编辑 “❌ Read-only analysis only”、Shell 命令 “❌ Not executed”、风险 Lowest，循环顺序 plan → default → auto-edit → auto → yolo，并逐字写 “Regular planning requests do not switch modes by themselves. If you want the read-only Plan Mode workflow, use `/plan`, the keyboard shortcut, or set the approval mode to `plan` explicitly.”；入口是 `Shift+Tab`（Windows 上 `Tab`，状态栏 `⏸ plan mode`）、`/plan`、`/plan <提示词>`、`/plan exit`（恢复进入前的审批模式）与 `/approval-mode` 选 `plan`，默认值写法是 `tools.approvalMode: "plan"`。

源码侧两个工具都在 [`packages/core/src/tools/`](https://github.com/QwenLM/qwen-code/blob/eeee1443a7e36ab22b2f1dcded8dec64b621a7ee/packages/core/src/tools/enterPlanMode.ts)：`enterPlanMode.ts`（9,040 字节）的 `enter_plan_mode` 描述以 “Use this tool only after the user explicitly asks to switch into plan mode or confirms they want plan mode. Entering plan mode is a privilege reduction, so it does not require user confirmation at execution time.” 开头，`getDefaultPermission()` 返回 `allow`，`userRequested` 参数用于区分用户要求与模型自行决定，YOLO 且未传该参数时不进入并回 “Stayed in YOLO mode (plan mode not entered).”（注释引用 #5970 并写该工具是 headless/ACP 会话进入 Plan 的唯一入口，因为 `/plan` 只在交互式可用、那里也没有 `Shift+Tab`），非交互且不是 ACP 时回 “Cannot enter plan mode in non-interactive mode without ACP support. The gate exit paths require user interaction.”，Subagent 中按 `subagent-plan-tool-policy` 被阻断，进入是幂等的以免覆盖已保存的 `prePlanMode`，并会 reveal 延迟声明的 `exit_plan_mode`。`exitPlanMode.ts`（15,813 字节）的 `exit_plan_mode` 必填 `plan`（“empty strings will be rejected”），`requiresUserInteraction()` 在 Plan 模式下返回真（注释逐字为 “Plan-mode gating lives in requiresUserInteraction() (forces 'ask' via permissionFlow) and execute() (returns guidance error outside plan mode).”，#7671），确认框 `title: 'Would you like to proceed?'` 且 `hideAlwaysAllow: true`；四个结果分别落到 `getPlanExecutionMode()` 或 `prePlanMode`（RestorePrevious，执行权限变了就抛 “Execution permission changed or was not confirmed. Request plan approval again with the current permission.”）、`auto-edit`（ProceedAlways）、`default`（ProceedOnce）与不批准（Cancel），失败文案含 “Plan execution was not approved. Remaining in plan mode.”、“Plan exit was cancelled. Remaining in plan mode.” 与 “Plan approval is stale because the approval mode changed. No action was taken.”；成功后 `savePlanBestEffort(plan)` 并以 `fromApprovedPlanExit: true` 切模式、回 “User approved. You can now start coding.”；团队场景的 plan-required teammate 改由 leader 裁决并回 “Leader approved.”，`PLAN_EXIT_APPROVED_LLM_CONTENT_PREFIXES = ['User approved.', 'Leader approved.']` 供调度器做执行后的历史清理（#6237）。

[`prompts.ts`](https://github.com/QwenLM/qwen-code/blob/eeee1443a7e36ab22b2f1dcded8dec64b621a7ee/packages/core/src/core/prompts.ts)（92,759 字节）给出每轮注入的约束：系统提示词写 “Do not enter plan mode or call enter_plan_mode on your own just because the task involves planning or complexity.”，`getPlanModeSystemReminder()` 写 “you MUST NOT make any edits, run tools classified as state-modifying (including changing configs or making commits), or otherwise make changes to the system. A shell command whose safety cannot be determined may run only after the user explicitly approves that exact invocation once, and only when it is necessary for the investigation.”，并写 “An exact one-off approval for an unknown shell command approves only that invocation. It does not approve the plan, authorize related commands, or exit Plan mode.” 与不得用包装、引号技巧、别名或混淆手段让被阻断的写操作看起来未知；`getManualPlanExitSystemReminder()` 在批准流程之外切换模式后注入一次性提醒。核对日期最新稳定版是 v0.26.3（2026-10-28T14:36:14Z），发布说明没有 Plan 模式或审批模式条目。

## Qoder CLI：Plan 是独立工作状态，两个 Plan 工具可整体关，进出 Plan 的确认不属于权限裁决

官方 [Permissions 页](https://docs.qoder.com/cli/permissions)（2026-10-28 以 `.md` 形式抓取 `https://docs.qoder.com/cli/permissions.md`，28,196 字节；`/en/cli/permissions` 返回 307 跳转）的启动参数示例逐字为 `qoder --permission-mode plan           # Legacy compat: translates to default + enters Plan work state`，取值表 `plan` 行为 “Read-only mode (legacy compat: maps to default + Plan work state)”；“Disable Plan mode” 一节给出 `{"general": {"plan": {"enabled": false}}}` 并写 “When set, the `/plan` command is unavailable, `--permission-mode plan` falls back to default, and EnterPlanMode/ExitPlanMode tools are not registered.”，即两个 Plan 工具默认注册、可整体关掉；auto 模式一节在讲完两阶段分类器与熔断后写 “The circuit breaker is the only condition under which a permission verdict produces an authorization prompt in `auto` mode.” 与 “Separately, tools that require user input (such as AskUserQuestion) and entering or leaving Plan always request confirmation, as does a session grown too long for the classifier to read its full context.
