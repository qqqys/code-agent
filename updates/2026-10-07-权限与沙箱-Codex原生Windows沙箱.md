# 文件系统隔离与网络隔离：Codex 原生 Windows 沙箱的三种实现与 `windows.allow_mxc` 退出开关

Codex 官方文档站有独立页面 [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)（副标题 “Configure and troubleshoot the native Codex sandbox on Windows”），逐字写明 “When you run Codex natively on Windows, agent mode uses a Windows sandbox to block filesystem writes outside the working folder and prevent network access without your explicit approval.”，并给出 `config.toml` 的 `[windows] sandbox = "elevated"` 或 `"unelevated"` 两种文档化模式。官方配置参考另把 `windows.sandbox` 的取值列为 `unelevated | elevated | mxc`，说明为 “Windows-only native sandbox mode when running Codex natively on Windows.”。本仓库此前在 `security-filesystem`（文件系统隔离）与 `security-network`（网络隔离）两个字段的 Codex 列只记沙箱策略（`read-only`/`workspace-write`/`danger-full-access`）与 `network_access`/`network_proxy`，完全没有记录 Windows 上的 OS 级沙箱实现，`docs/` 与 `site/` 全文也搜不到 `windows.sandbox`、`mxc` 或 “Windows 沙箱”。

本次按官方文档、官方配置参考、官方 Managed configuration 页与固定 SHA 的官方仓库源码／Release 补录该能力，并按仓库既有边界把它拆进两个字段：文件与路径边界写进 `security-filesystem`，网络边界写进 `security-network`。

MXC 是第三种实现。官方仓库 `codex-rs/mxc-sandbox/README.md`（固定到 main 分支提交 `e95abcdf4939`）写明该 crate “routes a command through the current Codex executable and directly into Microsoft's MXC `BaseContainerRunner`”，要求可用的 Windows 进程安全环境（PSEC），并且 “never invokes MXC's AppContainer dispatcher, edits host ACLs, creates sandbox users, runs setup, or requests elevation. The existing Codex Windows sandboxes remain separate backends.”。同文件给出选择与灰度规则：`windows.sandbox = "mxc"` 是严格选择；默认关闭的 `features.prefer_mxc` 在可用且未显式禁止本地绑定时为本地执行选中 MXC，否则沿用 legacy 配置与安装；远程 executor 保留自己配置的后端；命令失败从不触发后端回退；桌面端可在下次本机 Windows 启动时用 `-c features.prefer_mxc=true` 带上已保存的灰度决定；`config/read` 保留配置的后端而 `windowsSandbox/readiness` 反映本机生效选择。

2026-10-07 当天 main 分支合入 “Add a Windows MXC sandbox opt-out”（PR #51547，提交 `e95abcdf4939`），新增配置键 `windows.allow_mxc`：提交说明逐字为 “Setting it to `false` blocks automatic MXC selection even when `features.prefer_mxc` is enabled, and rejects explicit `windows.sandbox = "mxc"` configuration with a clear error. Omitting the setting preserves existing behavior.”，源码 doc comment 为 “False blocks both explicit MXC configuration and automatic selection.”。该键尚未发布：rust-v0.160.1（提交 `d27764b82f71`）的 `WindowsToml` 只有 `sandbox` 一个字段，官方配置参考与 Windows sandbox 页也都没有列出。

顺带核出两处一手资料冲突。其一，官方 Windows sandbox 页写 “By default, both sandbox modes also use a private desktop for stronger UI isolation. Set `windows.sandbox_private_desktop = false` only if you need the older `Winsta0\Default` behavior for compatibility.”，但固定到的 `WindowsToml` 标注 `#[schemars(deny_unknown_fields)]`、JSON schema 为 `additionalProperties: false` 且只有 `sandbox` 与 `allow_mxc` 两个键，因此该键的可用性记为未确认。其二，官方 Windows sandbox 页要求用 `/sandbox-add-read-dir C:\absolute\directory\path` 给沙箱授予读权限，但 CLI TUI 的 Slash 命令枚举在 rust-v0.154.0（提交 `6b9826e3aa83`）仍有该命令（描述 “let sandbox read a directory: /sandbox-add-read-dir <absolute_path>”）、自 rust-v0.155.0（提交 `f0a1b8f0849d`）起已无，官方 Slash 命令参考页也没有列出，CLI 侧入口记为未确认；本仓库 `docs/01-Slash命令矩阵.md` 的 Codex 命令目录此前一直列着它，本次据此移除。`/setup-default-sandbox`（源码描述 “set up elevated agent sandbox”）在 rust-v0.154.0、rust-v0.160.1 与 main 的枚举中都在，官方 Slash 命令参考页同样未列出。

其余四家本次复核后结论不变：Claude Code 最新 Release 仍为 v2.1.292（更新日志提交 `fbe20e00e285`），其 OS 沙箱文档仍只描述 macOS Seatbelt、Linux bubblewrap 与 WSL2，没有 Windows 原生沙箱实现；Qwen Code 最新发布为 v0.25.1-preview.0（2026-10-06），沙箱仍是可选 Seatbelt 或 Docker/Podman 容器且默认关闭；Kimi Code 官方仓库最新提交停在 2026-09-30，公开文档仍未确认命令子进程的 OS 沙箱；Qoder CLI 公开 Release Notes 最新条目为 CLI 1.1.63（2026-09-24），早于本仓库上次核对日期 2026-10-04，主 CLI 仍只有路径权限规则、Sandbox 只在 SDK 侧且默认关闭。
