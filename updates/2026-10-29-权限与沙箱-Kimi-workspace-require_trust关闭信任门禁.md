# 项目目录信任：Kimi Code 主干新增用户级 `[workspace] require_trust`（默认 `true`，设 `false` 时把所有工作区视为受信任并跳过启动信任提示；PR #4517 提交 `7d72ae396586`，compare 证实尚未进入任何 Release），并据此把「谁能关掉信任门禁、关掉后哪些照旧生效」补成一条比较轴

本次只处理 `security-trust`（项目目录信任）一个能力字段，能力字段总数维持 115。这一轮带来一处旧结论作废（Kimi 的 `defaults` 此前写「没有目录信任总开关，检查恒生效」，主干起有了一个用户级布尔开关）、一条此前不存在的比较轴（五家里只有 Qoder、Qwen 与主干上的 Kimi 有关闭门禁的键，Claude 与 Codex 仍只能逐目录信任或用 `--trust-workspace` 一类单次运行旗标）、以及四处复核坐标推进（Claude 的 Permissions 页与 v2.1.300–v2.1.312 更新日志、Codex 的配置参考与审批安全页、Qwen 的 v0.26.4 标签、Qoder 的 Release Notes 到 CLI 1.1.80）。

主线是「门禁能不能整体关掉、关掉之后什么变了什么没变」。Kimi 的这次改动同时动了文档、源码与 server API 三处，因此可以把它记到判定函数级别；另外四家在核对日期没有等价改动，只更新坐标并把「没有总开关」这句话钉在当天的一手页面上。

[`docs/zh/configuration/config-files.md`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/docs/zh/configuration/config-files.md)（该提交下 42,834 字节）顶层字段表新增一行 “| `workspace` | `table` | — | 工作区设置，包括信任机制 |”（原文把节名做成指向 `#workspace-trust` 的链接），并新增 `workspace trust` 一节：正文首句逐字为 “`workspace` 用于集中存放用户级 `config.toml` 中的工作区设置。其 `require_trust` 字段控制首次打开尚未受信任的工作区时是否要求信任确认；默认要求确认。”，字段表逐字为 “| `require_trust` | `boolean` | `true` | 首次打开未受信任的工作区时要求信任确认；`false` 将所有工作区视为受信任并跳过启动信任提示 |”，示例为 `[workspace]` 下一行 `require_trust = false`。

另外三份文档同批改写：[`env-vars.md`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/docs/zh/configuration/env-vars.md) 的 `KIMI_CODE_TRUST_WORKSPACE` 行追加 “该变量与 `[workspace] require_trust` 相互独立；后者为 `false` 时，假值不会重新启用信任机制”（原文把该键做成指向配置文件页 workspace trust 一节的链接；取值列仍是真值 `1`/`true`/`yes`/`on`、假值 `0`/`false`/`no`/`off`，全页仍只有这一个说明含 trust 的变量）；[`customization/mcp.md`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/docs/zh/customization/mcp.md) 的无头一段在 “将 `KIMI_CODE_TRUST_WORKSPACE` 设为 `1` 即可在该进程中信任当前工作区。” 之后追加 “如需全局关闭工作区信任机制并不经确认加载项目级 MCP server，可在 `config.toml` 中设置 `[workspace] require_trust = false`；仅应在所有工作区均已可信时使用该配置。”（原文同样把该键做成链接），即 CI 里多了一个不必逐进程设环境变量的入口；[`reference/server-api.md`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/docs/zh/reference/server-api.md) 的 `POST /api/v1/workspaces/{workspace_id}/untrust` 描述由 “撤销工作区信任，并卸载其项目级 MCP 配置。” 改为 “撤销工作区的持久化信任记录。如果进程或配置覆盖没有使工作区保持受信任，则同时卸载其项目级 MCP 配置。”，成功返回由 “成功时 `data` 为 `{ trusted: false }`。” 改为 “成功时 `data` 为 `{ trusted }`，表示撤销后的有效信任状态。通常为 `{ trusted: false }`；如果 `KIMI_CODE_TRUST_WORKSPACE` 或 `[workspace] require_trust = false` 生效，则仍为 `true`。”，错误码 `40410` 未变。

## Kimi Code：判定函数、三个消费点与配置层级

新增文件 [`configSection.ts`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/packages/agent-core-v2/src/workspace/workspaceTrust/configSection.ts)（802 字节）给出全部判定逻辑：`WORKSPACE_TRUST_SECTION = 'workspace'`、`WorkspaceTrustConfigSchema = z.object({ requireTrust: z.boolean().optional() })`、`DEFAULT_WORKSPACE_TRUST_CONFIG = { requireTrust: true }`，判定函数逐字为 `export function workspaceTrustRequired(config: IConfigService): boolean { return config.get<WorkspaceTrustConfig | undefined>(WORKSPACE_TRUST_SECTION)?.requireTrust ?? true; }`，并以 `registerConfigSection(..., { defaultValue: DEFAULT_WORKSPACE_TRUST_CONFIG })` 注册，因此缺省即门禁开启、schema 只接受 boolean。

[`workspaceTrustStore.ts`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/packages/agent-core-v2/src/workspace/workspaceTrust/workspaceTrustStore.ts)（5,965 字节）里 `WorkspaceTrustEntry` 新增私有 `trustGateEnabled()`（就是 `workspaceTrustRequired(this.config)`），同步判定改为 `isTrusted(): boolean { return !this.trustGateEnabled() || this.envTrusted || this.trusted; }`，而 `isPersistedTrusted(): boolean { return this.trusted; }` 未变；`get()` 与新增的 `refresh()` 都先 `await this.config.ready`、门禁关闭时直接 `return true`，因此连持久化读取都不再等待；`onConfigChange()` 在门禁关闭时立即 `fire({ trusted: this.trusted })`、开启时等 `ready` 后再 fire；`trust()`/`untrust()` 仍直接调 `mutate(true|false)` 且不检查门禁，`mutate()` 照常 `writeWorkspaceTrust`/`deleteWorkspaceTrust` 并 `track2('workspace_trust_changed', { trusted })`，这就是「已有信任记录会保留」的源码依据。`WorkspaceTrustStore` 也注入 `@IConfigService` 并订阅 `onDidSectionChange`，回调里 `if (event.domain !== WORKSPACE_TRUST_SECTION) return;` 之后逐 entry 调 `onConfigChange()`。

[`workspaceTrustService.ts`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/packages/agent-core-v2/src/workspace/workspaceTrust/workspaceTrustService.ts)（2,718 字节）的 `get()` 逐字为 `await this.config.ready; if (!workspaceTrustRequired(this.config)) return true; await this.ready; return this.inner.get();`，构造函数新增 `@IConfigService private readonly config`（`program.ts` 同步改为四参数装配），文件里没有解释该绕过分支的注释。三个消费点因此改口：`trustDisclosureService.describeGatedActivation()` 由「`await this.trust.ready` 后判 `isTrusted()`」改为 `if (await this.trust.get()) return EMPTY_ACTIVATION;`（门禁关闭时披露为空，启动弹窗没有可展示内容因而不出现），`mcpRegistryService` 改为 `const trusted = await this.trust.forRoot(cwd).refresh();`，`workspaceMcpConfigService` 改为 `const trusted = await this.trust.get();` 并据此设 `includeProject: trusted`；`packages/kap-server/src/routes/workspaces.ts` 的 untrust 路由 OpenAPI 描述改为 “Revoke persisted workspace trust (project-level MCP config unloads unless process or config overrides apply)”。

取值层级由 [`configService.ts`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/packages/agent-core-v2/src/app/config/configService.ts)（35,762 字节）确定：`seedInitialLoad()` 只 `readFileSync(this.bootstrap.configPath, 'utf8')` 读一份 TOML，`reload()` 走 `documentStore.get<ResolvedConfig>(CONFIG_SCOPE, this.configKey)`，文件里没有项目级或受管配置层；状态链为 `rawSnake` → `raw`（`transformTomlData(fileData, this.registry)`，即 TOML 的 `require_trust` 对应 schema 的 `requireTrust`）→ `validated`（缺失时补 section 的 `defaultValue`）→ `effective`（叠加 section env 绑定与 env overlay），`get(domain)` 先看 `ConfigTarget.Memory` 的 `memory`；`commit()` 只在深度比较不相等时 fire `onDidSectionChange`；配置文件另有 watch，去抖 `WATCH_DEBOUNCE_MS` 后 `void this.reload()`。[`overrides.md`](https://github.com/MoonshotAI/kimi-code/blob/7d72ae396586ad82f48ca4335956235d3c38f0d8/docs/zh/configuration/overrides.md)（6,800 字节）同口径写 “目前 CLI 只读取一份用户级配置文件，没有项目级配置文件机制。需要在不同项目间隔离配置时，用 `KIMI_CODE_HOME` 指向不同的数据目录”，优先级只列命令行选项与用户配置文件两级。这里留一处文档冲突：`config-files.md` 记录项目级 `<项目根目录>/.kimi-code/local.toml` 的 `[workspace]` 节（只文档化存量兼容字段 `additional_dir`），与 `overrides.md` 的「没有项目级配置文件机制」互相矛盾，因此项目级文件能否设 `require_trust`、以及受管或企业层能否下发该键，都记为未确认。
