# 自动委派：Kimi Code 2.3.2 把默认行为改成「不主动派发、要先被授权」并让 `AgentSwarm` 只由用户开启，五家的委派依据、授权来源与描述预算逐条补齐

本次只处理 `agent-auto`（自动委派）一个能力字段，能力字段总数维持 115。这一轮同时带来一处「矩阵尚未记录的新行为」（Kimi Code 2.3.2 的显式请求门禁与 `AgentSwarm` 的 swarm mode 硬门禁）、一处旧结论作废（Kimi 列此前写「依据 `description` · `whenToUse`」，把两个字段当成自动委派的判据，而 2.3.2 之后它们只参与授权之后的选型）、一处官方文档未同步的记录（Kimi 中文与英文 Agents 页在 2.3.3 标签下仍写「自动调度……无需用户手动指定」），以及把其余四家此前只有一句话的浅描述换成一手细节（Claude 的三项依据与 15000 token 描述预算与三档关闭粒度、Codex 的四组 Surface 正文与 Ultra 专属的主动委派、Qwen 的 “Automatic Delegation” 三条依据与 Fork 自动使用与 1000 字符软告警、Qoder 的 “Implicit Invocation” 与 `general-purpose` 回退）。

主线是「自动委派」这个字段此前只回答了「依据什么选」，没有回答「派发这个动作本身要不要先被授权」，而五家在这个问题上正好分成两组。Claude Code、Qwen Code 与 Qoder CLI 的官方文档都把「按描述主动委派」写成默认行为；Codex 与 Kimi Code 都要求先有请求或指令，但两者的落实层次不同——Codex 是官方文档按 Surface 分别陈述的产品行为，Kimi 是 2.3.2 用提示词文本加一处代码硬门禁刚改出来的默认值。

最大的新增在 Kimi Code。Release [`@moonshot-ai/kimi-code@2.3.2`](https://github.com/MoonshotAI/kimi-code/releases/tag/%40moonshot-ai%2Fkimi-code%402.3.2)（2026-10-25T07:59:14Z 发布，标签提交 `b8dd3a134060c6e80ba4a1659335cd63b68483f2`）的 `apps/kimi-code/CHANGELOG.md` 只有两条 Patch Changes，都正落在本字段上。第一条来自 [PR #4386](https://github.com/MoonshotAI/kimi-code/pull/4386) `fix(agent-core-v2): launch subagents only on explicit request`（提交 `fd2e2c7e2a3672dda91365d66b2ba74a1630521e`，2026-10-25T07:26:15Z），逐字为 “Handle tasks directly by default instead of proactively launching subagents; request delegation explicitly in your message, AGENTS.md, a skill, or an enabled multi-agent mode.”；第二条来自 [PR #4384](https://github.com/MoonshotAI/kimi-code/pull/4384) `fix(agent-core-v2): leave swarm mode to the user`（提交 `c9a48369843fdee1b494b9d49b1f4b3aeee73497`，2026-10-24T19:22:35Z），逐字为 “Agent swarms now start only when you turn on swarm mode: the agent can no longer launch `AgentSwarm` by itself, so swarms are no longer available in `kimi -p` or ACP clients such as Zed.”。compare 接口显示标签提交相对前者超前 2 个、相对后者超前 3 个且都不落后，即两条都已随 2.3.2 发布而不是只停在 main。

PR #4386 的实现方式是纯提示词，没有新增任何配置键、环境变量或权限规则，这点必须记清楚，因为它决定了这条门禁的强度。`packages/agent-core-v2/src/agent/tools/agent/agent.md`（`Agent` 工具描述的基串）新增一段，逐字为 “Do not launch a subagent unless the user explicitly asks for one. Each subagent starts cold and re-derives context you already have, which costs the user time and tokens. Asking means: the user asks for a subagent, delegation, or parallel agents, or requests one of the agent types below by name (for example "use an explore agent"). Explicit instructions in AGENTS.md or a skill, and a multi-agent mode the user turned on (such as swarm or tower mode), also count. Nothing else does: a large or multi-part task, or a request for depth, thoroughness, research, or investigation, is not a request to launch — do that work yourself with your own tools. The agent type descriptions below only help you choose a type once launching is authorized; they never authorize it. Resuming a subagent to continue already-authorized work needs no new request.”。这一段给出四类授权来源（用户明确要求 subagent、委派或并行 Agent／点名某个 Agent 类型／`AGENTS.md` 或 Skill 的显式指令／用户已开启的多代理模式），明确排除任务规模与「深入、调研、彻查」一类措辞，并且把 `description` 与 `whenToUse` 的作用限定为「授权之后帮你选类型，本身不授权」。同一提交还删掉了三处会诱导主动委派的文本：基串首段里那句 “Delegating also keeps the bulk of intermediate file contents out of your own context — you get a conclusion back instead of a pile of dumps.”、整段 “When NOT to use Agent: skip delegation for trivial work you can do directly…”，以及 Plan 模式工具描述里的 “For non-trivial tasks where you are unsure of the codebase structure or relevant code paths, use `Agent(subagent_type="explore")` to investigate first when the `Agent` tool is available.”。主 Agent 系统提示词 `packages/agent-core-v2/src/app/agentProfileCatalog/system.md` 同步加了一行 “Do not launch subagents with Agent unless the user, AGENTS.md, or a skill asks for them, or the user turned on a multi-agent mode such as swarm or tower mode.”，swarm 退出提醒追加 “Handle the request yourself, and launch subagents with Agent only if it explicitly asks for them.”，`session/agentLifecycle/profile/profiles.ts` 里内置 `explore` 档的 `whenToUse` 删掉了 “Use this agent for any read-only exploration that will clearly require more than 3 search queries. Prefer launching multiple explore agents concurrently when investigating independent questions.” 并把 “Use this when you need to quickly find files by patterns” 改写为 “it finds files by patterns”，即连内置档的描述也不再自带「该派发」的暗示。changeset 正文写得更直白：“Stop launching subagents without being asked; ask for subagents or parallel agents in your message or in AGENTS.md to have the agent delegate.”

PR #4384 与它相反，是代码层硬门禁，三处一起改。`features/swarm/tools/agent-swarm/agentSwarmTool.ts` 新增常量 `SWARM_MODE_OFF_RESULT`，`output` 逐字为 “Swarm mode is off, so AgentSwarm did not run and no subagents were started. Only the user can turn swarm mode on; do not call AgentSwarm until they do.” 且 `isError: true`，`resolveExecution()` 与 `execute()` 开头都先判 `if (!this.swarmMode.isActive) return SWARM_MODE_OFF_RESULT;`，同时删掉原先在 `execute()` 里由工具自己开启 swarm mode 的 `this.swarmMode.enter` 调用；`features/swarm/agent/swarmService.ts` 的 `enter(trigger)` 在 `trigger === 'tool'` 时抛 `Error2(ErrorCodes.VALIDATION_FAILED, 'Only the user can turn on swarm mode.')`，`onBeforeExecuteTool` 处理器加 `if (!this.isActive) return;`；`features/swarm/swarmOps.ts` 的 `swarmKey` reducer 对 `e.trigger === 'tool'` 直接返回原状态，因此状态机上也不可能再由工具进入 swarm mode。工具描述 `agent-swarm.md` 新增 “AgentSwarm runs only while swarm mode is on, and only the user can turn swarm mode on. When swarm mode is off, do not call AgentSwarm: the call is rejected and no subagents start.”。这一提交把四份官方文档一起改掉：中英文 `docs/*/reference/tools.md` 的 `AgentSwarm` 默认审批列由「swarm mode 中自动放行，否则需审批」改为「自动放行；仅在 swarm mode 中可用」，正文加「本工具仅在 swarm mode 开启时运行，且 swarm mode 只能由你手动开启（例如使用 `/swarm`）；swarm mode 未开启时，调用会被拒绝，不会启动任何 subagent。」并删掉「在 `manual` 权限模式下，未处于 swarm mode 时调用 `AgentSwarm` 会触发审批，除非已有权限规则允许」；中英文 `docs/*/reference/slash-commands.md` 的 `/swarm on` 与 `/swarm off` 行加上「`AgentSwarm` 仅在 swarm mode 开启时运行。」。也就是说 `manual` 权限模式下靠审批拦住 `AgentSwarm` 的旧机制被换成了直接拒绝，这同时影响 `agent-background` 与 `cmd-collaboration` 两个字段的既有记法，本轮只在本字段记录该门禁，那两个字段留作独立研究单元。

2.3.3（Release 2026-10-26T13:22:15Z，标签提交 `ec495f0cb00f6db9a9118bf979112886f4264a41`，是核对日期最新 Release）沿用同一策略，只补了两处交互：#4414（`f36c127`）逐字为 “Stop showing a failed swarm for `AgentSwarm` calls rejected before any subagent starts, such as while swarm mode is off; after such a rejection, the agent points you to `/swarm` if you asked for a swarm.”，#4423（`07a34fe`）逐字为 “Show a high-usage warning when you turn on swarm mode with `/swarm`.”。没有任何恢复主动委派或允许模型自启 `AgentSwarm` 的条目。开关侧也确认没有退路：2.3.3 标签下的 `docs/zh/configuration/env-vars.md` 里与 Subagent 相关的变量只有 `KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY`、`KIMI_CODE_SUBAGENT_SCOPE_CACHE_SIZE`、`KIMI_CODE_SUBAGENT_SCOPE_EVICT_TIMEOUT_MS`、`KIMI_SUBAGENT_TIMEOUT_MS`、`KIMI_CODE_SWARM_TIMEOUT_MS`、实验性 `KIMI_CODE_EXPERIMENTAL_SUBAGENT_FORK` 与 `KIMI_CODE_EXPERIMENTAL_TOWER`，`config-files.md` 的 `[subagent]` 与 `[swarm]` 两节都只有 `timeout_ms`，两处都没有控制主 Agent 是否主动派发的键。

`description` 与 `whenToUse` 的真实用途这次用源码钉住了。`packages/agent-core-v2/src/agent/tools/agent/agentTool.ts`（2.3.3 标签，31,103 字节）第 97 行把 `./agent.md?raw` 导入为 `AGENT_DESCRIPTION_BASE`，`get description()` 依次拼接该基串、后台说明（`AGENT_BACKGROUND_DESCRIPTION` 或 `AGENT_BACKGROUND_DISABLED_DESCRIPTION`）、开启 `SUBAGENT_FORK_FLAG_ID` 时的 fork 说明、以 “Available agent types (pass via subagent_type):” 起头的类型清单与模型池说明；`buildProfileDescriptions()` 把每个档的 `profile.description` 与 `profile.whenToUse` 过滤掉空值后用空格连接，写成 `- <name>: <details>` 一行。两个字段因此只出现在类型清单里，派发授权由基串与系统提示词那两处文本单独决定，这正是旧结论「依据 `description` · `whenToUse`」需要作废的原因。

本轮还记录了一处官方文档未同步。`docs/zh/customization/agents.md` 在 2.3.3 标签提交与核对日期的 main 分支都仍逐字写「subagent 由 main agent 自动调度：根据任务复杂度、上下文消耗和子任务的独立性，在适当时机派发，无需用户手动指定。」，英文版 `docs/en/customization/agents.md` 同一句为 “Sub-agents are scheduled automatically by the main Agent, based on task complexity, context consumption, and sub-task independence. They are dispatched at the right moment without the user having to specify one.”。该文件最后一次改动是 2026-10-23 的提交 `0325b755db46`（PR #4247 “feat(agent-core-v2): leave Plan mode to the user and review every plan”），早于两个委派提交，同页字段表也仍写 `description` 为「Agent 的用途。main agent 挑选 subagent 时会看到，请围绕委派决策来写」、`whenToUse` 为「补充说明何时应使用该 Agent」。本仓库按证据优先级以变更记录、工具描述、系统提示词与源码为准，把该文档页的「自动调度」说法记为未同步而不是记为冲突结论。

复核另外四家时把每家的浅描述都换成了一手引文。Claude Code 官方 Subagents 页（2026-10-26 抓取的 Markdown 形式，116,355 字节）的 “Understand automatic delegation” 一节给出三项依据与一句措辞建议，另有此前完全没记的描述预算与三档关闭粒度；核对日期最新 Release 仍是 v2.1.310（2026-10-23T23:39:00Z），其更新日志与自动委派无关，2026-10-24 与 2026-10-25 的仓库提交都是 “chore: Update mods/”，没有新的 CHANGELOG 段。Codex 官方 Subagents 页（22,907 字节）用 `ContentModeSwitch group="codex-surface"` 按 web、app、cli、ide 四组给出不同正文，本地三组都要求直接请求或适用的 `AGENTS.md`、Skill 指令，主动委派只属于 Web 端 ChatGPT Work 且只在 Ultra 档位，按本仓库 Surface 规则不计入 CLI 结论；核对日期 Releases 页最新仍是 stable 标签 rust-v0.164.0（2026-10-23T04:48:10Z）与其后的 rust-v0.165.0-alpha.1，2026-10-23 之后的提交是 Guardian 分类、GCP provider 设置、Hook 列举与 NFS 上的 SQLite journaling 一类改动。Qwen Code 的证据固定在 v0.26.1 标签提交 `b475278c4a300acebe6cfc990a9e1b1d18819bfc`（41,363 字节，与核对日期 main 逐字节相同，该文件最后一次改动是 2026-09-29 的提交 `31f6047e9d544f4f4a0fd9d46ee4a336da3853c3`），补上了 “Automatic Delegation” 的三条依据、Fork 的三种自动使用情形、Fork 子 Agent 的运行时禁止递归，以及此前没记的 “Limits” 一节两个软告警数字；2026-10-26 的 main 提交（`ca9d5f7ffab9`、`e11294b72866`、`2a6f777edfd3`、`e0702a270e13`、`3521066b4f65`、`e3bdc0f5d5c4`）都还没进入稳定 Release，且都不改自动委派依据。Qoder CLI 官方 Subagent 页把隐式选择写成与显式点名并列的入口并给出 `general-purpose` 回退，Release Notes 最新条目已推进到 CLI 1.1.78（October 23, 2026），1.1.78 与 1.1.77 两版都没有 Subagent 选择或委派条目。
