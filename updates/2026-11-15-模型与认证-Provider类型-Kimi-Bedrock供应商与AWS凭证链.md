# Provider 类型：Kimi Code 新增 `bedrock` 供应商类型与 AWS CLI 凭证链，云厂商凭据链字段同批改正「仅 VertexAI 使用该凭据链」

日期：2026-11-15
能力字段：`model-provider`（模型与认证 · Provider 类型，主字段）；同批修正 `auth-cloud-provider`（模型与认证 · 云厂商凭据链）中由同一变更作废的旧记法

## 本次改动

本次从官方来源快照里 Kimi Code 已发布到 `@moonshot-ai/kimi-code@2.6.2`、main 上出现 `feat(core): add Amazon Bedrock provider with AWS credential chain auth (#4895)` 这一坐标出发，核对后确认这是矩阵此前完全没有记录的一手确认新能力：**Kimi Code 的供应商 `type` 由六类增至七类，新增 `bedrock`，并且它是 Kimi 第二条绕过 `config.toml` 直接从 shell 读取凭据的通道**。

**一手证据**（统一固定到 PR #4895 合并提交 `88e3c20739a20a9a4003e366db7ecad9b88e10bd`，2026-11-13T08:20:37Z，改动 36 个文件；发布状态证据固定到 main HEAD `f082f04a093a3e71a2263c5461d52507dc31f83a`，2026-11-13T17:32:03Z）：

- 官方中文文档四页同步改写。`docs/zh/configuration/providers.md`（13,938 字节，本仓库此前固定的 `18c6d64272952503baccf706bff455bb6a2c488e` 版本为 9,874 字节）供应商类型表新增 `bedrock` 一行、协议列写作 Anthropic Messages 与 OpenAI 兼容「按模型区分」，并新增 `## bedrock` 整节；`docs/zh/configuration/config-files.md`（48,854 字节）的 `type` 行改为七个取值；`docs/zh/configuration/env-vars.md`（23,923 字节）的供应商凭证键表新增五个 `AWS_*` 键、页首例外句与表后 warning 都加入 Bedrock；`docs/zh/reference/server-api-service.md`（86,467 字节）创建与更新供应商两个端点的 `type` 枚举都含 `bedrock`，`models` 条目新增 `protocol` 行。
- 认证方式逐字为 “`type = "bedrock"` 的供应商可以使用标准 AWS CLI 凭证链，基于你的 AWS 环境凭证（来自 SSO、实例角色、环境变量、共享配置等）生成短期持有者令牌（bearer token）。只需指定 AWS 区域，可选地再指定一个命名 profile”，最小配置是 `[providers.bedrock]` 的 `type = "bedrock"` 加 `[providers.bedrock.env]` 的 `AWS_REGION`。env-vars 的 warning 逐字为 “对于 Amazon Bedrock，AWS 秘密凭证（`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_SESSION_TOKEN`、SSO 或 `~/.aws/credentials`）由 AWS SDK 的标准凭证链从 shell 读取。把它们写进 `[providers.<name>.env]` 不受支持、也不生效——CLI 只把区域和 profile 传给令牌生成器，由令牌生成器自行解析凭证。”
- 长期密钥是备选而非首选，且优先级更高：providers 文档逐字为 “另外，也可以改用 Amazon Bedrock API 密钥，通过 `api_key`、`api_key_env` 或 `[providers.bedrock.env]` 子表中的 `AWS_BEARER_TOKEN_BEDROCK` 键来配置。不过出于安全考虑，AWS 一般不建议使用长期 API 密钥。已配置的密钥始终优先于环境凭证链。”源码 `packages/agent-core-v2/src/llm-adapter/model/model-auth.ts`（10,125 字节）的解析顺序与之吻合：已配置密钥 → OAuth → `{ aws: { region, profile } }`，区域与 profile 都是子表优先、shell 兜底。
- 区域是硬性前提：逐字为 “区域必须能从 `AWS_REGION` 或 `AWS_DEFAULT_REGION`（写在子表里或在 shell 中导出）解析出来；目前不支持从 `~/.aws/config` 推断默认区域。”解析失败时 `model-auth.ts` 抛 `CONFIG_INVALID_ERROR_CODE`，文案为 “could not resolve an AWS region to build the endpoint URL”。
- 端点按区域与协议推导。`packages/core/src/llm/builtin/provider/bedrock/routing.ts`（3,003 字节）的后缀逐字为 `const suffix = protocol === 'anthropic' ? '/anthropic' : '/openai/v1';`，拼成 `https://bedrock-runtime.<region>.amazonaws.com` 加后缀；文档同时写明自定义 `base_url`（或 `AWS_BEDROCK_BASE_URL`）“是完整 URL：必须包含模型所用协议的线路路径（`/anthropic` 或 `/openai/v1`），CLI 会原样使用它，不会追加协议后缀”，适用场景点名 `bedrock-mantle`、代理与 FIPS/双栈主机名。
- 一个供应商承载多种线路协议，靠模型 ID 推断。跨区域前缀正则逐字为 `^(?:[a-z]{2}|apac|global)$`，剥掉前缀后 `anthropic.*` 走 Anthropic Messages、`openai.gpt-oss*` 走 Chat Completions、其余 `openai.*` 走 Responses、`moonshotai.*` 与 `moonshot.*` 走 Chat Completions，文档写 “其他前缀默认使用 OpenAI Chat Completions API”，源码回落值同样是 `openai`；模型别名上可写 `protocol`（`anthropic`／`openai`／`openai_responses`）显式覆盖。`provider-definition.ts`（5,753 字节）为此给 `bedrock` 注册了三条定义，只有 `anthropic` 那条换用 `bedrockAnthropicRequester`。
- Bedrock 的 Anthropic 通道与原生 `anthropic` 供应商认证隔离。`bedrock/anthropic.ts`（878 字节）以 `apiKey: null` 与 `authToken` 构造 `@anthropic-ai/sdk` 客户端，`packages/core/test/llm/bedrock.test.ts`（4,925 字节）断言 Bedrock 请求头 `authorization` 为 `Bearer …` 且 `x-api-key` 为 `null`，而原生 `anthropic` 协议发 `x-api-key`。这与提交信息里的子提交 “feat(core): add Bedrock provider with isolated Anthropic auth” 对应。
- 令牌生命周期有明确数值。`bedrock/credentials.ts`（2,413 字节）用 `@aws/bedrock-token-generator` 的 `getTokenProvider`，常量逐字为 `const DEFAULT_TTL_SECONDS = 43_200;` 与 `const EXPIRY_MARGIN_MS = 15 * 60 * 1000;`，并发 `resolve()` 合并成一次取令牌，`canRecover` 只在 HTTP 401 为真；测试断言时钟前进 12 小时后重取令牌、`{ status: 500 }` 不触发恢复、取令牌失败（示例文案 `run aws sso login`）原样冒泡且下次调用重试。`packages/core/package.json`（1,232 字节）为此新增依赖 `@aws/bedrock-token-generator@^1.1.0`，`apps/kimi-code/scripts/native/check-bundle.mjs`（2,998 字节）的 `optionalRuntimeRequires` 新增 `@aws-sdk/signature-v4a`。
- 「无密钥即已连接」是新的状态语义。`catalog-service.ts`（18,885 字节）与 `catalog.ts`（5,952 字节）新增 `supportsAmbientCredential`，取值逐字为 `provider.type === 'bedrock' && !hasApiKey && !hasOAuthToken`，`toProtocolProvider` 的 `status` 判定因此改为 `hasApiKey || hasOAuthToken || supportsAmbientCredential ? 'connected' : 'unconfigured'`；`authService.ts`（34,065 字节）新增 `if (auth.aws !== undefined) return;`，认证摘要不再因缺少 API Key 报错。即只写了区域的 `bedrock` 供应商在 `GET /api/v1/providers` 里直接报 `connected`。
- 导入通道明确不覆盖 Bedrock。同页 `/provider` 的 Known third-party provider 路径仍逐字写 “Amazon Bedrock / Cohere 等专有协议和无法识别的显式协议会被拒绝导入”，CLI 参考也写专有协议如 Amazon Bedrock 无法 `catalog add`，因此 `bedrock` 条目只能手写 `config.toml` 或经服务 API 创建。
- 周边同步：`packages/node-sdk/src/config/schema.ts`（14,697 字节）的 `ProviderTypeSchema` 加入 `bedrock`，`ModelAliasBaseSchema` 的 `protocol` 枚举由 `anthropic`／`openai_responses` 放宽到再加 `openai`；`packages/migration-legacy/src/steps/config.ts`（22,869 字节）的 `SUPPORTED_PROVIDER_TYPES` 同步加入 `bedrock`，`kimi migrate` 不会丢掉该条目。

**发布状态必须标条件**。changeset `.changeset/bedrock-provider.md`（136 字节）逐字为 frontmatter `"@moonshot-ai/kimi-code": minor` 加正文 “Add support for Amazon Bedrock providers, configured with `type = "bedrock"` and `AWS_REGION`.”，该文件到 main HEAD `f082f04a093a3e71a2263c5461d52507dc31f83a` 仍然存在，说明这次 minor 变更尚未被任何 Release 消费；核对日期最新 stable Release `@moonshot-ai/kimi-code@2.6.2`（2026-11-13T17:20:51Z）正文只有 #4875、#4876、#4885、#4905、#4922、#4927 六条 Patch Changes，没有任何 Bedrock 或 AWS 条目；GitHub compare 显示 2.6.2 标签与该提交的关系是 `diverged`（标签领先 27 个提交、落后 23 个），而 main HEAD 与同一提交是 `ahead`（领先 2 个、落后 0 个）。故截至 2026-11-15 尚无包含 Bedrock 的 Release，两个单元格的结论都带「合入 main 尚未发布」条件，证据状态由 `官方确认` 降为 `条件项`。
