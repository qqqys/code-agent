# 后台任务：Qoder CLI 1.1.94 给后台 Bash 命令加了默认 10 分钟超时（更新日志已确认、官方七页均未同步），同轮把 Claude 的后台命令时限、Kimi 的三层超时与 24 小时硬上限、Codex 的轮询窗口误读与 Qwen 的「后台不计时」全部补到源码与文档原文；另作废 Kimi `WaitFor` 90 秒上限「尚未发布」的旧结论（实为 2.2.0 已发布）

日期：2026-11-22
能力字段：`execution-background`（执行与 Git · 后台任务）

## 为什么选这个字段

官方来源快照里 Qoder CLI 没有公开仓库提交与 Release（闭源，只有文档站与更新日志站），本轮先核对 `changelog.qoder.com/cli`，最新条目仍是 **CLI 1.1.94（November 20, 2026）**。上一轮研究（提交 `4aaf351`，PR #151）处理了同小节的 Subagent 默认转后台，并在「未处理项」里明确留下这一条：

> **Qoder CLI 1.1.94 的 “Background Bash commands now default to a 10-minute timeout”**：属 `execution-background` 字段，本次未展开，是下一次研究的候选。

`docs/09-版本与证据.md` 的 Qoder 核对坐标行里也写着「同小节 “Background Bash commands now default to a 10-minute timeout” 属 `execution-background`、本次未处理」。因此本次研究单元定为 `execution-background`。

选定后又发现本字段其余四家的记录普遍偏浅：Claude 单元格只有 `/background`·`/tasks`·`Monitor` 三个入口名、完全没有官方早已文档化的「后台命令时限」一节；Codex 单元格只写「统一 PTY 执行通道可保留长进程」，而 `background_terminal_max_timeout` 这个键名极易被误读成后台终端的存活上限；Qwen 单元格没有任何超时口径；Kimi 单元格虽有「Bash 默认 10 分钟、Agent 默认 2 小时」一句，但既没有 24 小时硬上限、也没有配置节改名与 print 模式的实现方式，且同字段的 `WaitFor` 结论还停在「main 分支尚未发布」。于是按「一个能力字段、五家一起核对」的口径把后台超时与生命周期整条线一次补全。

### 4. Claude Code：补录官方早已文档化的「后台命令时限」一节

本仓库此前完全没有记录这一节。官方工具参考（`.md` **98,131 字节**）的 “Time limit for background commands” 逐字为：

> In a session that runs unattended, such as a run with the `-p` flag, an Agent SDK application, a CI job, or a cloud session, background Bash and PowerShell commands have a time limit. A local session you work in from a terminal, the desktop app, or the VS Code extension has no time limit on background commands.
>
> The time limit requires Claude Code v2.1.285 or later. Before v2.1.288, it applied in every session.
>
> The time limit counts from the moment the command enters the background:
>
> * A command that Claude starts in the background gets 30 minutes, or the `timeout` Claude passes with `run_in_background`, up to a maximum of 2 hours
> * A command that starts in the foreground and then moves to the background at its timeout gets 30 minutes from the move
>
> In a run with the `-p` flag whose prompt you pass as text rather than with `--input-format stream-json`, both defaults are 10 minutes instead of 30.

到限行为逐字为 “When a background command reaches its time limit, Claude Code stops it and tells Claude why, and Claude can start the command again with a longer `timeout` if the work still needs it. The stop notice reads `Background command "<description>" was stopped after reaching its background time limit`.”；抬高上限的两个变量逐字为 “Both take milliseconds, and neither can shorten a limit: a lower value leaves the defaults and the 2-hour maximum in place.”、“Set `BASH_DEFAULT_TIMEOUT_MS` above `1800000` to replace the 30-minute default with that value…”、“In a `-p` run whose prompt you pass as text, any value above `600000` replaces its 10-minute default” 与 “Set `BASH_MAX_TIMEOUT_MS` above `7200000` to raise the 2-hour maximum to that value.”。

前台侧口径（同页 “Timeout and output limits”）逐字为 “Each command runs under a timeout, and Claude manages it: when it wants longer than the default for a command, it passes the `timeout` parameter with that call. You never set a per-command timeout.”，两个变量为 `BASH_DEFAULT_TIMEOUT_MS`（默认 120000，即 2 分钟）与 `BASH_MAX_TIMEOUT_MS`（默认 600000，即 10 分钟），“the effective ceiling is the larger of the two”。前台转后台一节逐字为 “When a foreground command reaches its timeout without finishing, Claude Code moves it to the background instead of stopping it, unless the command starts with `sleep`.”，结果文本为 `Command did not complete within its 120s timeout and was moved to the background`，且 `cd`/`pushd`/`popd`/`chdir` 一律不带回（另附 `Session cwd remains <dir>; …`）。生命周期归属逐字为 “A command that a foreground subagent started stops when that subagent's run ends…” 与 “A command that the main conversation or a background subagent started keeps running after a final response, until it exits, is stopped, or reaches its time limit.”。输出侧另有 “a command whose output passes 5 GB is killed”。

Monitor 一节此前也没有记录截止期，逐字为 “Every watch Claude starts has a deadline: 5 minutes by default, at most 30 minutes, and at most 10 minutes in a non-interactive run given a single prompt with `-p`.” 与 “At the deadline the watch ends. Claude gets one notice, so it can start the watch again if it's still needed.”，WebSocket 观察同样受 `timeout_ms` 约束、`TaskStop` 可提前取消；同页工具表把 `TaskOutput` 记为 “Removed in v2.1.277. Previously retrieved output from a background task; Claude reads a background task's output file with `Read` instead”，本字段旧记录写的「已弃用的 `TaskOutput`」据此改为「已移除」。

版本时间线取自更新日志（固定到 `CHANGELOG.md` 提交 `e791a1c41eee7504672a109fd6eb66b11566b8a1`，2026-11-20T22:32:35Z，**1,382,549 字节**）：

| 版本 | 逐字条目 |

| v2.1.260 | Removed the one-hour time limit on background commands started by subagents; they now run until they exit or are stopped, matching the main session |

### 5. Codex：`background_terminal_max_timeout` 不是存活上限，后台终端数量有 64 的软上限

官方配置参考（`.md` **154,596 字节**，与 2026-11-17 记录同尺寸）的 `background_terminal_max_timeout`（number）逐字为：

> Maximum poll window in milliseconds for empty `write_stdin` polls (background terminal polling). Default: `300000` (5 minutes). Replaces the older `background_terminal_timeout` key.

即它约束的是**空 `write_stdin` 轮询窗口**，不是后台终端的存活时长。全页含 timeout 的配置键只有 `mcp_servers.<id>.startup_timeout_sec`／`startup_timeout_ms`／`tool_timeout_sec`、`model_providers.<id>.stream_idle_timeout_ms`、`model_providers.<id>.auth.timeout_ms` 与它自己六个，**没有任何给后台终端设总时长的键**。

标签 `rust-v0.171.0`（标签对象 `295eca93394bb83a6ec8e0841033f3997f97fcbd` 指向提交 `ccf9be8cc458bd6b8336fe84d68d8893f2691a5e`，2026-11-19T23:07:37Z）下的源码给出确切边界：

- `codex-rs/core/src/unified_exec/mod.rs`（**2,675 字节**）：`MIN_YIELD_TIME_MS = 250`、`WINDOWS_INITIAL_EXEC_YIELD_TIME_FLOOR_MS = 10_000`、`MIN_EMPTY_YIELD_TIME_MS = 5_000`（注释 “Minimum yield time for an empty `write_stdin`.”）、`MAX_YIELD_TIME_MS = 30_000`、`DEFAULT_MAX_BACKGROUND_TERMINAL_TIMEOUT_MS = 300_000`、`DEFAULT_MAX_OUTPUT_TOKENS = 10_000`、`UNIFIED_EXEC_OUTPUT_MAX_BYTES = 1024 * 1024 // 1 MiB` 与 `MAX_UNIFIED_EXEC_PROCESSES = 64`；`clamp_yield_time()` 在 Windows 上先抬到 10 秒再钳制，`UnifiedExecProcessManager::new()` 把配置值 `.max(MIN_EMPTY_YIELD_TIME_MS)`。
- `process_manager.rs`（**73,850 字节**）：注释 “Empty polls use configurable background timeout bounds.”，空轮询走 `.clamp(MIN_EMPTY_YIELD_TIME_MS, self.max_write_stdin_yield_time_ms)`、非空写入走 `.min(MAX_YIELD_TIME_MS)`，`let deadline = start + Duration::from_millis(yield_time_ms);` 只约束该次调用；`prune_processes_if_needed()` 在进程数达到 64 时按 LRU 淘汰，策略函数带注释 “Centralized pruning policy so we can easily swap strategies later.”，先把按 `last_used` 倒序的最近 **8 个**放进 `protected` 集合、再优先挑已退出且不受保护者、找不到才挑最久未用且不受保护者，持有 interaction lock 的候选被跳过（注释 “Do not prune processes while write_stdin or terminal event publication holds their interaction lock.” 与 “The store may temporarily exceed its soft cap while an exited process is publishing its terminal event. Do not evict a live process just because that exited process is briefly locked.”），被挑中条目在 `unregister_network_approval_for_entry()` 后执行 `terminate()`。
- `tools/handlers/unified_exec.rs`（**1,798 字节**）：`fn default_write_stdin_yield_time_ms() -> u64 { 250 }`。
- `tools/handlers/unified_exec/write_stdin.rs`（**5,364 字节**）：注释 “Empty writes are background polls, and non-empty writes continue a command that already ran PreToolUse as Bash, so do not emit a second pre hook here.”，`supports_parallel_tool_calls()` 返回 `true`。

官方 CLI Slash 命令参考（`.md` **59,711 字节**，与 2026-11-20 记录同尺寸）补上 `/ps` 的输出粒度，逐字为 “Codex shows each background terminal's command plus up to three recent, non-empty output lines so you can gauge progress at a glance.” 与 “Background terminals appear when `unified_exec` is in use; otherwise, the list may be empty.”；`/stop` 逐字为 “Codex stops all background terminals for the current session. `/clean` is still available as an alias for `/stop`.”。配置参考另确认 `features.unified_exec` 已是 stable：“Use resumable command execution (stable; enabled on all platforms). User opt-outs are ignored. Managed requirements can disable resumable processes and `write_stdin`, leaving one-shot `exec_command` available.”——托管要求禁用 resumable 进程时就没有后台终端。64 的软上限与 8 个受保护进程只见于源码、官方文档未记录，被淘进程 `terminate()` 后其输出是否仍可读官方也没有说明，两点记为未确认。

### 6. Qwen Code：后台 Shell 不计时，超时键官方明确只管前台

标签 `v0.28.4`（指向提交 `e8424c88ddd463c56602063efde57c328b917cd4`）下的三份材料：

- `packages/core/src/tools/shell.ts`（**308,165 字节**）：`execute()` 在计算生效超时**之前**就有 `if (this.params.is_background) { return this.executeBackground(signal, shellExecutionConfig); }`，`executeBackground()` 内不做任何计时，只拒绝 `git commit`（逐字 “Refusing to run `git commit` in background mode: AI-attribution notes are written by the foreground completion path. A value of 0 disables the timeout, but only at the settings/default level — the per-call `timeout` param is validated to be > 0 by `validateToolParamValues`, so 0 never arrives that way.”，实现为 `this.params.timeout ?? this.config.getShellDefaultTimeoutMs() ?? DEFAULT_FOREGROUND_TIMEOUT_MS`。常量为 `DEFAULT_FOREGROUND_TIMEOUT_MS = 120000`、`PROMOTE_CANCEL_SIGKILL_TIMEOUT_MS = 200`、`OUTPUT_FLUSH_TIMEOUT_MS = 10_000`、`MIN_LONG_RUN_THRESHOLD_MS = 1000`、`FOREGROUND_TIMEOUT_WARNING_LEAD_MS = 15_000` 与 `MAX_INTENTIONAL_SLEEP_SECONDS = 10 * 60`；schema 的 `timeout` 为 `minimum: 1, maximum: 600000`；前台即将超时的提醒逐字为 “Warning: this command is about to time out. In the interactive TUI, press Ctrl+B to keep it running in the background.”，长任务劝告阈值按注释 “Long-run advisory threshold: half the EFFECTIVE foreground timeout” 取生效前台超时的一半、下限 1000 毫秒。
- `packages/core/src/services/backgroundShellRegistry.ts`（**24,681 字节**）：全部上限常量只有 `MAX_NOTIFICATION_MODEL_COMMAND_LENGTH = 500`、`MAX_NOTIFICATION_OUTPUT_TAIL_BYTES = 8192` 与 `MAX_RETAINED_TERMINAL_SHELLS = 32`（淘汰为 `while (terminalEntries.length > MAX_RETAINED_TERMINAL_SHELLS)`，注释提到与 `MonitorRegistry.MAX_RETAINED_TERMINAL_MONITORS` 同构），**没有任何超时常量**。
- `docs/users/configuration/settings.md`（**451,480 字节**）：`tools.shell.defaultTimeoutMs`（number，默认栏 `undefined`）逐字为 “Default timeout, in milliseconds, for **foreground** shell commands started by the agent. Set to 0 to disable the timeout.”；全页 29 个 `tools.` 前缀键里没有任何后台 Shell 超时或后台任务时长键，6 个 `agents.` 前缀键里只有 `agents.defaultBackground` 与前后台相关（逐字 “The default is `true` (background execution). An explicit `run_in_background` argument takes precedence over the agent definition's `background` field, which takes precedence over this setting. Requires restart.”）。

后台 Shell 是否会在某个未公开路径上被回收、以及 `MAX_RETAINED_TERMINAL_SHELLS` 淘汰的是记录还是进程，官方文档没有说明，记为未确认。

### 7. Kimi Code：补全三层超时链、24 小时硬上限、`[task]` 节改名与 print 模式实现

标签 `@moonshot-ai/kimi-code@2.7.2`（标签对象 `1781dbd74bc7fabf23ac4721a570397f278817f1` 指向提交 `56145f849caa305d42acd09b67fb65d11146f887`，2026-11-20T09:06:52Z）下取证九份材料：

**常量层**——`packages/agent-core-v2/src/agent/tools/os/bash/bash.ts`（**2,740 字节**）逐字为 `DEFAULT_TIMEOUT_S = 60`、`MAX_TIMEOUT_S = 5 * 60`、`DEFAULT_BACKGROUND_TIMEOUT_S = 10 * 60` 与 `MAX_BACKGROUND_TIMEOUT_S = 24 * 60 * 60`，即前台默认 60 秒／上限 300 秒、后台默认 600 秒／**硬上限 86400 秒（24 小时）**。24 小时上限是本仓库此前完全没有记录的。`timeout` 的 schema 描述由常量拼出，逐字为 “Optional timeout in seconds for the command to execute. Foreground default 60s, max 300s. Background default 600s, max 86400s. Ignored for background commands when disable_timeout=true.”；`superRefine` 超限报错逐字为 `timeout must be ≤ <cap>s (background/foreground)`；`disable_timeout` 描述逐字为 “If true, do not apply a timeout to the command. Only applies when run_in_background is true.”。

`bashTool.ts`（**25,810 字节**）给出三分支：`args.disable_timeout ? undefined : args.timeout === undefined ? this.detachTimeoutMs() : normalizeTimeoutMs(args.timeout, true)`，`detachTimeoutMs()` 取 `resolveAgentTaskConfig(this.config)?.bashTaskTimeoutS`、未配置时回落 `DEFAULT_BACKGROUND_TIMEOUT_S * MS_PER_SECOND`，`autoBackgroundOnTimeout()` 为 `resolveAgentTaskConfig(this.config)?.bashAutoBackgroundOnTimeout ?? true`。注入模型的指引按开关三选一：“A foreground command that hits its timeout is moved to the background instead of being killed, and you are notified when it completes.”／“A foreground command that hits its timeout is killed.”／不允许后台时的 “A command that hits its timeout is killed.”；后台指引另写 “Set `disable_timeout=true` only when the task should run without a timeout.” 与 “Use `TaskOutput` only for a non-blocking snapshot, and `TaskStop` only to cancel.”。同文件给 subagent 的等待指引逐字为 “You are running as a subagent: ending your turn is your final hand-off to the parent agent, and completion notifications that arrive after it reach no one. Do not end your turn while a background task whose result you need is still running. Keep waiting for it with WaitFor, calling it again after a timeout if needed, or run the command in the foreground with a suitable timeout instead.”。
