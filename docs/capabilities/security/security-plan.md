# 只读或计划模式

[返回权限与沙箱详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=security-plan)

> 核对日期：2026-10-29

## 定义

在执行修改前进入以阅读、分析和方案确认为主的工作状态，并限制或阻断一般写入；本页同时比较谁能开启这一状态、Plan 期间放行与阻断什么、计划如何被审阅，以及退出后落到哪个权限模式。

## 比较边界

### 本页包含

- Plan 工作状态的入口与可开启者（用户入口与模型工具）
- Plan 期间被放行、被限制与被阻断的工具
- 计划的呈现方式、审批选项与退出后的权限模式
- 非交互运行与 Subagent 中的 Plan 行为
- Plan 相关配置键、默认值与计划文件保存位置

### 本页不包含

- 普通 Todo 或清单工具（Codex `update_plan`、Kimi `TodoList`）
- Subagent 的只读配置与内置 `plan`／`explore` 角色本身
- 代码 Review 命令
- OS 沙箱强度与网络边界本身

## 跨产品事实

1. 五家都有 Plan 工作状态，但“谁能开启”分成两类：Claude Code、Qwen Code 与 Qoder CLI 既给用户入口也给模型工具（Claude `EnterPlanMode`／`ExitPlanMode`、Qwen `enter_plan_mode`／`exit_plan_mode`、Qoder `EnterPlanMode`／`ExitPlanMode`），Codex 只有用户入口（`/plan` 与 TUI 的协作模式预设，`rust-v0.165.0` 的 `codex-rs/core/src/tools/handlers` 57 个条目里名字含 plan 的只有实现 `update_plan` 的两个文件），Kimi Code 自 2.4.0 起删掉 `EnterPlanMode`、只剩用户入口。
2. Kimi Code 2.4.0（2026-10-28T11:45:13Z 发布，标签提交 `f26e4d91ef8d5d233f6c20b42a150f96924d4f5e`）是这条轴上最新的一次收紧：`EnterPlanMode` 工具、它在 `default-tool-approve` 里的自动放行条目与它的 telemetry 事件一起删除（`DEFAULT_APPROVE_TOOLS` 由 24 项减到 23 项、仍含 `ExitPlanMode`），`coder` 档与 Tower worker 档删掉两个 Plan 工具，官方交互文档改写为“Plan 模式只能由你打开，Agent 不会自己进入，即使你在对话里要求它进入”，系统提示词按档注入 `PLAN_MODE_GUIDANCE`；改动来自提交 `0325b755db46f865f2dc0bca0d6c3d95ad817fcb`（PR #4247，2026-10-23 合入 main，84 个文件、+979/−790），与 2.3.3 标签提交的 compare 结果是 `diverged`、与 2.4.0 标签提交的 compare 结果是 `behind`，因此不在 2.3.3 及更早版本里。本仓库此前记的“Auto 会自动处理全部审批”“退出 Plan 通常仍需确认”据此作废——旧官方文档里“计划退出会自动批准，并在记录中标记为 "Auto-approved"”一句已在同一提交删掉。
3. 计划是否总要人工审阅：Kimi 与 Qoder 在任何权限模式下都要（Kimi 官方写“在任何权限模式下，包括 "Never Ask"，退出 Plan 模式都需要你确认”，Qoder 官方写“entering or leaving Plan always request confirmation … None of these are outcomes of a permission verdict”）；Qwen 的 `exit_plan_mode` 在 Plan 模式下 `requiresUserInteraction()` 返回真、确认框 `hideAlwaysAllow: true`；Claude 的 `ExitPlanMode` 在工具参考的 Permission required 列标 Yes，但交互式终端会话里 bypass permissions 可用时 Plan 的阻断整体不强制；Codex 的 Plan 模式“until a developer message explicitly ends it”，TUI 在计划被批准后弹 “Implement this plan?” 让用户选实现方式。
4. 无人值守模式与 Plan 的关系各不相同：Kimi “Never Ask”（`auto`）的唯一例外是计划审阅，注入提示逐字写 “Plan mode is the exception: ExitPlanMode still waits for the user to review the plan.”；Qoder `auto` 下分类器熔断是唯一由权限裁决产生授权提示的情况，而进出 Plan 的确认不属于权限裁决（1.0.12 与 1.1.11 曾取消该弹窗、1.1.21 恢复）；Qwen YOLO 下模型自行进入 Plan 被拒并回 “Stayed in YOLO mode (plan mode not entered).”，只有 `userRequested: true` 才生效（#5970）；Claude 在 auto 可用且 `useAutoModeDuringPlan`（默认开启）时让 classifier 审查规划期的 shell 命令而不是逐个询问。
5. Plan 期间允许什么、阻断什么的口径不同：Kimi 只允许写当前计划文件，拦 `TaskStop`、`CronCreate`、`CronDelete`，`Bash` 按普通权限规则；Qwen 的每轮注入提醒禁止任何编辑与状态修改类工具，安全性无法判定的 shell 命令要用户对那一次调用单独批准一次，并明令不得用包装、引号技巧、别名或混淆手段绕过；Codex 允许非变更动作（含只写缓存或构建产物的测试、构建与检查）但禁止任何改动仓库跟踪状态的动作，判据是“if the action would reasonably be described as "doing the work" rather than "planning the work," do not do it”；Claude 不改源码但会跑 shell 探索，规划期命令的处理按 bypass 可用、auto 加 `useAutoModeDuringPlan`、其余三种情况依次判定；Qoder 的 `plan` 取值被描述为 “Read-only mode”，1.0.33 起支持只读 Shell 命令，官方没有公开被阻断工具的完整清单。
6. 计划正文的载体五家不同：Kimi 用会话目录里的计划文件（`<sessionDir>/agents/<agentId>/plans/<id>.md`），`ExitPlanMode` 不接受计划正文、只读文件并在审阅前 `recordRevision()` 把该版写进 blob store 的 `plan/<id>/v<n>.md`（带 `sha256` 与 `bytes`），`options` 可给 1–3 个备选方案；Qwen 用 `exit_plan_mode` 的必填 `plan` 参数（空字符串被拒），批准后 `savePlanBestEffort(plan)`；Codex 要求把最终计划包在 `<proposed_plan>` 块里由客户端渲染（每轮至多一个块、修订必须整块替换）；Claude 官方只写 Claude “writes a plan” 并提供 `Ctrl+G` 在默认文本编辑器里打开拟议计划；Qoder 官方没有公开计划正文的载体，只能从 0.2.3 的 “Fixed Plan mode requiring permission to read plan files” 确认存在计划文件。
7. Subagent 范围：Kimi 的 Plan 模式只属于 main agent（`enter()` 对其他 agent 抛 `SESSION_PLAN_MODE_INVALID: "Plan mode is only available to the main agent"`，`planKey` 的 `PlanModeEnter` reducer 忽略非 main agent 的事件，`coder` 档与 Tower worker 档已删两个 Plan 工具，官方 Agent 文档同步删掉 `coder` subagent “进入 Plan 模式” 的说法）；Qwen 的两个 Plan 工具在 Subagent 里按 `subagent-plan-tool-policy` 被阻断，团队场景的 plan-required teammate 改由 leader 裁决（成功时 `llmContent` 以 “Leader approved.” 开头）；Qoder 0.2.15 修过 “Fixed auto mode not being respected during plan mode for subagent tool calls”，说明其 Plan 状态下存在 Subagent 工具调用；Claude 与 Codex 的 Subagent 侧 Plan 行为官方未公开，记为未确认。
8. 非交互运行：Kimi `kimi -p` 新会话跳过 `default_plan_mode`（stderr “default_plan_mode is not applied in print mode, because Plan mode waits for your review.”），恢复已在 Plan 的会话照常运行并提示用 `kimi -r <id>` 审阅，非交互宿主里审批立即判定且从不视为批准（计划审阅返回 deny 加 “Nobody can review this plan in a non-interactive run, so plan mode stays active for the rest of this run and you cannot edit files other than the plan file.”，`resolveNonInteractive` 的类型排除了 `ask`）；Qwen 的 `/plan` 只在交互式可用，headless/ACP 里 `enter_plan_mode` 是唯一入口，非交互且无 ACP 时直接拒绝；Claude 写 “Plan mode keeps its blocks wherever Claude Code runs without an interactive terminal, including non-interactive runs with `-p`, Agent SDK sessions, and conversations in the VS Code extension's chat panel.”；Qoder 1.0.35 修过 “Fixed Plan and Ask tools not being correctly disabled in headless mode”；Codex 非交互运行下的 Plan 行为官方未公开，记为未确认。
9. 配置键五家各自独立：Kimi `default_plan_mode`（默认 `false`，`kimi -p` 下不生效）；Qwen `.qwen/settings.json` 的 `tools.approvalMode: "plan"`；Claude 项目 `.claude/settings.json` 的 `defaultMode: "plan"`、VS Code 用户设置的 `claudeCode.initialPermissionMode: "plan"`，以及 `useAutoModeDuringPlan` 与 `showClearContextOnPlanAccept`；Codex 只有 `plan_mode_reasoning_effort`（Plan 模式专用推理强度覆盖，未设时用内置预设），没有默认进 Plan 或开关 Plan 的键；Qoder `general.plan.enabled: false` 一次性关掉 `/plan`、`--permission-mode plan` 映射与两个 Plan 工具，1.0.44 起 `/settings` 里也有开关。
10. Plan 与权限模式的关系不同：Qoder 自 1.0.14 起把 Plan 做成独立工作状态（`/plan` 进出、`Shift+Tab` 只循环权限模式，`--permission-mode plan` 只保留兼容映射 “translates to default + enters Plan work state”）；Claude 与 Qwen 的 Plan 是权限模式之一（Claude `Shift+Tab` 循环 `default` → `acceptEdits` → `plan`，Qwen 循环 plan → default → auto-edit → auto → yolo）；Codex 把 Plan 做成与 `Default` 并列的协作模式（`ModeKind`，TUI 可见的只有这两个，预设来自服务端发现、缺发现就没有预设）；Kimi 的 Plan 是独立于三种权限模式的开关（`/plan [on|off]`、`--plan`、`default_plan_mode`），恢复会话时可用 `--plan`／`--yolo`／`--auto` 覆盖原会话保存的模式。
11. Plan 工作流与技术上的只读沙箱不是同一概念：Codex 明确把两者作为不同控制（官方审批页把“想聊天或规划而不做改动”指向 `/permissions` 切 `read-only`），Kimi 的 Plan 门禁挂在工具执行器的 before-execute 钩子上、与权限策略链和沙箱都无关，Qwen 的 Plan 是审批模式而不启用 Sandbox。清单工具也与 Plan 模式无关：Codex 的 `update_plan` 在 Plan 模式下直接返回错误 “update_plan is a TODO/checklist tool and is not allowed in Plan mode”，Kimi 的 before-execute 门禁只拦 `Write`／`Edit` 越界写、`TaskStop`、`CronCreate` 与 `CronDelete`，`TodoList`／`SetTodoList` 不在其中。
