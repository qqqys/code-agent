# 文件系统隔离

[返回权限与沙箱详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=security-filesystem)

## 定义

通过 OS、容器或进程级边界限制命令及其子进程能读取和写入的文件路径，而不仅是让模型遵守工具规则。

## 比较边界

### 本页包含

- OS 或容器隔离
- 可写根目录
- 受保护与禁止读取路径
- Linux 后端与用户命名空间前置条件
- 削弱或退出隔离的开关及其代价

### 本页不包含

- 只针对文件工具的 Allow/Deny
- Git Worktree 隔离
- 网络访问策略

## 跨产品事实

1. Claude Code、Codex 与 Qwen Code 都公开了本地 OS 级文件系统沙箱；三家的 Linux 边界都落在 bubblewrap 上，Qwen 另提供 Landlock 回退。
2. Codex 官方 Sandboxing 页把 Linux 与 WSL2 的实现写成 bubblewrap（macOS 是 Seatbelt），而不是本仓库此前记录的 Landlock；Landlock 与 seccomp 在 Codex 里是 `codex-linux-sandbox` crate 的实现依赖，`bwrap.rs` 才是构造边界的地方。原生 Windows 另有 `elevated`、`unelevated` 与 `mxc` 三种实现，由 `[windows] sandbox` 选择；`codex sandbox` 是 Stable 子命令，可用同一套策略手动跑一条命令。
3. Linux 用户命名空间是三家的共同前置条件：Claude Code 与 Codex 都在官方文档里写了 Ubuntu 24.04 及以后的 AppArmor 限制会让 bubblewrap 建不出用户命名空间，并各自给出 profile 文件（Claude 是 `/etc/apparmor.d/bwrap`，Codex 是 `/etc/apparmor.d/bwrap-userns-restrict`）与同一个 sysctl 键 `kernel.apparmor_restrict_unprivileged_userns`；Qwen Code 则直接要求 bwrap 装在 `/usr/bin/bwrap`。
4. 三家都提供削弱或退出文件系统隔离的开关并写明代价：Claude Code 的 `sandbox.enableWeakerNestedSandbox`（改挂容器已有 `/proc`，官方写 “considerably weakens security”）与 `sandbox.allowNestedUserNamespaces`（v2.1.305 更新日志写 “this lets them get around the sandbox's file protections”，2026-11-28 复核时官方 Sandboxing 页与 Settings reference 已双页记录该键：Boolean、**Default** `false`、Scope 为 “User or managed”、需 v2.1.305 及以上）、Codex 的 `danger-full-access`、Qwen Code 的 `filesystem: "workspace-write"` 与 Landlock 后端的 `partial` enforcement。
5. Qwen Code 自 v0.24.4 起把 Linux 沙箱从「整个 CLI 跑在 bwrap 里」改成「只有工具执行跑在 bwrap 或 Landlock 里」，策略键 `tools.executionSandbox` 由运算符（User 或 System 设置）所有，Workspace 设置即使在受信任项目里也不能启用、关闭或修改它。
6. Kimi Code 2.8.1 标签的 6,505 条仓库路径里没有任何含 sandbox、bwrap、landlock、seccomp 或 seatbelt 的路径，文件边界仍由 `[permission]` 规则与工具层路径策略提供；该标签 `docs/zh/configuration/config-files.md` 里出现的 `[environments.sandbox]` 只是远端环境启动器示例（`command = "sandbox"` 加 `args = ["ssh", "i-1234567890", "--"]`），把 `kimi exec-server` 送进第三方受管沙箱运行，不是 Kimi Code 自己施加的 OS 或容器边界。Qoder CLI 官方文档在核对日期已无独立 Sandbox 页，`https://docs.qoder.com/en/cli/sandbox` 返回 404，设置参考与 SDK 参考都没有 `sandbox.*` 键，本仓库此前记录的 SDK `sandbox.filesystem` 已无法从官方文档复核。
7. Codex 的 Linux 边界在 main 分支上继续收紧而官方文档没有跟进：`065e18b04021` 及其前三个提交把可写根按解析后的挂载点分组、父先于子只绑定一次，把可写别名下拼写的 deny 映射到物理路径并在只读挂载之后施加，在 bwrap 建完挂载后用非递归 `--remount-ro` 把合成根、最小 `/dev` 与适用的 WSL 掩码封成只读，并让 deny-read 路径穿过对沙箱内进程仍可写的符号链接时以 `CodexErr::Fatal` 失败关闭；官方 Sandboxing 页在 2026-11-28（514,274 字节）对 symlink、junction、remount 与 deny mask 的命中数仍为 0。这四项都只在 main，既不在稳定 `rust-v0.172.0`，也不在预发布 `rust-v0.174.0-alpha.9`。
8. Codex 官方页仍逐字写 “Codex uses the first `bwrap` executable it finds on `PATH`.”，而 main 分支的 `find_pre_sandbox_executable_in_path` 已先按文件系统策略筛掉位于非 root 进程 cwd 之下、当前用户可改写、或可通过改写某个父目录替换的候选，权限解析失败时整段查找直接跳过；「第一个」因此只在候选都通过策略筛选时成立。
9. Claude Code 的 `sandbox.allowNestedUserNamespaces` 此前只有 v2.1.305 更新日志一处一手来源（本字段旧条件项逐字写「核对日期的官方 Sandboxing 页全文没有该词、Settings 参考索引表也没有该行」），2026-11-28 已由 Sandboxing 页（111,994 字节，命中 5 处）与 Settings reference（463,611 字节，独立小节加索引行）双页记录，取值集合、默认值、可写作用域与最低版本四项都已确认，此前记为未确认的部分据此改写。

| 默认状态 | 版本库目录通常采用 `workspace-write` + `on-request`，非版本库目录通常采用 `read-only`；具体启动状态还受目录信任和配置影响。原生 Windows 上 agent 模式默认就用 Windows 沙箱阻止工作目录外写入；未选择模式时 Codex 优先 `elevated`，`elevated` 安装没完成会退回 `unelevated`。MXC 不自动启用：`features.prefer_mxc` 在功能登记册里是 `Stage::UnderDevelopment` 且 `default_enabled: false`，`windows.sandbox = "mxc"` 则是严格选择。 |
| 具体行为 | `read-only` 禁止一般写入，`workspace-write` 只写工作区与附加 writable roots，`danger-full-access` 移除沙箱；`.git`、`.agents`、`.codex` 等路径仍受保护。Linux 与 WSL2 的边界由 bubblewrap 构造：官方写 Codex 用 `PATH` 上找到的第一个 `bwrap`，找不到时退回一个捆绑 helper，而该 helper “requires support for unprivileged user namespace creation”；`codex-rs/linux-sandbox/src/bwrap.rs` 在两处参数构造里都显式加 `--unshare-user`，注释说明一是让容器内的 root 不必持有 ambient `CAP_SYS_ADMIN` 就能建其余命名空间，二是不依赖 bubblewrap 在调用方为 uid 0 时会跳过的自动启用行为，同时借 ptrace 权限检查挡住宿主 procfs 的 root/cwd/fd 链接；同一参数表还有 `--unshare-ipc`、`--cap-drop ALL` 与按选项决定的 `--unshare-pid`、`--unshare-net`、`--proc /proc`。main（提交 `065e18b04021008e2e7d504db8dc50275f589f73`，同文件 55,756 字节、1,436 行）上另有三层收紧：可写根先经 `canonical_target_if_symlinked_path` 解析再归入 `BTreeMap<PathBuf, Vec<&WritableRoot>>`，注释逐字为 “Path ordering visits parents before descendants. Bind each physical root once and apply its deny masks after every alias's read-only carveouts.”，拼写路径与物理路径不同时把落在别名下的 deny 条目映射进 `alias_denials`（注释逐字为 “A later bind may cover a denial spelled through this alias. Record its physical destination before emitting any of the writable grants.”）再并回 `unreadable_roots` 排序去重，`read_only_mounts` 与 `deferred_by_path` 都按 `path_depth` 排序；bwrap 建完挂载后对 `synthetic_roots` 逐个追加非递归 `--remount-ro`，注释逐字为 “Bubblewrap must finish creating mount points before sealing their backing directories. --remount-ro is nonrecursive, so writable child mounts survive.”，`append_empty_directory_args` 的 `--perms 555 --tmpfs`、`append_existing_unreadable_path_args` 与 `append_daemon_socket_masks`、WSLg 遮蔽的 `--perms 000 --tmpfs` 之后同样补 `--remount-ro`；`validate_unreadable_root` 在受保护路径穿过对沙箱内进程仍可写的符号链接时直接以 `CodexErr::Fatal` 失败，注释逐字为 “Deny-read masks must fail closed when the protected path crosses a symlink that remains writable to the sandboxed process. | 规则能力 | `approval_policy` 的官方取值只剩 `on-request`、`never` 与 granular 五键（`untrusted` 不支持、`on-failure` 已弃用，详见交互审批字段）；命令 Rules、MCP 注解、权限 Profile 与沙箱共同生效。企业可用 `requirements.toml` 的 `[windows] allowed_sandbox_implementations = ["elevated"]` 限定允许的原生沙箱实现，写两个值即两者都允许；配置与强制规则冲突时本地客户端回退到兼容值并通知用户。官方 Sandboxing 页把三种模式逐字记为 `read-only`（“The agent can inspect files, but it can't edit files or run commands without approval.”）、`workspace-write`（“The agent can read files, edit within the workspace, and run routine local commands inside that boundary.
