# 文件系统隔离

[返回权限与沙箱详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=security-filesystem)

> 核对日期：2026-10-23

## 定义

通过 OS、容器或进程级边界限制命令及其子进程能读取和写入的文件路径，而不仅是让模型遵守工具规则。

## 比较边界

### 本页包含

- OS 或容器隔离
- 可写根目录
- 受保护与禁止读取路径
- Linux 后端与用户命名空间前置条件
- 削弱或退出隔离的开关及其代价

### 本页不包含

- 只针对文件工具的 Allow/Deny
- Git Worktree 隔离
- 网络访问策略

## 跨产品事实

1. Claude Code、Codex 与 Qwen Code 都公开了本地 OS 级文件系统沙箱；三家的 Linux 边界都落在 bubblewrap 上，Qwen 另提供 Landlock 回退。
2. Codex 官方 Sandboxing 页把 Linux 与 WSL2 的实现写成 bubblewrap（macOS 是 Seatbelt），而不是本仓库此前记录的 Landlock；Landlock 与 seccomp 在 Codex 里是 `codex-linux-sandbox` crate 的实现依赖，`bwrap.rs` 才是构造边界的地方。原生 Windows 另有 `elevated`、`unelevated` 与 `mxc` 三种实现，由 `[windows] sandbox` 选择；`codex sandbox` 是 Stable 子命令，可用同一套策略手动跑一条命令。
3. Linux 用户命名空间是三家的共同前置条件：Claude Code 与 Codex 都在官方文档里写了 Ubuntu 24.04 及以后的 AppArmor 限制会让 bubblewrap 建不出用户命名空间，并各自给出 profile 文件（Claude 是 `/etc/apparmor.d/bwrap`，Codex 是 `/etc/apparmor.d/bwrap-userns-restrict`）与同一个 sysctl 键 `kernel.apparmor_restrict_unprivileged_userns`；Qwen Code 则直接要求 bwrap 装在 `/usr/bin/bwrap`。
4. 三家都提供削弱或退出文件系统隔离的开关并写明代价：Claude Code 的 `sandbox.enableWeakerNestedSandbox`（改挂容器已有 `/proc`，官方写 “considerably weakens security”）与 v2.1.305 新增的 `sandbox.allowNestedUserNamespaces`（官方更新日志写 “this lets them get around the sandbox's file protections”）、Codex 的 `danger-full-access`、Qwen Code 的 `filesystem: "workspace-write"` 与 Landlock 后端的 `partial` enforcement。
5. Qwen Code 自 v0.24.4 起把 Linux 沙箱从「整个 CLI 跑在 bwrap 里」改成「只有工具执行跑在 bwrap 或 Landlock 里」，策略键 `tools.executionSandbox` 由运算符（User 或 System 设置）所有，Workspace 设置即使在受信任项目里也不能启用、关闭或修改它。
6. Kimi Code 2.3.0 标签的整棵仓库树里没有任何 sandbox、bwrap、landlock、seccomp 或 seatbelt 路径，文件边界仍由 `[permission]` 规则与工具层路径策略提供；Qoder CLI 官方文档在核对日期已无独立 Sandbox 页，`https://docs.qoder.com/en/cli/sandbox` 返回 404，设置参考与 SDK 参考都没有 `sandbox.*` 键，本仓库此前记录的 SDK `sandbox.filesystem` 已无法从官方文档复核。

### Codex

| 字段 | 记录 |
| --- | --- |
| 矩阵结论 | `read-only` · `workspace-write` · `danger-full-access`；条件：Linux 与 WSL2 用 bubblewrap（`PATH` 上的 `bwrap`，否则退回需要非特权用户命名空间的捆绑 helper），原生 Windows 另有 `[windows] sandbox` 的 `elevated`/`unelevated`/`mxc` 后端 |
| 入口与切换 | `/permissions` 与权限选择器控制当前会话；CLI 可传 `--sandbox`、`--ask-for-approval`，持久配置写入 `config.toml`。原生 Windows 沙箱实现由 `config.toml` 的 `[windows] sandbox = "elevated"` 或 `"unelevated"` 选择，TUI 的 `/setup-default-sandbox`（源码描述 “set up elevated agent sandbox”）负责 elevated 安装；`codex sandbox` 子命令（官方标注 Stable，Windows 形式的 `COMMAND...` 说明为 “Command to execute under the native Windows sandbox. Provide the executable after `--`.”）可用 `-P/--permission-profile`、`-C/--cd`、`-c/--config`、`-p/--profile`、`--include-managed-config` 以真实执行相同的策略跑一条命令，MXC 也走同一准备路径。官方 Windows sandbox 页要求用 `/sandbox-add-read-dir C:\absolute\directory\path` 给沙箱授予某个已存在绝对目录的读权限（仅当前会话），但 CLI TUI 的 Slash 命令枚举在 rust-v0.154.0（提交 `6b9826e3aa83`）仍有该命令、自 rust-v0.155.0（提交 `f0a1b8f0849d`）起已无，官方 Slash 命令参考页也未列出，CLI 侧入口记为未确认。Linux 与 WSL2 上没有开关命令，边界取决于 `PATH` 上是否有 `bwrap`。 |
| 默认状态 | 版本库目录通常采用 `workspace-write` + `on-request`，非版本库目录通常采用 `read-only`；具体启动状态还受目录信任和配置影响。原生 Windows 上 agent 模式默认就用 Windows 沙箱阻止工作目录外写入；未选择模式时 Codex 优先 `elevated`，`elevated` 安装没完成会退回 `unelevated`。MXC 不自动启用：`features.prefer_mxc` 在功能登记册里是 `Stage::UnderDevelopment` 且 `default_enabled: false`，`windows.sandbox = "mxc"` 则是严格选择。 |
| 具体行为 | `read-only` 禁止一般写入，`workspace-write` 只写工作区与附加 writable roots，`danger-full-access` 移除沙箱；`.git`、`.agents`、`.codex` 等路径仍受保护。Linux 与 WSL2 的边界由 bubblewrap 构造：官方写 Codex 用 `PATH` 上找到的第一个 `bwrap`，找不到时退回一个捆绑 helper，而该 helper “requires support for unprivileged user namespace creation”；`codex-rs/linux-sandbox/src/bwrap.rs` 在两处参数构造里都显式加 `--unshare-user`，注释说明一是让容器内的 root 不必持有 ambient `CAP_SYS_ADMIN` 就能建其余命名空间，二是不依赖 bubblewrap 在调用方为 uid 0 时会跳过的自动启用行为，同时借 ptrace 权限检查挡住宿主 procfs 的 root/cwd/fd 链接；同一参数表还有 `--unshare-ipc`、`--cap-drop ALL` 与按选项决定的 `--unshare-pid`、`--unshare-net`、`--proc /proc`。原生 Windows 上再由 `[windows] sandbox` 选实现：`elevated` 用专用低权限沙箱用户加文件系统权限边界，`unelevated` 用当前用户派生的受限 Windows 令牌加 ACL 边界，`mxc` 经 Microsoft MXC `BaseContainerRunner` 直接包裹命令，不改主机 ACL、不创建沙箱用户、不跑安装也不请求提权。MXC 的文件系统权限取自规范化的 Codex 权限 Profile（含受保护元数据豁免），deny glob 沿用既有 Windows 沙箱解析器在启动前展开为具体路径并保持相同的快照语义与扫描上限；Windows 卷根授权不递归，只授卷根与其直接子项，命令运行中新建或新挂载的目录不自动获得授权。 |
| 规则能力 | `approval_policy` 支持 `untrusted`、`on-request`、`never` 和 granular 分类策略；命令 Rules、MCP 注解、权限 Profile 与沙箱共同生效。企业可用 `requirements.toml` 的 `[windows] allowed_sandbox_implementations = ["elevated"]` 限定允许的原生沙箱实现，写两个值即两者都允许；配置与强制规则冲突时本地客户端回退到兼容值并通知用户。官方 Sandboxing 页把三种模式逐字记为 `read-only`（“The agent can inspect files, but it can't edit files or run commands without approval.”）、`workspace-write`（“The agent can read files, edit within the workspace, and run routine local commands inside that boundary. | 隔离边界 | 本地 CLI/IDE 使用 OS 级沙箱，官方逐字为 “Codex uses platform-native enforcement on each OS. | 默认状态 | `tools.approvalMode` 当前默认值为 `auto`；`security.folderTrust.enabled` 默认关闭。两层沙箱都默认关闭：`tools.executionSandbox` 是必填 `filesystem` 与 `network`、可选 `backend`（默认 `auto`）的完整策略对象，不写就不启用；整 CLI 的 `tools.sandbox` 默认 `undefined`，且官方逐字写 “**`--yolo` does _not_ automatically enable a sandbox.**”。工具执行沙箱只支持 Linux，`execution-sandbox-config.ts` 在不满足时抛 “tools.executionSandbox requires Linux with a compatible bwrap or Landlock backend.”。 |
| 具体行为 | 两层彼此独立。其一是 Linux 工具执行沙箱 `tools.executionSandbox`：只有命令及其子进程进边界，CLI 本体、模型传输、认证与会话存储留在宿主；`filesystem: "read-only"` 拒绝工作区写入，`"workspace-write"` 允许在当前规范化工作区内写入，每条命令另有私有 scratch 空间（经 `TMPDIR`/`TMP`/`TEMP` 暴露），普通 `includeDirectories` 不授予写权限；`backend: "auto"` 先试 bwrap，bwrap 不可用且 `network` 为 `open` 时可用内核 Landlock ABI 3 及以上的捆绑 Landlock helper，写 `bwrap` 或 `landlock` 则严格要求该实现。Landlock 后端报 `partial` enforcement：只限制 pathname 读写与目录变更，不创建 PID 或网络命名空间，也不能限制 `chmod`、`chown`、扩展属性与时间戳等全部元数据操作，可写设备面更窄（允许写 `/dev/null`，但不建 bwrap 的私有 `/dev` 与 `/proc`，写 `/dev/full`、`/dev/tty` 与在 `/dev/shm` 建文件被拒）。其二是把整个 CLI 跑进去的旧方法：macOS Seatbelt（`sandbox-exec`，默认 profile `permissive-open`，限制项目目录外写入）与跨平台 Docker/Podman 容器（挂载工作区和 `~/.qwen`）。 |
| 规则能力 | `permissions.deny` > `ask` > `allow`；规则可限制 Shell、Read、Edit、WebFetch、MCP 等。`tools.disabled` 在注册阶段直接移除工具。工具执行沙箱与规则是两层：官方写 “Approval and YOLO do not expand the filesystem or network policy.”，即审批模式与 YOLO 都不能放宽该策略；策略本身只认字面量，`parseExecutionSandboxSettings` 在出现 `backend`/`filesystem`/`network` 以外的键、缺 `filesystem` 或 `network`、取值不在枚举内或不是字符串时抛 `InvalidExecutionSandboxConfigError`（继承 `FatalConfigError`），消息为 “tools.executionSandbox requires literal filesystem (read-only \| workspace-write), network (open \| closed), and optional backend (auto \| bwrap \| landlock). | 隔离边界 | 工具执行沙箱覆盖 Shell、终端 `!`、提示词 shell 插值、Monitor、Read/Write/Edit 与受支持的嵌套 in-process Agent/Code Mode 调用，它们共用同一运行时策略；CLI 本体、模型传输、认证与会话存储留在宿主。读取仍然宽：官方写该模式 “does not hide host secrets or promise to isolate pathname Unix sockets and host services”。Landlock 后端另报 `partial` enforcement——不创建 PID 或网络命名空间、不能限制 `chmod`/`chown`/扩展属性/时间戳等全部元数据操作、命令能看到宿主进程并用宿主网络，分离的子孙进程保留文件系统限制但没有 bwrap 的 PID-namespace 生命周期边界；启动时的 Landlock 策略探测需要 `/usr/bin/true`，缺它的宿主即使内核支持也会探测失败。链接的 Git worktree 只对准入的工作区有写权限，工作区外的 Git common-directory 与 worktree 元数据保持只读。整 CLI 方法的边界则是 Seatbelt Profile 或容器挂载（工作区与 `~/.qwen`）。 |
