# 审批自动审查

[返回权限与沙箱详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=security-auto-review)

> 核对日期：2026-10-26

## 定义

把原本需要用户确认的越界或高风险操作交给产品内置的分类器或审查代理自动裁决；裁决可以放行也可以拒绝，与全部放行的 bypass 不同。

## 权限结论

| 产品 | 结论 | 证据状态 |
| --- | --- | --- |
| Claude Code | `auto` 权限模式 · classifier 审查 · `CLAUDE_CODE_AUTO_MODE_MODEL` 指定客户端分类器模型 | 官方确认 |
| Codex | `approvals_reviewer = "auto_review"` · `--approve-for-me` | 官方确认 |
| Qwen Code | Auto 审批模式 · LLM 分类器 | 官方确认 |
| Kimi Code | 无同类机制；`/auto` 为全部审批自动放行 | 官方确认 |
| Qoder CLI | `auto` 权限模式 · AI 分类器 | 官方确认 |

## 比较边界

### 本页包含

- 分类器或审查代理裁决审批请求
- 放行与拒绝决策
- 审查策略、提示与熔断配置

### 本页不包含

- 全部放行的 YOLO/Bypass 模式
- 静态 Allow/Deny 规则
- OS 沙箱边界本身

## 跨产品事实

1. Claude Code、Codex、Qwen Code 与 Qoder CLI 都提供基于分类器或审查代理的自动审查；Kimi Code 无同类机制，其 `/auto` 是全部审批自动放行的无人值守模式。
2. 自动审查不是权限放大：Codex 明确 auto-review 只更换审批请求的裁决者、不放宽沙箱边界；Claude Code 的 auto 模式仍会被 classifier 阻断高风险操作。
3. 四家都为连续拒绝设熔断，但阈值与回退形式各不相同：Claude Code 连续 3 次或累计 20 次阻断后暂停 auto 并回退询问（官方明写阈值不可配置）；Codex 同一 turn 内连续 3 次或最近 50 次审查的滚动窗口内 10 次拒绝即中断该 turn，源码里另有一组阈值为 1 与 1 的 Cyber 变体；Qwen Code 连续 3 次阻断、连续 2 次不可用或会话累计 20 次拒绝后只把当次调用降级为人工审批、会话仍留在 Auto；Qoder CLI 连续阻断达到上限后让下一个动作变成授权提示，官方没有公布数值上限。
4. 裁决用哪个模型只有 Qwen Code 给了用户可改的入口，官方逐字为 “The classifier uses your configured fast model (`/model --fast`). If no fast model is configured, the main session model is used instead.”；Claude Code 默认用 Claude Sonnet 5 而不是 `/model` 选的模型，v2.1.302 起 `CLAUDE_CODE_AUTO_MODE_MODEL` 可指定客户端分类器模型；Codex 的审查模型取自 `ModelInfo` 的 `auto_review_model_override`（后端 `/models` 接口返回的模型元数据）与 Provider 首选审查模型，配置参考里没有选审查模型的键；Qoder CLI 官方只在 1.1.63 发布说明里写 “Approval requests in Auto permission mode now follow the BYOK model”，文档不点名模型也没有对应配置键；Kimi Code 无分类器。
5. Qwen Code 与 Qoder CLI 都把裁决拆成两阶段来压低延迟：Qwen 的 Stage 1 快通道只输出 `{ shouldBlock }`（约 300 毫秒），只有 Stage 1 判阻断时才跑 Stage 2 思考审查，后者可以把阻断降级为放行并产出用户可见的 `reason`；Qoder 官方写第一阶段是只能放行的快速通道、未放行的动作交给唯一能判定阻断的第二阶段，因此不同工具调用的裁决延迟不同。Claude Code 与 Codex 的官方文档没有公布同类分阶段结构。
6. 只有 Claude Code 把分类器的执行位置分成客户端与服务端两条路径并公布计费差异：服务端审查作为会话自身模型请求的一部分完成、官方写 “at no charge”，`CLAUDE_CODE_AUTO_MODE_SERVER=0` 或网关丢掉审查字段时回退到 Claude Code 自己发的 classifier 请求，这些请求 “count toward your token usage”。

| 规则能力 | 分类器内部四层优先级、先命中先生效：`autoMode.hard_deny` 无条件阻断，用户意图与 `allow` 例外都不适用；`autoMode.soft_deny` 次之，可被用户意图与 `allow` 例外覆盖；`autoMode.allow` 作为匹配 `soft_deny` 规则的例外；最后是显式用户意图——用户消息直接且具体描述了 Claude 正要执行的动作时，即使命中 `soft_deny` 也放行。四张表都是自然语言散文条目而不是正则或工具模式，分类器按自然语言规则读。数组里写字面量 `"$defaults"` 就把内置规则拼在该位置，自定义规则可以放前也可以放后并继续跟随版本更新；`environment`、`allow`、`soft_deny`、`hard_deny` 任一节不设 `"$defaults"` 即整节替换掉内置列表。`autoMode.environment` 告诉分类器哪些仓库、桶与域名可信，分类器用它判断「外部」是什么意思，未列出的目的地都算潜在外泄目标；默认只信工作目录与当前仓库配置的 remote，其余每个信任槽默认 `None configured`。要按工具模式做硬阻断得用 `permissions.deny`（在分类器之前生效、分类器与用户意图都不能覆盖），按命令内容匹配的 `permissions.ask` 规则同样先于分类器强制弹审批。`autoMode.classifyAllShell: true` 在 auto 模式期间挂起全部 Bash 与 PowerShell allow 规则、让每条 shell 命令都过分类器（关键路径删除除外），代价是延迟与每条命令一次分类器调用，且只在 auto 模式期间生效、其他模式下 allow 规则照常。`useAutoModeDuringPlan` 默认开启，Plan 模式下 shell 命令（关键路径删除除外）由分类器审查而不是弹审批，批准的执行、拒绝的阻断；auto 模式不可用或该键关闭时，内置只读集合之外的命令弹审批。交互终端且 bypassPermissions 可用的会话里，planning 命令既不过分类器也不弹审批。分类器读的是 Claude 自己加载的同一份 CLAUDE.md，因此项目 CLAUDE.md 里写 “never force push” 会同时约束 Claude 与分类器；分类器还把对话中声明的边界当作阻断信号，但压缩掉声明该边界的消息后边界可能丢失。v2.1.198 起对同一主机和端口复用网络判定。 |

| 矩阵结论 | `auto` 权限模式 · AI 分类器 |
| 入口与切换 | `--permission-mode auto`、`Shift+Tab` 循环到 `auto`，或 `general.defaultPermissionMode` 设为 `auto`；`/goal set <objective>` 会自动切换到 `auto`。 |
| 默认状态 | 默认权限模式为 `default`；`auto` 模式下没有确认提示。`general.defaultPermissionMode` 为 enum、默认 `default`、取值 `default`/`accept_edits`/`plan`/`auto`/`bypass_permissions`/`dont_ask`、改动不需要重启。顶层 `autoMode` 为 object、默认 `{}`、改动不需要重启，官方设置参考逐字为 “Auto mode classifier soft-steering rules (`allow`/`soft_deny`/`environment`). Top-level key, read only from user-level and local configurations.”。分类器用哪个模型官方文档从不点名，只写 “the AI classifier”；发布说明 1.1.63（2026-09-24）逐字为 “Approval requests in Auto permission mode now follow the BYOK model”，即跟随用户配置的 BYOK 模型，且没有任何配置键可以单独选它。官方权限页写 “When no classifier model is available, switching into `auto` mode is refused.”，即拿不到分类器模型时连切进 `auto` 都会被拒绝。 |
| 具体行为 | `auto` 模式零确认提示：官方模式表把 `auto` 的行为写成 “Authorization is decided by the agent.”，与 `bypass_permissions`（“Skips approval prompts.”）和 `dont_ask`（“Never prompts. Any action that would normally ask is denied instead.”）并列。分类器分两阶段，官方逐字为 “The classifier runs in two stages. The first stage is a fast pass that can only approve; actions it does not approve are submitted to the second stage, which is the only stage that can conclude an action must be blocked. Adjudication latency therefore differs between tool calls.”。三类动作不经分类器裁决：只读工具（文件读取、搜索、glob）按工具名放行且不评估目标路径，因此工作目录外的路径也一并放行；工作目录内以及用 `/add-dir` 加进来的目录内的写入与编辑直接放行；其余动作全部提交分类器，包括写到这些目录之外。危险 shell 命令与受保护路径直接拒绝。`autoMode.allow`、`autoMode.soft_deny`、`autoMode.environment` 以自然语言注入分类器提示，官方明写 “These rules are **soft guidance** — injected into the classifier prompt as reference; the final decision is still made by the AI classifier.”。用户级 `AGENTS.md` 也被注入分类器上下文，作为「本次会话被要求做什么」的证据，只读用户级那一份，且其内容只描述意图、不构成授权——与安全规则冲突时它所看似认可的动作仍被阻断。 |
| 规则能力 | `autoMode.allow` 描述分类器倾向放行的操作，`autoMode.soft_deny` 描述倾向拒绝的操作（注意是 snake_case，与 Qwen Code 的 `softDeny` 写法不同，且 Qoder 没有对应的 hardDeny 键），`autoMode.environment` 提供环境上下文；官方逐字为 “These rules are **soft guidance** — injected into the classifier prompt as reference; the final decision is still made by the AI classifier.”。作用域限制逐字为 “For security, `autoMode` configuration is read only from your own global settings. Workspace files are ignored, including the local settings file: any file under the workspace can arrive with a checkout, and a repository able to add classifier `allow` entries could bias auto mode toward approving dangerous actions.”；官方设置参考页把同一个键写成 “read only from user-level and local configurations”，与权限页的「连 local settings 也忽略」相互矛盾，两处在核对日期并存、未由官方统一。用户级 `AGENTS.md` 也注入分类器上下文，官方逐字为 “The user-level `AGENTS.md` is also injected into the classifier context, as evidence of what the session was asked to accomplish. Only the user-level file is read. Its content describes intent and does not constitute authorization: an action it appears to sanction is still blocked when it conflicts with a safety rule.”。 |
| 隔离边界 | 失败关闭：官方逐字为 “When the classifier is unreachable or returns no usable verdict, the action is denied rather than prompted; the message states that this is not a safety verdict on the action, the same action may be retried, and read-only tools are unaffected.”。熔断逐字为 “When consecutive block verdicts reach the limit, the circuit breaker trips: the next action becomes an authorization prompt carrying the limit warning and the most recent block reason. The mode itself remains available, and the count clears once an action is approved.”，并写 “The circuit breaker is the only condition under which a permission verdict produces an authorization prompt in `auto` mode.”；官方没有公布这个数值上限。不经分类器裁决的三类动作见「具体行为」；此外 AskUserQuestion、进入与退出 Plan 以及「会话长到分类器读不完自己的上下文」仍会产生非裁决类的授权提示。`autoMode` 配置只从受信任来源读取，项目 settings 被排除以防恶意提权。 |
