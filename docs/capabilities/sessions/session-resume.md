# 恢复会话

[返回会话与上下文详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=session-resume)

> 核对日期：2026-10-16

## 定义

退出后重新载入已有会话，使历史消息、工具结果和产品明确保存的会话状态继续参与后续对话。

## 比较边界

### 本页包含

- 交互式选择历史会话
- 按最近会话或会话 ID 恢复
- 恢复后重新加载的状态
- 恢复时还原或丢弃的权限模式、审批放行与网络授权

### 本页不包含

- 跨会话自动记忆
- 把当前会话复制成新 ID
- 单纯查看终端输入历史

## 跨产品事实

1. 五家都提供恢复入口，但会话选择范围分别按项目、工作目录、Worktree 或 SDK 参数组织。
2. “恢复时还原哪些权限状态”是本页差异最大的一项，而且同一产品在不同 Surface 上结论可以相反：Claude Code 用五条恢复路径加八行矩阵规定恢复哪种权限模式（`bypassPermissions` 不恢复、`auto` 要账号仍合格、plan 在非交互与 VS Code 路径需 v2.1.246 及以上且受五个条件与 deny 规则约束）；Codex 自 rust-v0.163.0 起从线程自有快照还原 `approval_policy`、`approvals_reviewer`、权限档与网络域名授权，且套用时机提前到网络代理初始化之前，但 `codex exec resume` 因为自己总是显式带上这些字段而不回落保存值；Kimi Code 靠 durable 事件重放全 Surface 还原 `permissionMode` 与会话级放行 pattern，可用 `--auto`/`--yolo`/`--plan` 事后覆盖；Qwen Code 的交互式 `/resume` 与 Headless 路径都不还原审批模式，只有 daemon/ACP 冷加载会用转录里的 `system/session_approval_mode` 记录还原；Qoder CLI 只说明会话内临时放行规则进程退出即丢，冷启动恢复是否读回保存的权限模式记为未确认。
3. “会话内批准”与“写盘批准”是两种东西，只有后者天然跨会话：Claude Code 的 Bash 命令、WebFetch 域名与 WebSearch 选 “Yes, and don't ask again” 会写进仓库根的 `.claude/settings.local.json`，文件修改批准只到会话结束，`--fork-session` 到新进程不带会话内放行；Qoder CLI 的 Layer 6（`/allow`、`/deny`）写进 `settings.local.json`，Layer 7（“Allow for this session”）进程退出即丢；Codex 记住的网络域名规则写进 `$CODEX_HOME/rules/default.rules` 并在冷恢复时带回代理允许清单；Qwen Code 的会话级 allow 规则是内存态，`startNewSession()` 在 `/resume` 走的同一条路径上直接 `clearSessionAllowRules()`；Kimi Code 是例外——`permission.record_approval_result` 带 `durable` 因而会话级放行 pattern 会被重放回来，但 `permission.rules.add` 不带 `durable`，运行时规则表重放后是空的。
4. 恢复历史不等于恢复所有启动参数：Claude Code 明列 `--mcp-config`、`--settings`、`--plugin-dir`、`--fallback-model` 与 `--add-dir` 需要重传；Codex 只把本次启动命令行里出现的键当覆盖，`config.toml` 的默认值不阻止还原；Qwen Code 的 Worktree 绑定靠 `<sessionId>.worktree.json` sidecar，且 `--worktree` 与 `--resume` 同用时 Worktree 胜出。
5. 托管或组织策略在恢复路径上仍然最高：Codex 的 `requirements.toml`（`allowed_permission_profiles`、`allowed_sandbox_modes`、`deny_read`）会否决或收窄还原出来的权限档，Claude Code 的 managed settings 压过自己的设置文件与 `--settings`，Qoder CLI 的 `allowManagedPermissionRulesOnly` 与目录未受信任时的强制 `default` 回落同理。
6. 会话文件通常包含提示词、工具结果和本地路径，分享前需要按敏感数据处理。

| 具体行为 | 把新提示接在同一线程上继续。自 rust-v0.163.0 起冷恢复还会还原线程自己保存的权限状态：app-server 在 rollout 里倒序找最后一条 `thread_id` 等于被恢复会话的 `ThreadSettingsApplied` 事件作为权威快照（源码注释 “Copied or referenced history can contain another thread's settings. | 状态范围 | `codex resume --last` 只在当前工作目录范围内选最近会话，加 `--all` 才跨目录（官方页 “codex resume scopes --last to the current working directory unless you pass --all. It accepts model and sandbox overrides, but not --worktree.”）。恢复后用哪个工作目录由 `tui.resume_cwd` 决定：`session` 用会话记录的目录、`current` 留在当前目录、未设置且两者不同时弹出选择（官方配置参考 “Working directory to use when resuming or forking a session. | 保存与保留 | 会话记录保存在 `$CODEX_HOME/sessions`（默认 `~/.codex/sessions`），归档会话在 `$CODEX_HOME/archived_sessions`；官方故障排查页给出这两个目录，但当前命令页未承诺固定清理周期。恢复要还原的权限状态就写在这些 rollout 里的 `ThreadSettingsApplied` 事件中；官方网络授权回归测试把托管域名放在 `$CODEX_HOME/requirements.toml` 的 `[experimental_network]`，把记住的域名规则放在 `$CODEX_HOME/rules/default.rules`，写法为 `network_rule(host="127.0.0.3", protocol="http", decision="allow")`。 |
| 适用界面 | 本页区分交互式 Codex 与 `codex exec`。交互式 `codex resume`/`/resume` 走 app-server 的 `thread/resume`，上述还原生效；TUI 侧 `resume_permissions.rs` 的模块注释为 “Tracks direct launch permission choices separately from configuration defaults. Let the server resolve its defaults or restore the saved roots, then adopt the roots in its response.” |
| 条件与边界 | 还原有明确排除项：请求带 `sandbox_mode`、`permission_profile`、`default_permissions` 覆盖，或 `config` 覆盖表含 `sandbox_mode`/`default_permissions`/`sandbox_workspace_write`（含子键）时不还原未命名权限档；`requirements.toml` 设了 `allowed_permission_profiles` 时也不还原；`PermissionProfile::External`（执行器自有强制）与已物化的文件系统读授权被拒绝，源码注释为 “Executor-owned enforcement and materialized grants are not portable thread defaults.”；托管 `deny_read` 通过 `preserve_deny_read_restrictions_from` 保留，还原后的档还要再过 `permission_profile_satisfies_requirements`（只查 `allowed_sandbox_modes` 与 `deny_read`）。官方 Linux 集成测试 `cold_resume_restores_live_proxy_grants_and_persists_new_approvals` 在把 `default_permissions` 改成 `:danger-full-access` 后恢复只读线程，断言结果仍是 `ReadOnly { network_access: false }` 加 `AskForApproval::OnRequest`、已记住的域名 0 次审批、新域名 1 次审批并经 `ApplyNetworkPolicyAmendment` 持久化后复用 0 次、探测输出含 “proxied request succeeded; direct access blocked”。模型另有三态 `ResumeModelSettings`：`OverrideFromCurrentConfig` 把当前配置的模型、Provider 与推理强度作为显式覆盖发出，`RestoreFromThread` 省略这些覆盖 “so app-server restores the settings saved with the thread”，`PreserveExistingThread` 只重新接上已加载线程。`--worktree` 不能用于恢复，`codex exec resume --worktree` 报 “`--worktree` cannot resume an existing session; use `codex exec fork --worktree`”。 |
