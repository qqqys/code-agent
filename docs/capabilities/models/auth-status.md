# 认证状态检查

[返回模型与认证详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=auth-status)

> 核对日期：2026-11-05

## 定义

显示当前账号、认证方式、Provider 配置或运行诊断状态，并区分专用认证状态入口、通用运行状态页里的认证行、安装诊断命令里的认证检查项，以及凭据到期的提示与机器可读输出。

## 比较边界

### 本页包含

- 会话内与非交互的认证／登录状态命令
- 运行状态页里的账号、Provider 与凭据行
- 安装诊断命令中与认证直接相关的检查项
- 凭据到期与即将到期的提示
- 认证状态的机器可读输出与退出码

### 本页不包含

- 登录、登出与凭据存储本身（见关联能力）
- 组织级 SSO 与受管策略（见关联能力）
- MCP Server 的 OAuth 授权状态
- 模型调用是否成功的实际验证
- 只显示版本号而不涉及认证的行

## 跨产品事实

1. 不进入会话就能读认证状态的只有两家：Claude 的 `claude auth status` 输出 JSON（官方 CLI 参考写 “Exits with code 0 if logged in, 1 if not.”，`authMethod` 取值枚举为 `none`、`claude.ai`、`oauth_token`、`api_key`、`api_key_helper`、`third_party`，另有 v2.1.268 起的 `configDirectory`），Codex 的 `codex login status` 把结果写到 **stderr** 而不是 stdout、按 `AuthMode` 各打印一行、有凭据退出 0 而 `Not logged in` 退出 1，且 `LoginCommand` 没有任何输出格式旗标。Qwen 的独立 `qwen auth` CLI 已被移除、`qwen auth status` 只打印迁移通知；Kimi 的 `kimi login` 逐字为 “该子命令没有任何 flag”；Qoder 有 `qoder status`，但官方描述只有 “Display session status.”。
2. 凭据到期只有 Claude 报告，而且三个 Surface 用两个阈值：交互会话在到期前 3 天于启动时打印 `Your login expires in 3 days · run /login to renew`（官方 Authentication 页），`claude -p` 的文本输出从 v2.1.318 起在到期前 10 天打一行 stderr 警告（只有更新日志一处记录），机器可读侧 v2.1.318 给 `claude auth status` 加 `loginExpiresAt`、给 `claude -p` 的 JSON 结果加 `credential_expires_at`。到期本身不阻断，官方写 “The warning is informational and never blocks a request: authentication keeps working until the login actually expires.”
3. 其余四家都没有面向用户的凭据到期显示：Codex 官方 Authentication 页唯一相关的句子是自动刷新（“Codex refreshes tokens automatically during use before they expire”），而 `auth.json` 的 `TokenData` 记录只有 `id_token`、`access_token`、`refresh_token`、`oauth_provenance`、`login_owner_id` 与 `account_id`、没有任何到期字段；Qwen 的 `/doctor` 只判 `configured`／`invalid`／`not configured`；Kimi 的 CLI 与 TUI 都不显示到期，只有 `kimi web` 服务 API 的 `GET /api/v1/auth` 会报托管供应商登录态，而它的唯一实现只产出 `authenticated` 与 `unauthenticated` 两个值——文档与 schema 列出的 `expired`／`revoked` 在 2.5.1 运行时不可达（设备码流程的 `expires_in`／`expires_at` 是授权时限、不是凭据有效期）；Qoder 全站 185 条 Release Notes 里唯一的到期日期是 CLI 0.1.18（December 23, 2025）的 “Added plan expiration date to /usage command”，那是套餐到期日、落在 `/usage` 而不是 `/status`。
4. `/status` 在五家都是「运行状态页」而不是认证状态命令：Claude 的 `/status` 打开 Settings 界面的 Status 页签（与 `/config` 是同一对话框的不同页签），认证相关的行有 `Login method`、替代它的 `Profile`、`Organization`、`Email`、`API key`、`Auth token`、`apiKeyHelper` 与 `Login`；Codex 的 `/status` 官方描述是 “Display session configuration and token usage.”、检查项写的是模型、审批策略、可写根与 token 用量，但源码里它还渲染 `Account` 行（ChatGPT 登录为 `email (plan)`、API Key 登录为 `API key configured (run codex login to use ChatGPT)`）与条件性的 `ChatGPT workspace` 行，且 ChatGPT 订阅账号下会隐藏 `Token usage` 行；Qwen 的 `/status`（别名 `about`）描述为 “Display version information”，但**在 `-p` 与 ACP 模式下会打印一行 `Auth: <authType>`**，交互面板的十三项里另有 `Auth` 与 `Base URL` 两行（OAuth 登录时 Base URL 刻意留空）；Kimi 的 `/status` 由 `buildStatusReportLines` 渲染，行集合里没有任何账号、登录、供应商或凭据行；Qoder 的 `/status` 是 “View account and session status.”，Quick Start 写成 “View version, model, account, and API Connectivity”。
5. 安装诊断与认证检查在五家不是一回事：Claude 的 `/doctor` 是 bundled Skill（别名 `/checkup`），官方列出的五类检查项是 Installation health、Extensions、`CLAUDE.md` files、Permissions 与 Usage，**没有一类检查凭据**，检查凭据存储可写性的是 shell 侧的 `claude doctor`（Keychain 拒绝写入时报告以 `macOS Keychain is not writable` 开头的警告）；Codex 的 `codex doctor` 官方描述明确把 authentication 列入检查范围，源码里对应 id 为 `auth.credentials`、分组为 `auth` 的检查行；Qwen 的 `/doctor` 有 `Authentication` 组，`checkAuth` 给出三种结果并附 Provider、Base URL、Model 与 API key 是否已设；Kimi 的 `kimi doctor` 逐字只 “校验 `config.toml` 和 `tui.toml`”，与认证无关；Qoder 没有任何 `/doctor` 一类命令，登录问题放在文档站单独的 “Sign-in and Authentication Issues” 排障页。
6. 机器可读口径各不相同：Claude 有 `claude auth status` 的 JSON 与 `claude -p` 的 JSON 结果两条路；Codex 的 `codex login status` 只有 stderr 文本加退出码，机器可读报告要靠 `codex doctor --json`（“Emit a redacted machine-readable report.”）；Qwen 的 `/status` 在 `-p` 与 ACP 下输出固定行文本，而 `/doctor` 在非交互模式下整个报告直接以 `JSON.stringify({ checks, summary }, null, 2)` 返回、不需要任何旗标；Kimi 的机器可读认证状态只在 `kimi web` 服务 API 上，官方并写明 `GET /api/v1/auth` “不做凭据校验，因此此后的对话请求仍可能以 `40111` / `40112` 失败”；Qoder 的 `qoder status` 没有 `--json`，脚本化认证靠 PAT 与实际请求结果。
7. 五家的状态入口都只读、不改凭据，但脱敏程度不同：Codex 的 API Key 经 `safe_format_key` 只保留前 8 与后 5 字符（长度 ≤13 时整体替换为 `***`），Qwen 的 `/config` 输出对 API Key、token 与 base URL 打码，Kimi 的 `/logout` 选择列表实际上就是当前凭据清单（无凭据时打印 `Nothing to logout.`），Claude 的 `/status` 在登录与 API Key 同时存在时会标出未被使用的那一个、`apiKeyHelper` 行还会显示脚本的退出码与错误输出，Qoder 官方没有公开任何打印 PAT 的命令。
