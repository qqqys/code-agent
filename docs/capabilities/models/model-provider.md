# Provider 类型

[返回模型与认证详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=model-provider)

## 定义

定义 CLI 能直接连接的模型服务类型，包括厂商托管服务、云平台、本地运行时和自定义 Provider。

## 比较边界

### 本页包含

- 公开支持的 Provider 类型
- 协议适配器与本地运行时
- Provider 选择和配置入口

### 本页不包含

- 模型质量与价格
- 未在公开资料列出的私有适配
- 仅靠外部网关完成的透明转发

## 跨产品事实

1. 五家都区分「厂商托管目录」与「自带 Key」两条路，但入口形状不同：Claude Code 与 Codex 用配置键和环境变量声明 Provider，Qwen Code 与 Kimi Code 用 `/auth`、`/provider` 向导加配置文件，Qoder CLI 只允许从 `/model` 的 Custom 向导添加。
2. 只有 Qwen Code 与 Kimi Code 把「导入第三方 Provider」做成产品能力：Qwen 在源码里内置 15 个预设（`ALL_PROVIDERS` 的显示顺序，按 `uiGroup` 分 qwencloud、alibaba、third-party 三组），Kimi 从公开 models.dev 目录或自定义 registry `api.json` 导入、目录不可达时回退内置快照。
3. 协议边界不同：Codex 的自定义 Provider 只接受 `wire_api = "responses"`，官方 Models 页写明当前版本不支持 `wire_api = "chat"` 或仅 Chat Completions 的端点；Qwen 的 `openai` 协议按每条模型的 `wireApi` 在 `chat-completions` 与 `responses` 之间选；Kimi 把两种 OpenAI 协议拆成 `openai` 与 `openai_responses` 两个 `type`；Claude Code 只在 Messages 协议内换部署位置，不做任意协议适配。
4. 云平台 Provider 的覆盖不同：Claude Code 有 Amazon Bedrock（Invoke API 或 Mantle 端点）、Claude Platform on AWS、Google Cloud's Agent Platform（原 Vertex AI）与 Microsoft Foundry 四个云部署；Codex 内置 `amazon-bedrock` 一个云 Provider；Qwen 的 `vertex-ai` 与 Kimi 的 `vertexai` 都走 Google ADC；Qoder 公开文档没有任何云厂商 Provider 入口。
5. 凭据落盘口径不同：Qwen 的 Model Providers 文档写 “Credentials are never persisted in settings; the runtime reads them from `process.env[envKey]`.”，而认证文档同时把 Key 写进 `settings.json` 的 `env` 字段作为最低优先级兜底并提示明文风险；Kimi 的 `api_key` 与 `api_key_env` 互斥，二者都不存在时才读 `[providers.<name>.env]` 子表；Codex 用 `env_key` 或 `[model_providers.<id>.auth]` 的命令式 token，`experimental_bearer_token` 被官方标注为 discouraged；Qoder 由 BYOK 向导保存并明确要求不要手工编辑 `settings.json`。
6. 「Provider 目录的事实来源」定义不同：Qwen 的预设、端点与 Key 前缀校验固定写在源码里并随版本发布，QwenCloud 两个预设自 v0.25.3-preview.0 起才存在、stable v0.25.2 没有；Kimi 的第三方目录来自远端 models.dev 或私有 registry，同一 registry 地址下的供应商在后续启动时一起刷新；Qoder 的 Custom 向导以「当前账号可见的实时 BYOK 目录」为准，文档点名的六家厂商只是示例。

### Codex

| 字段 | 记录 |
| --- | --- |
