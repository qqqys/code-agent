## 比较边界

### 本页包含

- 文件读取、创建、覆盖和局部修改
- Notebook 或媒体文件的专用入口
- 单次读取的大小上限、超限结果与一次读完的入口
- 修改前读取、权限审批与工作区边界

### 本页不包含

- Shell 工具自身的执行、超时与后台进程管理
- 代码搜索和符号导航
- Git 暂存、提交与回退

## 跨产品事实

1. 五家都提供模型可直接调用的文件读写能力，不需要先拼接 Shell 命令。
2. Claude Code、Qwen Code 和 Qoder CLI 单独提供 Notebook 编辑工具；Kimi Code 的当前工具表把媒体读取与文本读取分开。
3. 工具名称相近不代表审批相同：只读工具通常可直接运行，写入和编辑仍受各自权限模式、工作区边界与沙箱约束。
4. 换行处理不同：Codex `apply_patch` 自 rust-v0.162.0 起无条件保留原换行（旧的归一为 LF 模式与 `apply_patch_preserve_line_endings` opt-in 开关已移除）；Qwen Code `edit` 默认检测并保留原换行风格。Claude Code、Kimi Code 与 Qoder CLI 的官方工具文档未列同类换行保留或规范化配置。
5. 写前读与过期写入保护在 2026-11-28 复核后分成四类。仍强制且没有自动恢复例外的是 Kimi Code：2.8.1 标签提交下的中文工具文档在 `Write` 与 `Edit` 段各写明目标文件必须先在本会话用 `Read` 读过、文件自上次读取后在磁盘上变化即拒绝、新建文件不受限。强制但带恢复例外的是 Claude Code 与 Qwen Code：Claude Code 工具参考的 **Read-before-edit** 要求当前会话先读取（`PARTIAL view` 截断读取不算，Opus 4.6、Haiku 4.5 及更早模型始终要求先读，较新模型在读取免权限提示且 Read 可用时可编辑未读文件），读后磁盘变化的文件在 `old_string` 精确唯一匹配且读取无需提示时仍可直接编辑；Qwen Code 自 v0.28.0 起把同类例外升级为有官方设计文档的「授权过期恢复」——`edit` 在读后指纹漂移时按当前文件内容自动改写唯一一处字面匹配、默认开启且不加人工确认，而 `write_file` 从不请求恢复、必须等一次成功文本读取刷新基线。已取消的是 Qoder CLI：1.1.100 更新日志逐字写 “Improved Edit logic so it no longer requires reading a file with Read before editing”，这是官方一手资料第一次承认此前存在该要求，Tools 页在核对日期没有任何对应文字。从未有过的是 Codex：Apply Patch 指南不设写前读要求，`update_file` 上下文与文件内容不匹配时返回 `Error: Invalid Context` 由模型自行重读。
6. 过期恢复都不构成授权边界，且都不保证语义位置：Claude Code 把「读取无需权限提示」当作例外的前提条件之一，Qwen Code 的设计文档逐字写 “This is a deliberate tradeoff for default automatic recovery, including AUTO_EDIT/YOLO and noninteractive execution. A confirmation warning or a returned snippet communicates the event; neither is an authorization boundary or a proof of the old semantic location.”，并说明恢复只替换 `old_string` 在**当前文件**里的那一处字面匹配、“It does not prove that this occurrence is the semantic location seen in an earlier Read.”；Kimi Code 一律拒绝漂移写入，Qoder CLI 自 1.1.100 起一律不检查，两者都没有这一层。
7. 单次读取的额度口径五家各不相同：Claude Code 按 token 计（默认一次至多 25,000 token，整文件超过 256 KB 直接拒绝），自 v2.1.296 起模型可在单次调用传 `allow_large: true` 改为按会话剩余上下文窗口计量；Kimi Code 自 2.4.1 起是字符加估算 token 双上限（默认与单次可申请上限都是 100,000 字符，单次调用还在估算 token 达到 `[read] max_chars` 的四分之一即默认约 25,000 时停止，非 ASCII 每字符计 1 token、ASCII 每 4 字符计 1，调高配置 `max_chars` 同时抬高两个上限，旧的「单次可申请到 500,000 字符」作废）；Qwen Code 按行数加字符计（默认 1000 行、25,000 字符，各自设 `-1` 关闭，都需要重启），没有每次调用的放大入口；Codex 没有专用文本读取工具，文本读取走 `exec_command`/`write_stdin` 的 `max_output_tokens`（默认 10000 token）并另有 1 MiB 的保留输出硬上限；Qoder CLI 官方只写「文件过大时读取聚焦片段」，没有公布任何数值上限。
8. 超限后的可恢复性也不同：Claude Code 整文件超 token 上限时返回首页并附 `PARTIAL view` 提示、整文件超 256 KB 或分页读超 token 上限时直接报错并要求改用 `offset`/`limit` 或 Grep；Kimi Code 在状态里给出列范围与 `Next Read` 参数，单行放不下时按片段返回，2.4.1 起指定 `n_lines` 或负 `line_offset` 的范围在 `max_chars` 之内放下后仍超估算 token 上限时直接报错并给出放得下的行数与改用 Grep 的建议、不返回部分内容，一次返回整个文件且没有需要说明的情况时省略状态块；Qwen Code 把超限输出写进会话临时目录并在历史里留预览加指针，模型可用 `read_file` 取回；Codex 对 stdout 与 stderr 各自 `truncate` 到上限，保留开头、丢弃结尾且不报告截断行数。
9. 非文本读取的边界各自独立：Claude Code 拒绝超过 128 MB 的图片源（v2.1.302，更新日志与工具参考同口径）并拒绝 `.xlsx`、`.parquet`、`.heic`、`.zip` 等按二进制处理的扩展名；Kimi Code 图片与视频走 `ReadMediaFile`、官方写明文件大小上限 100 MB；Qwen Code PDF 的 `pages` 一次至多 20 页（`PDF_MAX_PAGES_PER_READ`），自 v0.26.2 起托管 Provider 场景的 `ReadFileTool` 可带 `mediaLimits` 限制内联媒体与结果字节数而标准 CLI 构造不传该参数；Codex `view_image` 声明没有字节或像素上限；Qoder CLI 自 1.1.100 起内置 PDF 阅读插件，更新日志逐字为 “Added a built-in PDF reading plugin so you can read PDF text and images without installing a third-party environment”，但 Built-ins、Plugins Reference 与设置参考三页对 `pdf` 的命中数均为 0，插件名、入口、能否禁用与页数或字节上限都没有公布，此前 Tools 页 “Inspect supported document formats, such as PDFs, when available.” 里的 “when available” 是否就指该插件也未确认，其余媒体类型仍然没有数值上限。

| 执行行为 | 读取与编辑分别经过路径权限、工作区信任和 approval mode。`read_file` 的默认分页上限不是硬编码行数，而是取 `config.getTruncateToolOutputLines()`，也就是设置项 `tools.truncateToolOutputLines`（默认 `1000`，官方描述 “Maximum lines or entries kept when truncating tool output. | 矩阵结论 | `Read` · `Edit` · `Write` · 2.4.1 起默认与单次可申请上限都是 100000 字符，并在估算 token 达 `[read] max_chars`/4（默认约 25000）时停止 · 调高配置 `max_chars` 同时抬高两个上限 · 官方文档已记录写前读与磁盘变化拒绝 |
| 入口与工具 | 模型调用 `Read`、`Write`、`Edit`；图片和视频使用 `ReadMediaFile`（文件大小上限 100 MB）。 |
| 核心机制 | `Read` 按字符加估算 token 双额度返回，参数为必填的 `path` 与可选的 `line_offset`（起始行号，负数从末尾倒数）、`column_offset`（正向读取时起始行内从 0 开始的位置）、`n_lines`（请求读取的源文件行数，省略时向文件末尾读取）与 `max_chars`（结果的字符上限，包含行号与状态信息）；2.4.1 起默认上限和单次调用可申请的最大值都是 100,000 字符，单次调用还会在估算 token 数达到配置 `[read] max_chars` 的四分之一（默认约 25,000）时停止，token 折算为每个非 ASCII 字符计 1、每 4 个 ASCII 字符计 1 并向上取整，因此中文等非 ASCII 字符较多的文本每次返回的字符更少；字符数与列偏移按显示文本的 JavaScript 字符串长度计算（常见字母与汉字各计 1，许多 emoji 计 2），列偏移不含行号前缀。`Write` 支持 overwrite/append；`Edit` 支持唯一匹配或 `replace_all`。 |
| 执行行为 | Read 默认放行，Write/Edit 默认需审批；Grep/Glob 会过滤敏感文件，写入缺失父目录时会自动创建。读取额度由 `[read]` 配置块控制，官方写明它「控制 `Read` 工具的字符额度，包含文件正文、行号和状态信息，不额外叠加行数或 UTF-8 字节数上限」，字段为 `default_max_chars`（integer，默认 `100000`，工具调用未指定 `max_chars` 时的额度）与 `max_chars`（integer，默认 `100000`，2.4.1 起由 `500000` 下调，单次调用可申请的最大额度）；两个值都必须是正整数，调用里的 `max_chars` 覆盖默认值但不会超过配置的最大值（超出时状态提示 “Requested max_chars=… was capped at the configured maximum …”），配置的默认值超过最大值时默认读取也按最大值执行；估算 token 上限只由配置的 `max_chars` 派生（源码 `tokenLimit = Math.ceil(limits.maxChars / 4)`，默认 25,000），调用参数 `max_chars` 不改变它；官方写明想让单次调用返回超过 100000 字符或约 25000 token 需要提高 `max_chars`，想让较大文档默认就一次返回、不用 Agent 主动申请更大额度再同时提高 `default_max_chars`。超额页面在组装时就地收缩而不重读文件：多行时逐行丢弃，单独一行放不下时按 token 权重切片段（ASCII 每字符 0.25、非 ASCII 每字符 1，不拆散代理对），纯 ASCII 文本因 token 折算向上取整通常触不到 token 上限、保持精确的字符分页。`Read` 优先返回完整行，官方逐字为「结果不会再被通用工具输出限制缩短」；除非一次就返回了整个文件且没有需要说明的情况，内容后附带 `<system>` 状态块，状态里给出列范围与 `Next Read` 参数因而不需要提高额度即可续读，不完整页面另附提示 “If the answer may be further on, continue with Next Read or find the section with Grep instead of answering from this page alone.”；调用指定了范围（带 `n_lines` 或负 `line_offset`）而 `max_chars` 之内放得下的行仍超过 token 上限（源码为状态预留 256 token）时，直接返回错误 “Lines X-Y are more than one Read can return (about N estimated tokens). Read at most M lines at a time, for example {…}, or find the section with Grep.” 而不是只返回其中一部分，只被 `max_chars` 截短的范围仍返回一页加 `Next Read`，整文件读取、从 offset 读到末尾、单行请求与列续读都照常分页；拼接同一行的片段时不要额外插入换行，一行只返回部分内容时仍计入剩余的 `n_lines` 范围直到行尾返回，非法列偏移明确报错而不跳过内容。尾读优先返回请求范围里较新的完整行，连一条完整行都放不下时给出未读范围的正向 `Next Read` 参数，`column_offset` 不能与负数 `line_offset` 同时使用；续读位置针对文件当前内容，文件变化后要重新读取，尾读若提示读取期间文件发生变化则基于更新后的文件重试。10 MiB 以内的 UTF-16 LE/BE 文件先尝试严格解码，失败后把损坏序列替换掉并返回可读文本、每一页都告警发生了有损解码，告警本身也计入字符额度。2.4.1 起 `Edit`/`Write` 成功的结果附带状态提示 “The change is applied; there is no need to Read the file back to check it.”，`Read` 的工具描述同步删掉了「任务需要大文件全文时在首次调用申请更大 `max_chars`」一句并新增 “After a successful `Edit`/`Write`, do not re-read solely to prove the write landed.”。v2 引擎的 staleGuard 在工具执行前拦截 Edit/Write：修改已有文件要求本 Agent 此前成功执行过 `Read`（`Read`/`Edit`/`Write` 成功后记录文件 mtimeMs，失败不记录），当前磁盘 mtime 与记录不一致即拒绝；同一批工具调用中已有对同一路径的 `Read` 时放行；新建文件不受影响。拒绝时分别提示 "has not been read by this agent yet" 或 "has been modified on disk since this agent last read it"，要求先（重新）读取；Agent 运行时变化会清空记录。 |
