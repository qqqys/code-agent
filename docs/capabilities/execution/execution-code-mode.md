# 代码模式调用工具

[返回任务执行与 Git 详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=execution-code-mode)

> 核对日期：2026-11-15

## 定义

模型不再逐个发起工具调用，而是写一段代码交给产品在受控运行时里执行，代码内部通过注入的绑定发起多个嵌套工具调用，只有显式返回的内容回到模型上下文。

## 比较边界

### 本页包含

- 开启代码模式的开关、环境变量或配置键，以及它们可写的位置
- 承载代码的工具名、代码语言与运行时的隔离方式
- 代码里可用的全局对象、助手函数与嵌套工具绑定规则
- 嵌套调用的权限、Hook、并发、超时与输出边界
- 长任务、后台执行、跨调用状态与会话恢复的限制

### 本页不包含

- 未开启代码模式时模型直接发起的普通工具调用
- Shell 工具自身的命令执行、超时与后台进程管理
- 工具声明延迟与按需发现机制本身，本字段只记它与代码模式的衔接
- 沙箱、审批模式与工具白名单的总体边界

## 跨产品事实

1. 五家里四家已有代码模式，只有 Kimi Code 没有：Claude Code、Codex 与 Qwen Code 都有一手资料确认的开关、专用工具与隔离运行时，Qoder CLI 由官方更新日志宣布但文档站没有对应页面，Kimi Code 的中英文工具文档、配置参考与更新日志都查不到该机制。
2. 有代码模式的四家全部默认关闭并标为实验性或开发中：Claude 写 “experimental and off by default”，Codex 的 `code_mode` 是 `Stage::UnderDevelopment` 且 `default_enabled: false`、官方配置参考写 “This feature is under development and off by default.”，Qwen 的设置 label 是 “Code Mode Only (Experimental)” 且默认 `false`，Qoder 需要环境变量加设置面板两步开启。
3. 承载代码的工具名不统一：Claude 是 `REPL`（只在 Code Mode 专页的 Hook matcher 与故障表里出现，官方工具参考页没有独立条目），Codex 与 Qwen 都是 `exec`（Codex 另有配套的 `wait`），Qoder 未公布。
4. 运行时与隔离方式分三种，且都强调没有 Node 环境：Codex 在独立宿主进程 `codex-code-mode-host` 里为每次 `exec` 新建 V8 isolate（可按 gRPC 连远程宿主），描述写 “no Node, no file system, no network access, no console”，宿主还主动删掉 `console`、`Atomics`、`SharedArrayBuffer` 与 `WebAssembly`；Qwen 在专用子进程里跑编译成 WASM 的 QuickJS、每次调用新建 runtime 与 context，写 “There is no Node.js, process, require, filesystem, network, import, console, WebAssembly, Atomics, or persistent state.”；Claude 只写 “Claude Code runs that code in your session”，没有公布引擎与隔离层级。
5. 三家都写明嵌套调用不绕过权限，但审批粒度不同：Claude 在 auto mode 下由分类器“审代码而不是审每个工具调用”、看不到运行时算出来的值，其余权限模式逐个调用照常提示；Codex 的 Hook 决策逐条作用到嵌套调用，`PreToolUse` 阻断会让工具 promise 在运行前 reject；Qwen 的嵌套调用重新进入 `Session.runTool` 或 Core 调度器，沿用同一套校验、权限、确认、Hook、遥测与截断路径。
6. 跨调用的持久状态只有 Codex 提供：`store(key, value)` 与 `load(key)` 在同一会话的后续 `exec` 之间保留可序列化值；Qwen 的设计文档把 “Persistent cells, globals, or values between `exec` calls” 与 “Background jobs, `wait`, `yield`, `store`, or `load`” 明确列为 Non-goals；Claude 没有公布同类助手。
7. 长任务的口径三家完全不同：Claude 是等待模式下代码十分钟后停止（含在权限提示上花的时间）、后台模式最多两小时但必须以 auto 或 `bypassPermissions` 模式启动；Codex 是 `exec` 到点先 yield 并返回 cell ID，模型再用 `wait` 按 `cell_id` 续取输出，`yield_control()` 还能在脚本继续跑时立刻交出已积累输出；Qwen 是 `CODE_MODE_TIMEOUT_MS = 30_000` 加 QuickJS interrupt handler 实施的 guest CPU 预算，没有 yield 或后台机制。
8. 未 await 的调用一律被丢弃或取消，且两家都有对应测试：Codex 写 “When the JS code is fully evaluated, the isolate's lifetime ends and unawaited promises are silently discarded.”，Qwen 写 “Await every tool promise; unawaited calls are cancelled when the script finishes.”，其 unawaited-timer 测试在核对日期当天（2026-11-15）刚把 guest 预算从 25 毫秒调到 5 秒以消除 CI 抖动。
9. 与工具延迟发现的衔接方式不同：Qwen 在搜索可用时从 `exec` 描述里省略延迟工具的签名与描述、要求模型先在顶层调用 `tool_search`，搜索不可用时才把全部允许工具的签名塞进 `exec`；Codex 用独立开关 `code_mode_tool_search`（开发中、默认关闭）决定代码里是否有 `tools.tool_search({query, limit: 8})` 的 BM25 发现；Claude 没有公布代码模式下的工具发现路径。
10. 开启入口的可写位置各有边界：Claude 只认 shell、用户设置与 `--settings` 文件，项目与本地设置里的该变量被忽略，managed settings 只能写 `0` 封禁而不能替用户打开；Codex 与 Qwen 走各自的配置文件（Qwen 另需重启，且在 safe 与 bare 模式下被忽略）；Qoder 需要环境变量与 `/settings` 面板选择同时成立。

| 入口与工具 | `config.toml` 的 `[features.code_mode]` 表里写 `enabled = true`（官方手册的示例同时给出 `excluded_tool_namespaces = ["mcp__codex_apps"]` 与 `direct_only_tool_namespaces = ["mcp__history"]`），`features.code_mode` 也接受布尔写法；`features.code_mode_only` 把模型可见工具收缩到代码模式入口 `exec` 与 `wait`，源码注释逐字为 “Restrict model-visible tools to code mode entrypoints (`exec`, `wait`).”，`normalize_dependencies()` 里写着开了 `code_mode_only` 会自动开 `code_mode`；另有开发中且默认关闭的 `code_mode_tool_search`（“Expose ranked tool discovery inside JavaScript code mode.”）与 `code_mode_only_strict_3p_tools`（“Keep eligible MCP/app and dynamic tools deferred in exec, only in Code Mode Only. | 核心机制 | 模型可见两个工具。`exec` 由 `create_code_mode_tool()` 声明为 `ToolSpec::Freeform`，名字取 `codex_code_mode::PUBLIC_TOOL_NAME`（逐字 `pub const PUBLIC_TOOL_NAME: &str = "exec";`），格式是 `{ type: "grammar", syntax: "lark", definition: … }`，语法允许纯源码或首行 pragma（`PRAGMA_LINE: /[ \t]*\/\/ @exec:[^\r\n]*/`），即收原始 JavaScript 文本而不是 JSON 参数；`wait` 由 `create_wait_tool()` 声明为普通 Function 工具（`WAIT_TOOL_NAME` 逐字为 `"wait"`），参数是必填的 `cell_id`（“Identifier of the running exec cell.”）、`yield_time_ms`（“Wait before yielding more output. Defaults to 10000 ms.”）、`max_tokens`（“Output token budget for this wait call. Defaults to 10000 tokens.”）与 `terminate`（“True stops the running exec cell; false or omitted waits for output.”）。嵌套工具挂在全局 `tools` 对象上、名字规范化成 JavaScript 标识符（描述里的例子是 `await tools.exec_command(...)` 与 `await tools.mcp__ologs__get_profile(...)`），元数据在 `ALL_TOOLS`；助手清单为 `exit()`、`text(value)`、`image(...)`、`audio(...)`、`generatedImage(result: { image_url: string; output_hint?: string })`、`store(key, value)`、`load(key)`、`notify(value)`、`setTimeout`／`clearTimeout` 与 `yield_control()`，宿主在 `install_globals()` 里先删掉 `console`、`Atomics`、`SharedArrayBuffer`、`WebAssembly`，再编译运行内置的 `settled.js` 与 `content.js`。 |
| 执行行为 | `exec` 描述首行逐字为 “Run JavaScript code to orchestrate/compose tool calls”，要点包括 “Evaluates the provided JavaScript code in a fresh V8 isolate as an async module.”、“Nested tool methods take either a string or an object as their input argument.”、“Runs raw JavaScript -- no Node, no file system, no network access, no console.”、“Accepts raw JavaScript source text, not JSON, quoted strings, or markdown code fences.” 与 “When the JS code is fully evaluated, the isolate's lifetime ends and unawaited promises are silently discarded.”；pragma 示例是 `// @exec: {"yield_time_ms": 10000, "max_output_tokens": 1000}`，`max_output_tokens` 的默认值写死为 10000 token。运行时用 V8：`initialize_v8()` 的注释逐字为 “Initializes the process-wide V8 platform with the requested JIT mode. … V8 cannot change JIT mode after initialization, so a later call requesting a different mode returns an error. Code mode initializes V8 with JIT enabled by default when this function has not been called explicitly.”，`V8JitMode::Disabled` 时加 `--jitless`，初始化还会因 pinned V8 的 `Array.prototype.sort` 内联问题设 `--no-maglev --no-turbolev --no-turbo-inline-array-builtins`。三个协议默认值是 `DEFAULT_EXEC_YIELD_TIME_MS = 10_000`、`DEFAULT_WAIT_YIELD_TIME_MS = 10_000`、`DEFAULT_MAX_OUTPUT_TOKENS_PER_EXEC_CALL = 10_000`，而配置项 `default_exec_yield_time_ms` 的默认值是 `DEFAULT_CODE_MODE_EXEC_YIELD_TIME_MS = 30_000`，`CodeModeService::execute()` 在请求未带 `yield_time_ms` 时用后者补上；`tool_input_schema_max_bytes` 的 schema 描述逐字为 “Maximum UTF-8 bytes per rendered tool input type, with a 16,000-byte minimum and default. For ordinary MCP tools, this is also at least their server's explicitly configured input limit.”；`exec` 不能递归调用自己（源码里返回 “exec cannot invoke itself”）。 |
| 运行范围 | 工具注册在 `codex-rs/core` 的会话里，因此终端会话与 app-server 会话都能用——TUI 快照测试 `codex_tui__chatwidget__tests__status_and_layout__unsupported_code_mode_warning.snap` 逐字渲染出 “⚠ Code Mode is enabled in configuration, but model `gpt-5.4` does not advertise Code Mode support.”，证明告警出现在终端界面而不只是日志；app-server 默认起本地 Code Mode 宿主，官方写 “By default, app-server starts a local Code Mode host. | 后台与并发 | 长脚本靠 yield 加 `wait` 续接：`wait` 的描述逐字为 “Use `wait` only after `exec` returns `Script running with cell ID ...`.”、“`wait` returns only the new output since the last yield, or the final completion or termination result for that cell.”、“If the cell is still running, `wait` may yield again with the same `cell_id`.” 与 “If the cell has already finished, `wait` returns the completed result and closes the cell.”；脚本内部可用 `yield_control()` “yields the accumulated output to the model immediately while the script keeps running”，`notify(value)` 则 “immediately injects an extra `custom_tool_call_output` for the current `exec` call”。`store(key, value)` 与 `load(key)` 让可序列化值在同一会话的后续 `exec` 调用之间保留。中断侧有 Stable 且默认开启的 `code_mode_interrupt`（“Terminate active code mode cells when their turn is interrupted.”），`CodeModeService::interrupt_active_cells()` 逐个终止活动 cell；`[code_mode] heartbeat_interval_s` 的 schema 描述逐字为 “Idle seconds between gRPC stream heartbeats. | 入口与工具 | `tools.codeModeOnly`（boolean，默认 `false`，`requiresRestart: true`，`category: 'Tools'`，`showInDialog: true`，label 逐字为 “Code Mode Only (Experimental)”），官方设置文档写 “Set `tools.codeModeOnly` to `true` to enable experimental Code Mode with lazy tool discovery. | 核心机制 | 唯一入口工具是 `exec`（`ToolNames.EXEC` 逐字为 `EXEC: 'exec'`，显示名 `Exec`），描述首行逐字为 “Execute JavaScript in a fresh isolated runtime and wait for it to finish.”；全局清单是 `tools`（“all registered code-mode-callable tool functions permitted in this context, including deferred tools”）、`ALL_TOOLS`（“frozen metadata for every function in tools”）、`text(value)`、`image(imageUrlOrItem: string \| ImageContent)`、`audio(dataUrl: string)`、`generatedImage(result: CodeModeToolResult)`、`setTimeout(callback, delayMs?)`、`clearTimeout(timeoutId?)` 与 `exit()`；嵌套调用写成 `tools.<jsName>(args)`，`jsName` 由 `normalizeCodeModeToolName()` 把非法标识符字符替换成 `_`、给数字开头的名字加 `_` 前缀，`planCodeModeBindings()` 按规范名排序、冲突时保留字典序第一个并在描述末尾列出 “- {omitted} is omitted because it collides with {kept} as tools.{jsName}.”；媒体助手共用每次 `exec` 16 项与 10 MiB 解码后 base64 的额度；`type CodeModeToolResult = { callId: string; name: string; status: 'success'; output: string; content?: ImageContent[] }`。 |
| 执行行为 | 运行时是 QuickJS 编译成 WASM、跑在专用子进程里：设计文档逐字为 “`exec` runs QuickJS compiled to WebAssembly in a dedicated child process. Each call creates a fresh QuickJS runtime and context. The child process receives a small framed JSON protocol over stdio; it has no tool implementations or Qwen configuration.”，实现里宿主进程导入 `@jitl/quickjs-singlefile-mjs-release-sync` 与 `quickjs-emscripten-core`，只用 `process.stdout.write(encodeFrame(message))` 与父进程通信。guest 能力边界逐字为 “The guest has no Node globals, `require`, `process`, filesystem, sockets, module loader, `console`, timers, `Atomics`, `SharedArrayBuffer`, or `WebAssembly`. Dynamic and static imports fail because no module loader is installed.”，工具描述里也写 “There is no Node.js, process, require, filesystem, network, import, console, WebAssembly, Atomics, or persistent state. Static and dynamic imports are unsupported.
