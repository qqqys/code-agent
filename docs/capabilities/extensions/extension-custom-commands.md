# 自定义 Slash 命令

[返回扩展系统详情目录](./README.md) · [打开网页详情](https://qqqys.github.io/code-agent/capability.html?id=extension-custom-commands)

> 核对日期：2026-10-23

## 定义

把提示模板保存成可输入的 Slash 命令，并区分独立 Command 文件、Skills、Plugin Commands、用户配置里的数字槽位与已弃用机制。

## 比较边界

### 本页包含

- Markdown Prompt Command 的目录与命名
- 参数、命名空间和加载优先级
- 与 Skills 或 Plugin Commands 的关系
- 用户配置里的数字槽位与召回快捷键

### 本页不包含

- 产品内置 Slash 命令
- MCP Server 动态暴露的 Prompt
- 只通过自然语言自动触发、没有命令入口的 Skill
- 槽位或命令内容所指向的模型、权限、终端标题与状态行设置本身

## 跨产品事实

1. Claude Code、Qwen Code 和 Qoder CLI 都保留独立 Markdown Command 目录；Kimi Code 当前只文档化 Plugin Commands 与 Skills，官方 `docs/zh/customization/` 下没有 commands 文档。
2. Codex 有旧新两条并存的路：`~/.codex/prompts/*.md` 自定义 Prompt 已弃用（官方逐字为 “Custom prompts are deprecated. Use skills for reusable prompts”）且只在本机使用，2026-10-15 合入 main 的 `/presets` 则把最多十个数字槽位写进用户配置的 `tui.presets.<0-9>`，槽位内容是一条提示词或一条 Slash 命令行，按 `0`–`9` 召回。
3. 存储位置决定共享范围：Claude Code、Qwen Code 与 Qoder CLI 的项目级 Command 目录可随仓库提交共享，Kimi Code 的插件命令随插件分发，Codex 的旧 Prompt 与 `/presets` 槽位都只属于本机用户——官方对旧 Prompt 的说法是 “they’re not shared through your repository”。
4. 同名覆盖方向不一致：Claude Code 是 “Enterprise over personal, and personal over project”，Qoder CLI 是用户级覆盖项目级，Qwen Code 相反、官方写 “Project commands > User commands (project command used when names are same)”。
5. 参数占位符各家不同、位置参数的基底也不同：Claude Code 与 Kimi Code 都从 0 开始（`$0` 是第一个参数），Codex 已弃用的 Prompt 用 `$1` 到 `$9`（没有 `$0`）并另有 `$ARGUMENTS`、大写命名占位符与 `$$` 转义，Qwen Code 只有 `{{args}}` 加 `!{command}` 与 `@{file path}`，Qoder CLI 没有记录任何占位符语法。
6. 只有 Codex 把可复用提示词存进配置文件的数字槽位；其余四家在核对日期的一手资料里都是文件式命令目录或 Skill。Claude Code 的输入历史（`Up` 召回、`Ctrl+R` 反向搜索）与 Qoder CLI 1.1.20 的 “Added Ctrl+S to stash the current prompt draft and restore it later” 都是历史或草稿机制，不是可命名、可编号的提示词槽位。
7. 同样显示为 `/name` 的入口可能来自内置命令、Skill、Prompt Command、Plugin 或 MCP Prompt，矩阵只比较其公开加载机制。

### Codex

| 字段 | 记录 |
| --- | --- |
| 矩阵结论 | Skills；`/prompts:*` 已弃用 · 条件：`/presets` 把提示词或 Slash 命令行存进用户配置 `tui.presets.<0-9>` 十个数字槽位，`0`–`9` 直接召回、`leader p` 或 `/presets` 开菜单（合入 main 尚未发布） |
| 入口与配置 | 推荐通过 Skill 暴露可复用能力；旧 Prompt 使用 `/prompts:<name>`。main 分支另有 `/presets`（源码描述逐字为 “run or save reusable prompts and slash commands”，无别名、不在 `supports_inline_args` 清单里因而不接受内联参数），在输入框上方打开标题为 “Presets” 的菜单：`0`–`9` 运行已存槽位或在空槽新建，`n` 新建、`s` 从当前设置新建、`e` 编辑、`d` 删除、`Esc` 关闭；隐式快捷键是 `leader p`，对应键位动作 `tui.keymap.chat.open_presets`（`config.schema.json` 描述逐字为 “Open saved prompts and slash commands.”），该动作在 `/keymap` 中列出。 |
| 文件与目录 | 旧 Prompt 只从用户目录 `~/.codex/prompts/*.md` 加载，官方写明只扫描该目录顶层的 Markdown 文件；项目不提供同等 Prompt 目录。`/presets` 不用目录：槽位写进当前生效的用户配置文件（源码字段 `local_settings.user_config_path`，官方配置参考逐字为 “User-level configuration lives in `~/.codex/config.toml`.”）的 `tui.presets.<slot>`，`slot` 是单个数字 `0`–`9`，每槽是只含 `input` 与 `label` 两键的 TOML 表。 |
| 具体行为 | 旧 Prompt 把 Markdown 内容插入对话；Skill 可携带更完整的脚本和资源，并支持显式或自动调用。`/presets` 的槽位只存纯文本：`input` 可以是一条提示词，也可以是一条 Slash 命令行，召回时经 `queue_user_message_with_options(input, QueuedInputAction::ParseSlash, …)` 走常规排队提交路径并解析 Slash 命令，全程不改写输入框因而保留草稿。`s` 打开 “Start preset from current settings”，四项分别生成命令行：“Current model” 生成 `/model <name>` 并按可用情况追加 `--reasoning=<effort>` 与 `--speed=<speed>`（服务层级为默认值时速度取 `standard`），“Current permissions” 生成 `/permissions <profile_id> --approval-policy=<policy> --reviewer=<reviewer>`（profile 名经 `shlex::try_quote` 引号化），“Current terminal title” 与 “Current status line” 生成保留条目顺序与重复项、归一化条目别名的 `/title <item…>` 与 `/statusline <item…>` 并给状态行追加 `--colors` 或 `--no-colors`，条目为空时改用 `<command> --clear`。写入前校验：`input` 去空白后为空报 “Preset input cannot be empty.”，去空白后以 `!` 开头报 “Presets support prompts and slash commands, not shell commands.”，超过 8000 UTF-8 字节报 “Preset input cannot exceed 8,000 UTF-8 bytes.”；图片与 linked mention 不能存进槽位（分别提示 “Images cannot be copied into a preset. Starting with empty text.” 与 “Linked mentions cannot be copied into a preset. Starting with empty text.”）。菜单只列出已占用槽位，有 `label` 时显示 label、否则显示 input 且过长以 `…` 截断；编辑与删除都要过 “{action} preset {slot}?” 确认，替换时给出 “{}\n→ {}” 的旧值新值对照。 |
| 作用域与优先级 | 旧 Prompt 仅本机用户；Skills 可放项目 `.agents/skills` 或用户目录。`/presets` 的槽位按配置层归属：只能替换当前用户配置拥有的槽位，最高层定义落在别的配置层时报 “Preset {slot} is defined outside your user config. Edit its source configuration instead.”；清空时只要有任何非用户配置层定义过该槽位就一并拒绝，源码注释写明 “Clearing must not reveal a shadowed slot from another configuration layer.”；把 `label` 写成空字符串可遮蔽下层继承来的标签（注释 “An explicit empty label masks labels inherited from lower layers.”）。写入失败报 “Failed to update preset {slot}: …” 且内存中的设置保持不变，只读与失败两条路径都会用 `restore_quick_dial_editor` 把编辑器回填。 |
| 扩展构成 | 旧机制只有 Markdown Prompt：YAML front matter 里可写 `description:`（显示在弹出菜单的命令名下）与 `argument-hint: KEY=<value>`，正文可用位置占位符 `$1` 到 `$9`（官方逐字为 “`$1` through `$9` expand from space-separated arguments you provide after the command. `$ARGUMENTS` includes them all.”）、大写命名占位符如 `$FILE` 或 `$TICKET_ID`（以 `KEY=value` 传值、含空格的值要加引号，例如 `FOCUS="loading state"`）与字面量 `$$`；Skills 使用 SKILL.md 与辅助资源。`/presets` 槽位是 Rust 类型 `QuickDial`（结构体注释逐字为 “One reusable prompt or slash command submitted through the TUI composer.”，JSON schema 名 `Preset` 且 `deny_unknown_fields`）的两个字段：`input: String`（“Plain-text input, limited to 8,000 UTF-8 bytes.”）与 `label: Option<String>`（“Optional short name for the picker and shortcut hints.”）；在 `Tui` 结构里以 `#[serde(default, rename = "presets")]` 暴露为 `BTreeMap<String, QuickDial>`，字段注释逐字为 “Saved inputs keyed by a single digit (`0` through `9`).”。源码没有槽位数量常量，十个槽位来自“键是单个数字”这一约定与提交说明里的 “ten numbered preset slots”。 |
| 加载与刷新 | 旧 Prompt 在客户端发现后以 `/prompts:*` 提供，官方写明 “Codex reads prompt metadata and resolves placeholders the next time the session starts.” 与 “After editing prompt files, restart Codex or open a new chat so the updates load. Codex ignores non-Markdown files in the prompts directory.”，并且只扫描 `~/.codex/prompts/` 顶层的 Markdown；新内容应使用 Skills。`/presets` 的槽位随用户配置加载进 `local_settings.tui.quick_dials`，保存或删除成功后立即同步内存副本并提示 “Saved preset {slot}.” 或 “Deleted preset {slot}.”，不需要重启会话；启动完成前按数字键提示 “Presets are available after startup completes.”，线程不可用时提示 “Presets are unavailable in this conversation.”。 |
| 适用界面 | 以 Codex CLI 为准；桌面端、IDE 扩展、Cloud 和 `codex exec` 不自动继承全部交互命令。`/presets` 定义在 `codex-rs/tui`，在 `available_during_task` 的 `=> true` 分支里因而回合运行中可用，但不在 `available_in_side_conversation` 与 `available_when_thread_unavailable` 两个 `matches!` 清单中（两者默认返回 `false`），即 side conversation 内与线程不可用时不能执行；官方文档没有记录它在其他 Surface 的可用性，记为未确认。 |
| 权限与信任 | Prompt 或 Skill 都不绕过审批与沙箱。`/presets` 同样只是提交文本：槽位里的 Slash 命令与提示词走正常解析与权限流程，源码明确拒绝把 `!` 开头的 Shell 命令存成槽位；`s` 生成的 `/permissions <profile-id> --approval-policy=<policy> --reviewer=user\|auto_review` 命令行仍要经过 `/permissions` 自己的解析与校验，未知策略报 “Unknown approval policy `{value}`.
