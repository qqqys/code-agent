## 定义

把 Agent 作为可被其他程序或设备连接的长驻进程运行，通过 stdio、HTTP、SSE、WebSocket、ACP 或 MCP 管理会话和事件。

## 比较边界

### 本页包含

- 面向客户端集成的协议服务器
- 本地常驻服务和远程终端连接
- 本地常驻服务的发现、版本更新与重启入口
- 会话、事件、权限与认证边界

### 本页不包含

- 单次 Headless 子进程
- 单纯的云端任务网页
- 只消费外部 MCP Server 的客户端能力

## 跨产品事实

1. Codex 的 app-server、Qwen 的 qwen serve 和 Kimi 的 kimi web 都提供面向富客户端的双向服务，但协议分别是 JSON-RPC、HTTP + SSE、REST + WebSocket。
2. Qoder 的 ACP Server 面向 IDE，Remote Control Daemon 面向 Qoder Web/移动端；它不是公开的本地 HTTP Agent API。
3. Claude Code 有三条常驻路径且托管对象各不相同：后台会话 supervisor（`claude daemon` 管理）只承载后台会话的 worker 进程，Agent SDK 是宿主进程内的长连接运行时，Remote Control 是经 Anthropic 中继的跨端通道。三者都不是通用本地 HTTP Agent API，官方 CLI 参考的 `claude` 子命令表里也没有 `claude mcp serve`，`claude mcp` 下只有 `login <name>` 与 `logout <name>`。
4. Codex、Claude Code 与 Qwen Code 都有 CLI 自己管理的本地常驻进程和生命周期子命令，但启动方式三种不同：Claude 的 supervisor 由 CLI 在首次把会话转入后台或打开 agent view 时自动拉起（官方逐字 “Claude Code starts it the first time you background a session or open agent view, and you don't need to manage it yourself.”），Codex TUI 默认发现并附加共享 daemon（特征开关 `daemon_auto_start`），Qwen 的 `qwen daemon start` 必须显式执行、官方文档同时保留 systemd/launchd/`nohup &`/tmux 与 Local launch templates。Kimi 与 Qoder 没有任何生命周期子命令：`kimi web` 在前台运行到 SIGINT/SIGTERM，Qoder 子命令表 14 行里与常驻服务有关的只有 “`remote-control` | Start the remote-control daemon.”，`status` 是会话状态而不是 daemon 状态。
5. 版本更新入口只有 Codex 与 Claude 有：Codex `/daemon` 菜单的 “Install latest public stable” 与 “Use this CLI build” 两项更新被管理二进制，`codex app-server daemon update` 即使关闭自动更新也选最新 stable；Claude 的 supervisor 在自动更新后自行重启到新版本并在后台迁移空闲会话（正在工作、等待用户或已被接管的会话不中断），`claude daemon status` 在 supervisor 版本与调用的 `claude` 不一致时告警并让你跑 `claude daemon stop --any` 换新版本，`claude respawn --all` 则把所有会话迁到更新后的二进制。Qwen 的 `qwen daemon restart` 只按记录的端口、hostname、工作区、Web Shell 模式与 `--require-auth` 重启同一二进制，不做版本更新，也没有服务安装入口。
6. 发现记录与状态文件位置各不相同：Codex 在 `CODEX_HOME/app-server-daemon/`（`settings.json`、`app-server.pid`、`app-server-updater.pid`、`daemon.lock`），Claude 在 `~/.claude/daemon.log`、`~/.claude/daemon/roster.json`、`~/.claude/daemon.lock` 与 `~/.claude/jobs/<id>/state.json`（设 `CLAUDE_CONFIG_DIR` 时 supervisor 改用该目录并成为带自己会话的独立实例），Qwen 在 `$QWEN_RUNTIME_DIR`／`$QWEN_HOME`／`~/.qwen` 下的 `daemon/daemon-<port>.json`（POSIX `0600`、目录 `0700`、从不包含 bearer token），Kimi 在 `~/.kimi-code/server/instances/` 登记多实例并把 token 写进 `~/.kimi-code/server.token`，Qoder 未公开。
7. Codex daemon 的生命周期、状态文件与 `/daemon` 菜单只记录在官方仓库（`codex-rs/app-server-daemon/README.md`、TUI 源码与 CLI 集成测试）；官方文档站的 App Server 页没有 daemon 字样，只有 Developer commands 页的 remote-control 段写 “the local app-server daemon”。Qwen 的 `qwen daemon` 相反，仓库文档、官方文档站与命令源码三处一致；Claude 的 `claude daemon` 记录在官方 CLI 参考与 Agent view 两页，但更新日志里只有 v2.1.300 的两条修复、没有引入条目，因此引入版本未确认。

| 工具与能力 | supervisor 承载的是完整的 Claude Code 后台会话，因此带该会话自己的工具、MCP 与项目配置；supervisor 给每个后台会话的终端各起一个宿主进程。连接后的远程界面使用本机会话已有的文件、MCP、工具和项目配置。 |
| 认证与权限 | supervisor 与其会话使用和交互会话相同的已存凭据；后台会话的凭据来自 supervisor，因此 `Could not resolve authentication method` 意味着 supervisor 进程本身拿不到已存凭据，要在那次启动 supervisor 的 shell 里设好变量再重启它。LLM 网关只有在 supervisor 本身就是从导出了同一网关的 shell 启动时才够得着，否则要从跑 respawn 命令的终端重启 supervisor。Remote Control 要求同一 Claude 账号并受组织开关控制；SDK 按 Agent SDK 认证。 |

### Codex

| 字段 | 记录 |
| --- | --- |
| 矩阵结论 | `codex app-server` · `mcp-server` · 本地后台 daemon（`app-server daemon start\|restart\|update\|stop` · TUI `/daemon`） |
| 入口与调用 | `codex app-server`（默认 stdio，或 `--listen ws://127.0.0.1:4500`、`--listen unix://`）；`codex mcp-server`；`codex app-server daemon start\|restart\|update\|enable-remote-control\|disable-remote-control\|stop\|version\|bootstrap`；TUI 内 `/daemon`（源码描述 “Manage the local background server”）打开标题为 “Daemon” 的菜单；远程 TUI 可用 `app-server --listen` 配合 `codex --remote`；官方 Developer commands 页写 `codex remote-control start` “start the local app-server daemon with remote control enabled”、`codex remote-control stop` 停止它。 |
| 协议与输出 | app-server 使用双向 JSON-RPC，默认 stdio JSONL，也支持 Unix socket；WebSocket transport 标为实验且不受支持。MCP Server 使用 stdio MCP。daemon 生命周期命令走 `CODEX_HOME` 下的 Unix 控制套接字：`start` 幂等，在 app-server 能应答常规 JSON-RPC initialize 握手后返回；每条命令成功时向 stdout 写恰好一个 JSON 对象；同一 `CODEX_HOME` 的改动型命令串行执行。 |
| 具体行为 | app-server 提供认证、线程历史、审批和流式 Agent 事件；MCP Server 暴露 `codex` 与 `codex-reply` 工具。TUI 默认发现并附加本地后台 daemon（特征开关 `daemon_auto_start`，`codex --disable daemon_auto_start` 关闭），附加成功时状态行显示 `Server: Local background server`、改用内嵌服务器时显示 `Model:`；隐式发现的 daemon 无法初始化连接时 TUI 改起内嵌服务器，显式 `--remote` 端点仍以远端为准并报告连接失败。`/daemon` 菜单三项为 “Install latest public stable”、“Use this CLI build” 与 “Restart background server”：两个更新项在标题 “Update daemon and exit Codex?” 的确认（默认落在 Cancel）后退出 TUI、由启动它的 CLI 可执行文件执行更新并传播失败；重启项在标题 “Restart background server?” 的确认（正文 “Active or queued work in other chats may be interrupted.”、“Codex will reconnect automatically.”）后重启并自动重连，TUI 退出时进行中的重启会跑完。`stop` 先发优雅终止请求、超过 `shutdownGraceSeconds` 仍存活再强制结束；`update` 即使关闭自动更新也选最新 stable 并让被钉住的本地包恢复生产资格，运行中的 daemon 会重启、已停止的保持停止；`enable-remote-control`/`disable-remote-control` 持久化启动设置并重启已在运行的被管理 app-server。 |
| 会话与状态 | 一个服务可管理多个 thread/turn；远程终端连接到服务端工作区而非复制文件。daemon 状态在 `CODEX_HOME/app-server-daemon/`：`settings.json`（`remoteControlEnabled`、`shutdownGraceSeconds` 取 0–300 默认 60、`updater.autoUpdateEnabled`、`updater.updateIntervalMinutes`）、`app-server.pid`、`app-server-updater.pid` 与 `daemon.lock`；被管理的二进制固定在 `CODEX_HOME/packages/app-server-daemon/current/bin/codex`（Windows 为 `codex.exe`），生命周期命令一律用它而不随调用方 CLI 版本变化，旧 daemon 保留 `CODEX_HOME/packages/standalone/current`。CLI 集成测试以 `app-server-daemon/daemon.pid` 的内容变化断言重启确实发生，该文件与 README 记录的 `app-server.pid` 的关系未确认；测试写入的 `settings.json` 还含 `featureOverrides`（例如 `{"api_key_model_discovery": false}`），README 的键列表没有列出它。默认值以 crate 源码为准：`settings.rs`（main 提交 `40db507eeca2ff778c040c325449eb72e90c0590`）的常量是 `DEFAULT_UPDATE_INTERVAL_MINUTES: u32 = 60`、`DEFAULT_SHUTDOWN_GRACE_SECONDS: u32 = 60` 与 `MAX_SHUTDOWN_GRACE_SECONDS: u32 = 5 * 60`，两个字段各带 `#[serde(default = …)]`，校验为 shutdown grace 不得超过 300 秒、update interval 必须为正；同一提交的 README 示例 JSON 却把 `updateIntervalMinutes` 写成 `120`，而 README 正文写 “Eligible managed daemons check for updates after five minutes, then hourly by default.”，即示例与常量冲突，本仓库按源码记 60。 |

| 矩阵结论 | `qwen serve` HTTP + SSE · `qwen daemon start\|status\|logs\|stop\|restart` |
| 入口与调用 | `qwen serve`，默认绑定 `127.0.0.1:4170`；可加 `--port`（`0` 请 OS 分配临时端口）、`--hostname`、`--workspace`（可重复）、`--web`/`--no-web`、`--open`、`--max-sessions`（默认 32）、`--require-auth` 与 bearer token（`--token` 或 `QWEN_SERVER_TOKEN`）。v0.26.0 起另有 `qwen daemon` 命令族，根命令描述逐字为 “Inspect and control local qwen serve daemons”，五个子命令为 `start`（“Start a local qwen serve daemon in the background”）、`status`（“List local qwen serve daemons and their health”）、`logs`（“Show or follow a local daemon log file”）、`stop`（“Stop a local qwen serve daemon”）与 `restart`（“Restart a local qwen serve daemon on its recorded port and workspaces”）。 |
| 协议与输出 | HTTP REST 管理会话与工作区，SSE 推送事件；内部通过一个或多个 `qwen --acp` 子进程承载 Agent。`qwen daemon` 不引入新协议，只读运行时目录里的发现记录并打 HTTP 探测：健康探测是 `GET /health`（超时 1 秒，任何 HTTP 响应都算活，含 `--require-auth` 下的 401），`status --detail` 打 `GET /daemon/status`（超时 1.5 秒）取版本、运行时长、活动会话与 issue 数。`GET /daemon/status` 默认 `detail=summary`，只读内存态（会话、权限、SSE/ACP transport 计数、限流拒绝数、进程内存、解析后的 limits）且不启动 ACP 子进程，`?detail=full` 才给每会话诊断、ACP 连接细节、认证 device-flow 计数与工作区分节；`GET /capabilities` 与 `GET /daemon/status` 都暴露 `limits.maxRegisteredWorkspaces`。 |
| 具体行为 | 多客户端共享会话、权限请求和 Diff；SSE 支持 `Last-Event-ID` 重连，Web Shell 与 API 同源。`qwen daemon start` 以 detached 子进程（`detached: true`、`windowsHide: true`，子进程 stdio 指向一个日志 fd）启动 `qwen serve`，等它发布发现记录后打印绑定 URL、PID、日志路径与停止命令，再对子进程 `unref()` 回到 shell；默认端口 4170，按 `record.pid === child.pid` 而不是按端口匹配记录，因此支持 `--port 0`。同一规范工作区已有存活 daemon 且没传 `--port` 时拒绝启动，报 “qwen daemon: a daemon is already running for <path> on port <n>; pass --port to start another.”；`--wait` 要等到运行时无 `daemon_runtime_starting` issue 且不为 `error` 才返回，超时保留启动日志并以非零退出，不带 `--wait` 时只等发现记录（30 秒、每 100 ms 轮询，`--wait` 的就绪等待同样是 30 秒但每 250 ms 轮询）。`stop` 只在监听器应答 `/health` 或记录的 PID 仍存活时才发 SIGTERM，`--force` 在优雅超时（10 秒、每 100 ms 轮询）后加 SIGKILL，注册了多个 daemon 时必须传 `--port`，`--all` 停掉全部。`restart` 先经 `daemon stop` 停一个已注册 daemon、再经 `daemon start --wait` 按记录的端口与 hostname、记录的启动工作区、Web Shell 模式与 `--require-auth` 设置重启，`--web`/`--no-web` 与 `--require-auth`/`--no-require-auth` 覆盖记录，`--force` 只在你显式传时才转发给 `daemon stop`。`logs` 默认先打印末 50 行（`--lines`/`-n`），`--follow`/`-f` 每 250 ms 轮询续打，日志被轮转换名时先把旧句柄读到 EOF 再切。官方明确不做进程守护与崩溃重启。 |
| 会话与状态 | 发现记录在运行时目录（`$QWEN_RUNTIME_DIR`、`$QWEN_HOME`，否则 `~/.qwen`）下的 `daemon/daemon-<port>.json`，POSIX 上文件 `0600`、目录 `0700`，从不包含 bearer token；内容含绑定 URL、PID、已注册的规范工作区、日志路径、认证类型、`startedAt` 与写入方的 `pidNamespace`，用临时文件加改名原子发布。崩溃遗留的记录报 `stale`，由 `status --prune` 或 `stop` 清理；健康状态只有 `running`、`stale` 与 `unreachable` 三种。`start` 的启动日志名为 `start-<pid>-<时间戳>.log`、`0600`，启动成功后删除，失败或超时则保留并打印末 40 行，超过 24 小时的 `start-*.log` 会被清扫；logger 没有文件 sink（返回空串）时记录里省略日志路径、读侧回落到运行时目录的 `debug/daemon/daemon.log`。持久化 transcript 仍可分页读取和恢复；活跃进程状态在 daemon 重启后需重新加载，跨重启队列需应用层处理。 |
| 工具与能力 | 客户端可查询或控制工具、Skills、MCP、Approval mode、工作区和 Channel；严格变更路由要求 token。`qwen daemon` 只管进程生命周期，官方设计文档写明 “`qwen daemon start` is local process management; it does not change the serve protocol, authentication, or workspace isolation.”；ready 的 channel worker 之后崩溃时 daemon 继续运行、在有界重启策略下重拉它，并把状态（含 `channel_worker_exited` 告警）报进 `GET /daemon/status`。 |
| 认证与权限 | loopback 默认可无 token；非 loopback 绑定必须配置 bearer（`qwen daemon start` 下非 loopback 必须有 `QWEN_SERVER_TOKEN`），`--require-auth` 可在 loopback 上也强制 bearer，远程设备登录可走 device flow。`start` 从子进程环境里移除启动会话的标识与私有能力绑定，显式 token 通过环境变量而不是子进程参数传递，且子进程一律带 `--no-token-qr` 启动以免 token 进入启动日志。`status --detail` 只在记录说明该 daemon 用 bearer、且记录的进程存活、可寻址、启动时间与记录相符时才发送 `QWEN_SERVER_TOKEN`；记录的 PID 命名空间本进程无法寻址时绝不发送 bearer，没有 token 时要求 bearer 的 daemon 回报需要认证。 |
