# 阅读指南：这份对比到底在比什么

## 先说人话

Code Agent 不是只有“模型聪不聪明”一个维度。真实体验至少由五层组成：

1. **模型**：理解、推理和生成能力。
2. **Agent 运行时**：怎么读文件、改代码、跑命令、处理失败。
3. **安全与治理**：审批、沙箱、权限和团队策略。
4. **扩展系统**：MCP、Skills、Hooks、插件、Subagent。
5. **产品入口**：CLI、IDE、Desktop、Web、Cloud、SDK。

因此，本仓库比较的是完整产品表现，不做单纯模型跑分。

## 四种证据状态

| 标签 | 含义 | 能否写成“支持” |
| --- | --- | --- |
| 已实测 | 在指定版本和环境中真实运行过 | 可以，但要保留版本和环境边界 |
| 官方确认 | 官方文档、仓库、Release 或 Changelog 明确说明 | 可以写“官方提供”，不能冒充实测 |
| 源码确认 | 公开源码中能找到入口和实现 | 可以写“源码存在”，不代表产品默认可用 |
| 待验证 | 一手证据不足或不同 Surface 冲突 | 不能写成“不支持” |

## 三个容易踩坑的地方

### 1. 同名不等于同能力

五家都有“Plan”“Memory”“Subagent”之类的名字，但状态保存、权限继承、失败恢复和
展示方式可能完全不同。表格先写用户能做什么，再解释底层差异。

### 2. CLI、IDE、Desktop 和 Cloud 不能混写

例如 Codex App 的并行工作台不等于 Codex CLI 的 TUI；Qwen Daemon 的 HTTP+SSE
接口也不等于交互式 `qwen`。每项结论都应写清 Surface。

### 3. 版本变化很快

这个领域每天都在变。正文写当前结论，[版本与证据](./13-版本与证据.md)保存快照，
[updates](../updates/)记录重要变化。

## 本仓库不做什么

- 不把功能数量当产品得分。
- 不把营销页一句话扩写成完整工程能力。
- 不引用无法公开核验的实现细节。
- 不复制其他对比仓库的大段内容。
- 不因没有验证就断言某家“不支持”。
