# Qwen Code 产品机会

[返回首页](../README.md) · [查看五方矩阵](./02-功能总矩阵.md) ·
[查看版本与证据](./13-版本与证据.md)

这不是“照抄功能清单”。Qwen Code 已经有开源、多 Provider、Daemon、SDK、多端入口、
Subagent/Team/Workflow 和 Arena 等差异化能力。更有价值的方向，是把这些能力收敛成
稳定、可理解、可治理的产品体验。

## 已有优势：应继续保持

| 优势 | 为什么重要 | 建议 |
| --- | --- | --- |
| 开放源码与可定制运行时 | 企业能检查、修改和集成 | 保持核心协议稳定，降低二次开发升级成本 |
| 多 Provider | 不被单一模型与账号绑定 | 增加能力探测、统一错误和团队模型策略 |
| Daemon 与多客户端 | 能成为平台级 Agent 运行时 | 统一会话归属、生命周期、事件和权限模型 |
| TypeScript/Python/Java SDK | 覆盖前后端和企业 Java 生态 | 用同一套契约验证三个 SDK |
| IDE/Desktop/Web Shell/IM | 触达场景最宽 | 从“多个入口”升级为“一个任务到处继续” |
| Team/Workflow/Arena | 编排和评测空间大 | 收敛任务模型，统一状态、重试、隔离与汇总 |

## Now：优先补齐

### 1. 统一任务状态和错误解释

用户首先需要知道任务是运行中、等待审批、失联、失败还是完成。CLI、Daemon、Desktop、
Web Shell 和 IM 应使用同一状态机；Provider、权限、网络、工具、运行时错误要分层说明。

### 2. 做出默认交付闭环

把理解任务、编辑、聚焦测试、自查 Diff、Review、提交/PR、跟踪 CI 串成一条默认流程。
高级用户仍可拆开使用，但普通用户不需要自己拼装十几个命令。

### 3. 让权限边界一眼可见

任务开始前展示可写目录、网络、凭据和审批规则。提供“只读分析 / 安全编辑 / 受控自动
执行”三个结果导向预设，并让企业能够集中下发。

### 4. 提升多 Provider 的可预测性

在调用前探测工具、图片、上下文和结构化输出兼容性；失败时明确是账号、配额、网络、
模型能力还是 Provider 协议问题。

## Next：形成产品差异

| 方向 | 目标 |
| --- | --- |
| 跨端任务连续性 | CLI 发起，Desktop/Web/IM 查看并接管，不丢上下文与审批 |
| 云端/远程执行 | 在受控远程工作区继续长任务，具备密钥、日志、成本和接管能力 |
| 统一扩展中心 | MCP、Skill、Hook、Extension 的来源、权限、版本和 Surface 一处管理 |
| 可观测多代理 | 子任务的负责人、工作区、权限、状态、产物和冲突全部可见 |
| 企业治理 | Provider 白名单、策略、审计、数据边界与升级通道产品化 |

## Observe：先观察，不急着追

- 为了数量继续增加入口或 Agent 类型；
- 缺少稳定协议时扩大插件市场；
- 只在演示中好看、不能稳定恢复和重试的超长自治任务；
- 没有真实用户任务数据支撑的绝对排行榜；
- 为追平竞品名称而引入重复概念。

## 建议衡量指标

| 指标 | 比“功能数量”更有价值的原因 |
| --- | --- |
| 真实任务完成率 | 衡量是否交付，而非是否调用过工具 |
| 人工接管次数 | 反映默认流程是否可信 |
| 恢复成功率 | 衡量长任务、会话和运行时连续性 |
| 错误自解释率 | 反映用户能否不看源码就解决问题 |
| 跨 Surface 一致率 | 衡量 CLI/IDE/Desktop/IM 是否真是一套产品 |
| Provider 兼容通过率 | 把多模型优势变成稳定能力 |

## 一句话结论

Qwen Code 最应该学习的不是某一家独立功能，而是：

- Claude Code 的工作流成熟度；
- Codex 的沙箱和多任务工作台；
- Kimi Code 的轻量产品感；
- Qoder CLI 的云任务连续性；
- 同时保留 Qwen Code 自己的开放、多模型和平台化优势。
