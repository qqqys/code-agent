“执行前会问我”与“操作系统真的把它关在隔离区里”不是同一件事。本篇把它们分开：
权限规则负责决定是否允许，沙箱负责限制已经允许的进程能碰到什么。

## 五方表现

| 维度 | Claude Code | Codex | Qwen Code | Kimi Code | Qoder CLI |
| --- | --- | --- | --- | --- | --- |
| 操作审批 | Permission Mode 与 deny/ask/allow 规则 | Approval Policy，必要时逐动作升级 | Plan/Default/Auto/Edit/YOLO 等姿态 | 新版公开规则待补证 | 工具规则明确返回 allow/ask/deny |
| 文件边界 | 工作区权限；可配系统级隔离 | **三平台系统级沙箱是核心能力** | macOS Seatbelt、容器与项目 Trust | 新版边界待补证 | 文件操作有权限规则；系统隔离范围待证 |
| 网络边界 | 权限和 Managed Policy | 沙箱网络默认受限，可按策略开放 | Open/Closed/Proxied Network | 待验证 | Web/MCP 工具可设 allow/ask/deny |
| 危险命令 | 规则匹配与交互确认 | 沙箱加审批的双层限制 | 命令检查、审批姿态与沙箱组合 | 待验证 | Bash 规则可按命令模式控制 |
| 企业管控 | Managed Policy | Managed Config、工作区管理与监控 | 开源配置、Trust 与策略能力 | 待验证 | 账号、PAT、权限与云环境管理 |

## 三个容易混淆的概念

### 1. Plan 模式

模型只分析和给方案，通常不写文件。这是工作姿态，不等于系统沙箱。

### 2. 审批

工具准备执行某个动作时，产品询问用户，或用规则自动决定 allow/ask/deny。这能防止
误操作，但如果用户允许了，后续安全性仍取决于实际隔离边界。

### 3. 沙箱

即使进程想访问工作区外文件或网络，操作系统或容器也会拒绝。Codex 把这层能力做成
核心产品概念；Claude Code 和 Qwen Code 也提供系统或容器隔离路径。对 Kimi Code 和
Qoder CLI，当前公开资料不足以对所有入口给出同等精度的结论。

## 怎么选

- 个人仓库：默认审批、限制工作区外写入，通常已经够用。
- 公司代码：需要可集中下发的规则、审计记录和禁用项。
- 处理密钥或生产环境：必须同时确认文件、网络、子进程和凭据边界。
- 自动化流水线：不能依赖临时弹窗，必须有非交互式的最小权限配置。

## 对 Qwen Code 的启示

Qwen Code 已有多种姿态和沙箱入口，但名称多、组合多。更好的产品表达是直接给出三种
结果导向的预设：

| 预设 | 用户理解 | 建议边界 |
| --- | --- | --- |
| 只读分析 | 不改任何东西 | 禁止写入，网络默认关闭 |
| 安全编辑 | 只改当前项目 | 工作区可写，外部路径和网络按需询问 |
| 自动执行 | 适合受控 CI | 无弹窗、规则预先声明、完整审计 |

每次任务开始时显示“本次能写哪些目录、能否联网、哪些操作会询问”，比只展示模式名
更容易让人做出正确判断。
